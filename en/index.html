Why OpenAIR

Four old research problems, four closed-loop answers

OpenAIR models "how research gets done" as an orchestrable, verifiable, traceable four-stage process — not a hard-coded pipeline

PainLong cycles, fragmented tooling: literature, compute, experiments and writing each live in their own silos, with humans as the glue
OrchestrableOne four-stage process model; capabilities ship as skills, scheduled by a unified registry; long-horizon tasks run continuously
PainResults that don't reproduce: different person, different machine, different outcome — nobody can pinpoint the deviation
VerifiableSkills are defined by SKILL.md + I/O contracts, independently testable and replayable (replay mode reproduces the full pipeline with zero keys)
PainUntraceable evidence: which input, which version, which run produced this conclusion? No way to audit afterwards
TraceableEvery artifact carries a provenance chain — which skill, which inputs, which version — forming a trustworthy evidence chain
PainUnderused feedback: experimental results come back but rarely flow into the next round of design and decisions
Closed-loop iterationDry-lab (computational) and wet-lab (fabrication) feedback iterate in one loop, converging toward discovery

Mechanisms

Three pillars of the trustworthy loop

🔁 Process Orchestration

The four stages are an organizational frame, not a rigid pipeline: new results or feedback re-enter earlier stages, with humans confirming plans and key decisions at the workbench.

🧾 Evidence Chain

Tasks, artifacts, capability calls and source versions are recorded end-to-end; any conclusion can be audited along its evidence chain, and replay lets anyone reproduce it key-free.

🧩 Skill Ecosystem

200+ Markdown-shaped research skills with contracted inputs/outputs in a unified registry; a new domain is a new skill pack — no platform code changes.

git clone https://github.com/pdl-openair/OpenAIR.git
cd OpenAIR && cp .env.example .env
docker compose up -d --build
