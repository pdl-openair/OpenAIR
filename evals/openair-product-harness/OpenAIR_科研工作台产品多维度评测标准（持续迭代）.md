**版本：** v0.2.6（冻结基线元信息同步版）

**适用对象：** 产品经理、科研用户、课题负责人、UX / 信息架构设计师、UI 设计师、QA / 工程人员、证据审计人员、评测 Agent

**可选内部辅助证据基线：** openair-skill-lab `9a33ae9dce5b342909cf2caef9545fb265943a72`

## 0. 一页结论

### 0.1 评测目标

本标准用于判断 OpenAIR 是否已经达到“科研人员能够稳定推进真实科研任务，并获得可信、可追溯、可复用结果”的产品可用水平。

满分为 100 分。对外可用版本的放行条件为：

```text
总分 ≥ 90
且全部发布硬门槛通过
且 P0 = 0
且三类核心科研用户的代表性任务均真实跑通
```

评分不是视觉美观度评分，也不是单个 Skill 的输出质量评分。评测必须同时验证：

```text
科研用户是否能顺利推进任务
→ 是否理解当前阶段和下一步
→ AI 是否真正减少科研工作负担
→ 证据、来源、推断和假说是否清楚分层
→ 系统是否真实执行而非静默回放
→ 失败和部分成功是否透明
→ 关键产物是否能够回看、复用和交接
```

### 0.2 OpenAIR 的产品主线

```text
自然语言科研目标
→ 问题建模
→ 方案设计
→ 执行验证
→ 洞察生成
→ 形成可追溯科研产物
→ 支撑后续实验、计算、代码实验、报告或下一轮研究
```

OpenAIR 的一级价值不是“回答一个问题”，而是把科研目标组织成可执行、可追踪、可回溯、可复用的研究过程。

平台负责检索、整理、抽取、分析、生成、调用和记录。科研用户负责目标确认、关键选择、结果判断和后续决策。

### 0.3 首版锚定的三类核心科研用户

| 用户类型 | 典型任务 | 首版重点验证 |
|---|---|---|
| 计算机领域科研人员 | 文献调研、研究问题凝练、方法对比、代码实验、Benchmark 对比、结果分析 | 方法链路、基线对比、代码与实验产物、复现线索、引用回溯 |
| 理论材料领域科研人员 | 文献与计算证据整理、理论机制分析、候选体系推演、后续计算设计 | 参数条件完整性、理论证据、计算边界、机制链路、可计算验证建议 |
| 实验材料领域科研人员 | 配方、工艺、测试条件、性能结果与表征证据分析，形成下一轮实验建议 | 条件可比性、证据可信度、配方—结构—性能链路、可实验验证建议 |

三类科研用户共用一套平台主线，但代表性场景、证据要求和科研产物结构必须按领域适配。

| D8 | 信息架构、状态一致性与恢复 | 8 |

### 0.5 评测分层

OpenAIR 当前处于持续建设阶段。为避免“规则过严导致无法迭代”或“规则过松导致回放冒充真实运行”，评测分为四层：

| 层级 | 目的 | 允许的运行方式 | 是否可作为对外可用结论 |
|---|---|---|---|
| L0 结构评测 | 验证页面结构、信息层级和交互骨架 | Fixture | 否 |
| L1 集成回归 | 验证 API、状态持久化、产物读取和恢复 | API + Replay / Fixture | 否 |
| L2 真实链路评测 | 验证真实模型、真实适配器、真实外部来源、运行证明和失败透明度 | Live | 可用于内部试用 |
| L3 发布验收 | 三类科研用户代表性任务真实跑通，全部硬门槛通过 | Live + 人工抽检 | 是 |

任何页面展示、回放数据或 Fixture 样例，都不得静默冒充 Live 结果。


### 0.6 首版发布配置与计分口径

首版规则只覆盖：

```text
OpenAIR 科研工作台 MVP
```

必须评测：

```text
任务创建
任务推进
证据与来源回溯
运行模式识别
能力调用与产物关联
失败与部分成功透明
人工纠错
状态恢复
三类科研用户代表性流线
```

按本轮发布范围决定是否评测：

```text
真实代码执行
理论计算任务执行
实验设备调用
复杂团队协作
正式权限系统
```

如果某项能力未进入本轮发布范围，可以标记：

```text
N/A：本轮不适用
```

但必须满足：

1. 只能由产品负责人在评测开始前声明；
2. 不允许对发布硬门槛、三类核心用户必测场景和已承诺功能使用 N/A；
3. 不允许在评测结束后为了提高分数临时改为 N/A；
4. 报告必须记录 N/A 项及原因；
5. 调整后得分按适用项重新归一化。

计算方式：

```text
角色得分 = 该角色适用子项实得分 ÷ 该角色适用子项满分 × 100
全局得分 = 全部适用子项实得分 ÷ 全部适用子项满分 × 100
```

发布判定必须同时满足：

```text
全局得分 ≥ 90
计算机科研角色得分 ≥ 85
理论材料角色得分 ≥ 85
实验材料角色得分 ≥ 85
课题负责人审阅流线得分 ≥ 85
任一关键场景不得失败
```

不能使用平均分掩盖某一类用户不可用。

## 1. 文档目的与适用边界

### 1.1 本标准解决的问题

- 不再依赖“页面感觉不错”或“某个 Skill 跑通了”的局部判断。
- 让产品、科研用户、设计、QA、证据审计人员和多个评测 Agent 使用同一套口径独立评分。
- 将 OpenAIR 的产品体验、科研可信度和真实运行证明纳入同一闭环。
- 将问题统一沉淀为可回归验证的 P0 / P1 / P2 清单。
- 保证优化始终围绕科研任务推进和科研产物，而不是围绕页面局部美化或单个 Skill 散点修补。
- 为后续“Agent 自动评测 → 自动修复 → 自动回归 → 人工复核 → 规则迭代”建立可执行基准。

### 1.2 适用范围

本标准覆盖 OpenAIR 桌面端科研工作台，包括：

```text
任务创建
任务看板
任务详情
主工作台
四阶段导航
二级科研节点
人机协作
必要确认
能力调用记录
科研产物展示
来源与证据回溯
状态恢复
错误与部分失败
基础桌面适配
```

### 1.3 不在本轮规则范围内

- 单个 Skill 的全部专业质量细则；
- 全量领域能力完备度；
- 正式权限系统与复杂团队管理；
- 完整态势看板的数据分析能力；
- 低收益视觉微调；
- 成熟生产环境的全量安全审计。

### 1.4 OpenAIR 与 openair-skill-lab 的平台边界

本标准的唯一主评测对象是：

```text
OpenAIR 对外科研工作台
```

当前首轮优化重点是：

```text
多视角 UI / UX 设计优化
基础前后端流程 Bug
跨页面状态一致性
真实用户主流线
错误、恢复与产物回看
```

`openair-skill-lab` 是内部 Skill 迭代平台。优化后的 Skill 再按发布流程上线 OpenAIR。它不属于本轮 OpenAIR 产品级 Harness 的主评测对象，也不得阻塞首轮产品体验评测和集中收口。

| 对象 | 定位 | 主要评测问题 | 评测单位 |
|---|---|---|---|
| OpenAIR | 对外产品；本标准唯一主评测对象 | 科研用户能否完成真实任务，理解状态，获得可信可追溯产物 | 完整用户流线、页面、跨 Skill 链路、科研产物 |
| openair-skill-lab | 内部 Skill 迭代与优化平台；按需提供辅助证据 | 单个 Skill 是否符合契约、稳定、可追溯、可执行 | 单个 Skill、输入输出、Schema、Deterministic Checks、人工评分 |

两套评测有关联，但不能混为一体。

```text
单个 Skill 全部通过
≠
OpenAIR 产品真实可用

Skill Lab 尚未完成某项内部治理
≠
必须暂停 OpenAIR 首轮 UI / UX 与基础流程优化
```

只有当 OpenAIR 的 L2 / L3 真实链路涉及特定 Skill，且必须验证其真实执行、输出契约或来源证据时，才按需接入对应 Skill Lab 证据。

## 2. 源码只读盘点结论

### 2.1 已确认的产品主线

当前源码与产品文档已明确：

```text
问题建模 → 方案设计 → 执行验证 → 洞察生成
```

该主线允许按不同科研场景启用、跳过、回退、重跑、分支或局部迭代，但状态、产物和回溯关系必须保留。

### 2.2 已确认的核心页面

| 页面 | 当前定位 |
|---|---|
| Workbench 主工作台 | 自然语言入口，承接阶段结果、人机确认、补充输入、能力执行与科研产物查看 |
| Task Board 任务看板 | 快速判断任务状态、关键进展、价值产物、风险和下一步 |
| Task Detail 任务详情 | 回看节点状态、运行记录、失败原因、能力调用和完整产物 |
| Situation Board 态势看板 | 面向平台效能、统计、协作和 Skill 使用情况；尚不是本轮重点 |
| Settings 设置 | 系统配置页面，不属于科研主链路 |

### 2.3 已确认的工作台结构

主工作台采用三栏结构：

```text
左侧：任务流 / 阶段导航
中间：主内容流 / 阶段结果与科研产物
右侧：人机协作 / 确认、追问、提醒与快捷操作
```

该结构适合承载不同领域流程，但评测必须防止：

- 左中右三栏重复争夺注意力；
- 复杂节点树、长日志和底层字段直接暴露给科研用户；
- 右侧协作区退化成流水日志；
- 材料字段或计算机字段写死到通用工作台；
- Fixture、Replay 和 Live 状态表达不清。

### 2.4 已确认的运行模式边界

当前源码中同时存在：

```text
API 数据
Fixture 回退
Replay
Live
```

这对开发和演示有价值，但也形成产品风险：

```text
回放结果或前端 Fixture 不能静默冒充真实执行结果
```

后续产品评测必须显式记录：

```text
source_mode
run_id
runtime
provider / adapter
started_at
finished_at
status
关联能力调用
关联产物
来源或外部检索状态
```

### 2.5 已确认的 Skill Lab 基础能力

当前 openair-skill-lab 已支持：

- 动态发现注册 Skill；
- Fixture Replay；
- 部分白名单 Skill 的 Live Run；
- Schema Checks；
- Deterministic Checks；
- 真实模型结构化输出验证；
- 运行结果落盘；
- 人工逐维度评分保存。

下一阶段仍需补齐：

- Agent Grader；
- 人评与 Agent 评分对齐；
- 多 Skill 串联评测；
- 产品级浏览器流线评测；
- 三类科研用户代表性任务评测；
- 产品级证据包汇总。

## 3. 内部设计原则

### 3.1 科研目标优先

页面必须持续回答：

```text
用户正在研究什么？
当前处于哪一阶段？
系统刚刚完成了什么？
留下了哪些科研产物？
下一步最值得做什么？
```

### 3.2 科研证据优先于生成内容

系统生成的总结、解释和研究线索必须建立在可回溯证据之上。

默认展示层应明确区分：

```text
原始来源
结构化证据
系统归纳
机制解释
推断
假说
待验证建议
```

### 3.3 真实运行必须可证明

任何 Live 结果必须附带可核查的运行证明。任何 Fixture 或 Replay 都必须显式标记。

禁止：

```text
页面看起来像真实运行
但实际来自静默 Fixture 或 Replay
```

### 3.4 部分失败必须透明

外部检索、文献访问、模型调用、代码执行、计算任务、设备调用和产物生成都可能部分失败。

产品必须告诉用户：

```text
哪些成功
哪些失败
失败影响什么
当前结果还能否使用
建议如何继续
```

### 3.5 AI 必须形成行动

AI 输出不能只是长篇解释。每轮输出应尽可能形成：

```text
可确认
可修改
可补充
可重试
可跳过
可返回修改
可进入下一阶段
```

### 3.6 OpenAIR 不替代科研判断

系统负责推进、整理、生成和记录。涉及研究目标、关键假说、实验方案、计算条件、证据冲突、结论采纳和后续投入时，应保留人工确认点。

### 3.7 通用主干稳定，领域适配可变

```text
一级阶段：稳定
二级科研节点：按场景配置
三级 Skill / 工具：按能力替换
结果块：按领域插拔
```

### 3.8 普通科研视图与审计视图分层

普通科研用户默认只需要看到：

```text
当前任务
当前阶段
关键证据
结果边界
失败影响
下一步
```

审计视图再按需展开：

```text
run_id
runtime
provider / adapter
model
skill_hash
输入快照
配置快照
来源清单
转换过程
artifact_hash
完整 Capability Call
```

禁止为了证明系统“真实运行”而把底层运行噪声直接堆在主工作台。
也禁止为了界面简洁而隐藏必要的真实性证据。

### 3.9 能力边界与纠错闭环

产品必须明确告诉用户：

```text
当前系统能做什么
当前系统不能稳定做什么
本次结果的可信边界
用户如何修改、纠错、重跑或撤回
```

当 AI 结果仅部分正确时，用户应能够局部修订，而不是被迫全部重来。

### 3.10 以证据评分

每个扣分项必须附带至少一种证据：

```text
截图
录屏
浏览器 Trace
网络请求
控制台日志
运行记录
Capability Call
产物文件
来源回溯结果
前后版本对比
```


### 3.11 从单点现象抽象为可复用规则

人工或 Agent 发现新问题后，不得直接进入单点修补。必须先判断：

```text
这是单一页面偶发问题，还是同类页面可能重复出现的结构性问题？
问题背后的用户任务、信息层级或交互约束是什么？
能否写成可复用规则？
能否转化为 Harness 自动检查或 Agent 证据评审项？
同类页面、同类状态和常见视口是否需要批量扫描？
```

默认处理顺序：

```text
发现现象
→ 聚类与根因判断
→ 迭代评测规则
→ 将规则转为 Harness Gate / Regression Case
→ 扫描同类页面与同类状态
→ Agent 按最小批次批量修复
→ 自动回归
→ 人工抽检
→ 将新盲区继续回写规则
```

禁止：

```text
看到一张截图
→ 只改一个高度、一个文案或一个卡片
→ 不检查同类页面
→ 不补规则
→ 不补回归
```

## 4. 使用方法

### 4.1 每轮评测组成

每次完整回归至少包含：

| 类型 | 说明 |
|---|---|
| 产品主线检查 | 验证四阶段主线、主行动、页面边界和最终科研产物 |
| 三类科研用户流线 | 分别完成计算机、理论材料、实验材料代表性任务 |
| 真实运行检查 | 验证 Live / Replay / Fixture 区分，运行证明，外部来源与部分失败 |
| 数据与状态检查 | 验证任务状态、阶段状态、能力调用、产物引用和恢复 |
| UX / UI 检查 | 验证信息层级、密度、可读性、侧栏和基础桌面适配 |
| 证据审计 | 抽查来源、证据、推断、假说和建议的回溯链路 |
| Skill Lab 辅助证据接入（按需） | 仅在 L2 / L3 涉及特定真实 Skill 时，复用其 Schema、Deterministic Checks 与人工评分结果；不阻塞首轮 UI / UX 与基础流程评测 |

### 4.2 执行顺序

1. 固定版本号、测试环境、账号、模型配置和测试数据。
2. 明确本轮属于 L0、L1、L2 或 L3。
3. 使用同一套基准 Fixture 和 Live 场景运行全部必测流程。
4. 每位评测 Agent 独立记录问题与评分，不先互相影响。
5. 对每个问题附带证据，并标注维度、场景、严重程度和回归条件。
6. 将问题按用户任务、页面区域、状态类型和根因模式聚类，判断是单点 Bug 还是结构性问题。
7. 对结构性问题先更新评分规则、检查清单、必测场景或证据要求。
8. 将新增规则转化为 Harness Gate、视觉回归项、Regression Case 或 Agent 证据评审项。
9. 使用新 Harness 扫描同类页面、同类状态和常见视口，形成第一批批量收口范围。
10. 只优先修复 P0 和高收益 P1，避免低收益散点优化。
11. 使用相同场景回归，保留修复前后证据。
12. Agent 平均分达到 90 分并且硬门槛全部通过后，再交人工体验验收。
13. 人工发现的新问题必须再次进入“规则迭代 → Harness 迭代 → Agent 自动修复 → 回归 → 人工复核”闭环。

### 4.3 单项评分锚点

| 得分比例 | 含义 |
|---|---|
| 100% | 达到当前层级可用水平，无明显阻碍 |
| 80% | 基本可用，存在少量可绕过问题 |
| 60% | 可以完成任务，但理解成本、操作成本或科研复核成本明显偏高 |
| 40% | 经常犹豫、重复操作或依赖人工兜底 |
| 20% | 任务明显受阻，结果可信度不足 |
| 0% | 无法完成，或结果不可用、不可信、不可回溯 |

### 4.4 总分与放行规则

| 总分 | 判定 |
|---:|---|
| 90–100 | 达到目标层级；硬门槛通过后可进入人工体验验收 |
| 80–89 | 可进入集中收口；优先批量修复高收益 P1 |
| 70–79 | 产品结构、可信度或真实链路仍需明显优化 |
| 0–69 | 暂不适合扩大使用 |

无论总分多少，只要任一发布硬门槛失败，均不得判定为“对外可用”。

### 4.5 三类证据责任

每个评分子项必须标注主要验证方式：

| 标记 | 含义 | 适用内容 |
|---|---|---|
| M | 机器确定性检查 | 字段、状态、文件、引用、运行记录、接口响应、可访问性扫描 |
| A | Agent 证据评审 | 页面层级、任务推进、科研证据表达、领域适配、UI 一致性 |
| H | 人工抽检 | 科研价值判断、真实可理解性、复杂领域结论、Agent 评分盲区 |

原则：

```text
机器能稳定判定的，不交给 Agent 猜测。
Agent 可以初筛但容易误判的，必须保留人工抽检。
人工新发现的问题，必须回写为 M / A / H 中至少一种可执行检查。
```

### 4.6 Agent 评分校准

Agent 评分不得直接作为唯一放行依据。首轮必须建立一套人工校准样本：

```text
至少 10 个历史页面问题
至少 5 个真实运行问题
至少 5 个证据可信度问题
至少 3 个领域适配问题
```

对每个样本保存：

```text
人工结论
严重程度
评分项
证据
期望 Agent 判断
```

发布前要求：

```text
硬门槛漏判数 = 0
P0 漏判数 = 0
Agent 与人工的维度评分差异原则上 ≤ 10 分
```

## 6. 发布硬门槛

任一硬门槛失败，对外可用结论均为：

```text
暂不可发布
```

即使总分达到 90 分也不能放行。

| 编号 | 硬门槛 | 通过条件 |
|---|---|---|
| G01 | 三类科研用户代表性任务跑通 | 计算机、理论材料、实验材料各至少 1 条真实科研流线可完成 |
| G02 | 四阶段主线无阻断 | 从科研目标到可复核科研产物，真实环境可推进 |
| G03 | 运行模式可辨识 | Live、Replay、Fixture 不得静默混用或冒充 |
| G04 | Live 运行证明完整 | Live 结果具有 run_id、runtime、provider / adapter、model、skill_hash、输入与配置快照、状态、耗时和关联产物；普通用户视图允许简化展示，审计视图必须可展开 |
| G05 | 来源可回溯 | 关键证据可回到真实来源、元数据或原文片段 |
| G06 | 事实、证据、推断和假说分离 | 用户不会将 AI 推断误判为已验证事实 |
| G07 | 部分失败透明 | 外部检索、来源访问、模型、代码、计算或设备失败均明确提示影响 |
| G08 | 科研判断保留人工确认 | 高风险目标、方案、冲突证据和结论不得被系统静默确认 |
| G09 | 产物可回看与可复用 | 关键产物可打开、可定位、可回溯、可交接 |
| G10 | 状态一致且可恢复 | 刷新、退出、重新进入后任务状态、阶段和下一步一致 |
| G11 | 跨域适配不写死 | 通用工作台不被单一领域字段污染 |
| G12 | 无内部噪声外泄 | 默认用户视图不暴露调试日志、内部 Schema、秘密值或无关技术字段 |
| G13 | 阻断性错误为零 | 必测场景中不存在导致任务无法继续的前端、接口、权限、数据或运行错误 |
| G14 | 敏感信息不外泄 | 页面、日志、产物和证据包不得暴露密钥、Token、密码或不应公开的数据 |
| G15 | 能力边界清楚且支持纠错 | 用户能够理解系统能做什么、不能稳定做什么，并可局部修改、重试、撤回或返回修改 |
| G16 | 普通科研视图与审计视图分层 | 普通用户不被底层日志淹没；审计人员仍可展开查看完整运行证明 |
| G17 | 基础可访问性可用 | 核心流线支持键盘操作、可见焦点、文本错误提示和常见桌面宽度下的可读性 |

## 7. 多角色评测分工

### 7.1 核心科研用户

| 角色 | 重点检查 | 必须回答的问题 |
|---|---|---|
| 计算机领域科研人员 | 方法链路、Benchmark、代码实验、基线、复现与论文产物 | 系统是否帮助我缩小问题、比较方法并形成可复现的下一步？ |

### 7.3 评分汇总原则

- 各角色独立评测后再汇总。
- 三类核心科研用户均必须完成代表性场景。
- 最终总分使用 100 分权重表汇总。
- 任一核心科研用户评分低于 85 分，不得进入发布验收。
- 任一硬门槛失败，不得被平均分掩盖。
- 争议项以真实任务证据为准，不以个人审美裁决。

### 7.4 多用户流线

领域差异之外，还必须覆盖不同使用方式。首版至少包含：

| 用户流线 | 目标 | 必测内容 |
|---|---|---|
| U01 首次使用的科研执行者 | 验证无需培训也能开始任务 | 创建任务、理解系统能力边界、完成第一步、识别下一步 |
| U02 持续推进任务的科研执行者 | 验证日常使用效率 | 恢复上下文、局部修改、重跑、查看新增产物、处理部分失败 |
| U03 课题负责人 / PI 快速审阅 | 验证决策效率 | 在 3 分钟内判断当前进展、关键证据、风险、待确认项和是否继续投入 |
| U04 跨领域切换用户 | 验证通用骨架 | 在计算机、理论材料和实验材料任务之间切换，确认信息表达不串域 |
| U05 证据审计者 | 验证可信度 | 从结论回到证据、来源、运行记录、模型与能力调用信息 |

发布时必须同时输出：

```text
全局得分
三类核心科研用户得分
U01–U05 流线完成率
最差流线得分
```

## 8. 必测真实场景

### 8.1 通用基准测试数据

每次回归至少保留四类脱敏测试包：

| 测试包 | 用途 | 特征 |
|---|---|---|
| Fixture A：信息不足 | 验证问题澄清、补充输入和必要确认 | 只有粗粒度科研目标，缺少关键边界 |
| Fixture B：信息较完整 | 验证主链路 | 包含研究对象、目标、约束、来源范围和预期输出 |
| Fixture C：冲突或补充信息 | 验证状态更新、证据冲突和局部重跑 | 新增材料、冲突来源、修订约束 |
| Fixture D：失败与部分成功 | 验证降级透明度和恢复 | 来源不可访问、部分检索失败、模型失败、重复提交或产物缺失 |

### 8.2 通用场景

| 场景 | 用户任务 | 成功条件 | 关键证据 |
|---|---|---|---|
| S01 创建科研任务 | 输入 Fixture A，创建任务并确认研究目标 | 系统提出必要问题，用户知道下一步 | 截图、录屏、任务记录 |
| S02 推进四阶段 | 使用 Fixture B 推进至可复核科研产物 | 阶段、节点、产物和下一步清楚 | Trace、Capability Call、产物 |
| S03 查看历史产物 | 从看板进入详情，定位历史阶段和产物 | 可回看来源、版本、能力调用和阶段 | 截图、产物记录 |
| S04 退出后恢复 | 刷新、退出或重新登录后继续任务 | 状态、阶段、产物和下一步不丢失 | 录屏、前后对比 |
| S05 识别运行模式 | 分别运行 Fixture、Replay 和 Live | 三种模式清楚标记，不会误判 | 页面截图、运行记录 |
| S06 部分失败恢复 | 模拟来源不可访问、调用失败或重复提交 | 成功与失败部分分离，可理解、可继续 | 错误截图、日志、结果边界 |
| S07 证据回溯 | 从研究线索回到证据，再回到来源 | 回溯路径完整 | 来源截图、证据链 |
| S08 基础桌面适配 | 常见桌面宽度下展开或收缩侧栏 | 主工作区可操作；滚动容器贴合视口 | 分辨率记录、截图 |
| S16 视口滚动贴合 | 在任务看板、任务详情等 App Shell 页面浏览长内容 | 仅主内容区滚动；滚动条轨道贴齐视口；无页面级双滚动 | 截图、滚动容器度量 |
| S17 Workbench 信息层级与互动空间 | 在历史阶段查看、同阶段非当前二级节点浏览、回放结果、左右侧栏展开 / 折叠等状态下检查工作台 | 同一语义只有一个主展示区；提示分层不重复；查看同阶段非当前二级节点时须显示局部浏览态提示，且不得与全局回放提示重复占屏；互动时间线可读、可滚动、可恢复历史上下文；中心任务区不被持续挤压 | 多视口截图、DOM 度量、滚动记录、人工 10 秒口述 |
| S18 Workbench 主展示可读性与产物态覆盖 | 在左右侧栏组合、常见桌面视口、无产物与有产物状态下检查中心任务区 | 去重后保留的唯一主展示区必须可读：关键进展、风险、待确认事项和下一步不得仅以不可展开的省略号隐藏；无产物状态不得长期以大面积空白占据主视口；必须覆盖至少一个真实挂载产物或结构化结果可阅读场景 | 多视口截图、文本溢出度量、展开入口检查、产物态 Fixture、人工 10 秒口述 |
| S09 状态一致性 | 对比看板、详情、工作台和产物状态 | 状态无冲突 | 页面截图、接口结果 |
| S10 人工确认 | 修改目标、方案或关键结论 | 人工确认点清楚，修改可生效 | 录屏、修改前后对比 |
| S11 首次使用与能力边界 | 首次进入系统，理解适用范围并创建任务 | 用户知道系统能做什么、不能稳定做什么，知道从哪里开始 | 首屏截图、口述记录、录屏 |
| S12 AI 结果局部纠错 | 对一个部分正确但存在错误的 AI 结果进行修订 | 可局部编辑、补充证据、重试或撤回，不必全部重来 | 修改前后产物、录屏 |
| S13 PI 三分钟审阅 | 课题负责人快速查看任务 | 3 分钟内判断当前进展、关键证据、风险、待确认项和下一步投入 | 计时、口述、截图 |
| S14 长任务与中断恢复 | 启动长任务，刷新或离开后返回 | 状态持续可见，返回后不中断或可恢复，失败影响清楚 | Trace、录屏、状态记录 |
| S15 基础可访问性 | 使用键盘完成核心页面导航和关键操作 | 关键控件可达、焦点可见、错误有文本提示，常见桌面宽度下可读 | 自动扫描、键盘录屏、截图 |

### 8.3 计算机领域科研人员场景

#### CS01 方法路线与研究空白分析

```text
任务示例：
围绕“多模态对齐在视觉检索中的方法路线”，检索近年代表性工作，
比较任务设定、数据集、Benchmark、方法机制、代码可用性和局限，
形成研究空白与下一轮实验建议。
```

成功条件：

- 研究目标与检索范围明确；
- 可查看论文候选、筛选理由和来源；
- 可比较方法路线、Benchmark 和代码可复现性；
- 关键判断能够回到论文来源；
- 形成可执行的实验或复现任务；
- 生成可复用的报告片段或下一轮输入包。

#### CS02 代码实验与结果分析

```text
任务示例：
选择一个代表性基线，形成代码实验任务，
记录执行状态、输出、失败原因、结果对比和后续建议。
```

成功条件：

- 代码执行与静态示例明确区分；
- 执行记录、结果、错误和产物可回看；
- 用户能够判断是否值得继续扩大实验。

### 8.4 理论材料领域科研人员场景

#### TM01 机制证据与计算验证建议

```text
任务示例：
围绕高电压、快充条件下锂金属电池电解液设计，
整理溶剂化结构、界面膜形成机制和理论计算证据，
提取结合能、静电势、计算方法、边界条件和不确定性，
形成可进入后续计算验证的候选体系。
```

成功条件：

- 理论证据、实验观察和系统推断分层；
- 关键计算参数与边界条件可查看；
- 机制链路可回到来源；
- 候选体系能够进入后续计算任务；
- 不确定性和待验证点清楚。

### 8.5 实验材料领域科研人员场景

#### EM01 配方—条件—性能—机制链路分析

```text
任务示例：
围绕高电压、快充条件下锂金属电池电解液设计，
抽取电解液配方、正极负载、锂箔厚度、充放电协议、
可逆容量、循环寿命、表征证据与机制解释，
形成可进入下一轮实验验证的配方候选。
```

成功条件：

- 不同来源的实验条件完整且可比较；
- 缺失条件显式标记；
- 配方、结构、性能与机制链路清楚；
- 研究线索区分证据、推断和建议；
- 输出能够作为实验或贝叶斯优化输入。

### 8.6 跨域通用性场景

#### X01 三领域切换

依次加载计算机、理论材料和实验材料场景。

成功条件：

- 四阶段主线稳定；
- 左中右三栏职责稳定；
- 领域特定字段只在对应结果块出现；
- 通用工作台不被单一领域字段污染；
- 能力调用和产物模型可复用。

## 9. 定量指标与 90 分目标

以下指标为 OpenAIR 内部产品优化目标，不等同于外部认证要求。

| 指标 | L3 发布目标 | 说明 |
|---|---:|---|
| 发布硬门槛通过率 | 100% | G01–G14 全部通过 |
| 必测通用场景完成率 | 100% | S01–S10 均可完成 |
| 三类科研用户代表性任务完成率 | 100% | CS、TM、EM 至少各 1 条 Live 主链路 |
| 阻断性问题 P0 | 0 | 不允许存在主链路、可信度、数据或恢复阻断 |
| 高优先级问题 P1 | 原则上 ≤ 3 | 仅允许明确可绕过且不破坏主线的问题 |
| 核心科研用户单角色得分 | ≥ 85 / 100 | 防止平均分掩盖某一领域不可用 |
| 总分 | ≥ 90 / 100 | 进入人工体验验收的前提 |
| 新用户 10 秒识别下一步 | ≥ 90% | 进入关键页面后能准确说明动作 |
| 代表性科研任务成功率 | ≥ 90% | 真实用户可完成规定任务 |
| Live / Replay / Fixture 标记准确率 | 100% | 不允许静默回退 |
| Live 运行证明覆盖率 | 100% | Live 结果必须具有可核查运行记录 |
| 关键证据可回溯率 | ≥ 95% | 抽查关键结论与来源 |
| 关键产物可打开率 | 100% | 产物可查看、可复用 |
| 状态恢复成功率 | 100% | 刷新、退出、重新进入不丢失上下文 |
| 状态冲突数 | 0 | 看板、详情、工作台、运行记录一致 |
| 部分失败可解释率 | 100% | 失败影响和下一步清楚 |
| 单任务易用度 SEQ 平均分 | ≥ 5.5 / 7 | 识别高摩擦步骤 |
| 基础交互反馈 | ≤ 1 秒出现状态提示 | 长任务可继续执行，但必须及时提示运行状态 |

性能阈值需要在首轮基线后进一步按场景细化，不应在没有真实基线时虚构统一耗时目标。

### 11.4 人工反馈进入自动修复前的转译要求

人工反馈不得直接等同于开发任务。每条反馈在进入 Agent 自动修复前，必须补齐：

| 字段 | 说明 |
|---|---|
| 用户现象 | 用户实际看到或遇到什么 |
| 用户影响 | 为什么影响理解、判断、推进或复核 |
| 根因模式 | 信息重复、层级混乱、空间挤压、状态不透明、恢复缺失等 |
| 泛化范围 | 哪些页面、状态、视口或用户角色可能同样受影响 |
| 新增或修改规则 | 应修改哪一条评分项、检查清单、场景或硬门槛 |
| Harness 转译 | 可沉淀为 DOM 度量、视觉截图、状态门禁、Regression Case 还是 Agent 证据评审 |
| 批量修复边界 | 第一批应同时收口哪些同类问题 |
| 回归条件 | 如何证明问题真正解决且没有引入回归 |

默认门禁：

```text
没有完成规则转译
→ 不进入自动修复

没有完成同类扫描
→ 不进入批量收口

只修一个截图中的表象
→ 不视为完成
```


### 11.5 Harness 场景确定性与失败归因

浏览器级回归必须确保每条用例可以独立运行，也可以在完整 baseline 中稳定复现。浏览器上下文隔离不能替代后端 Fixture、Replay 任务状态和服务端数据的显式场景准备。

每个 Regression Case 在执行产品断言前，必须先完成：

```text
固定测试任务或创建独立测试任务
→ 建立目标页面状态
→ 建立目标阶段与二级节点
→ 建立侧栏展开 / 折叠状态
→ 建立视口
→ 校验场景前置条件
→ 再执行产品 Gate
```

失败必须区分：

| 失败类型 | 含义 | 处理方式 |
|---|---|---|
| HARNESS_SETUP_FAIL | 未稳定进入目标场景、前置条件不满足、测试选择器或共享测试状态漂移 | 只迭代 Harness，不修改产品源码 |
| PRODUCT_GATE_FAIL | 已确认进入目标场景，但产品未满足规则 | 进入产品结构性修复 |
| INFRA_FAIL | 隔离服务、依赖、端口或运行环境失败 | 修复基础设施，不计入产品问题 |

每个高收益 Gate 至少保存：

```text
scenario_id
task_id
expected_stage
actual_stage
expected_substage
actual_substage
expected_sidebar_state
actual_sidebar_state
viewport
precondition_status
gate_status
failure_type
```

默认要求：

```text
定向运行 PASS
且
完整 baseline PASS
且
相同场景前置条件一致
→ 才可冻结 Gate

未校验前置条件
→ 不允许将失败归因到产品

通过放宽阈值、删除断言或依赖执行顺序刷绿
→ 禁止
```


### 11.6 去重后的可读性与产物态覆盖

信息架构去重不能以隐藏关键信息为代价。将多个重复区域收口为唯一主展示区后，必须继续验证：

```text
唯一主展示区是否完整可理解
→ 关键字段是否发生文本溢出
→ 溢出时是否存在明确展开或详情入口
→ 无产物状态是否产生大面积无效留白
→ 有产物状态是否覆盖真实长文本、结构化证据与来源阅读
```

Harness 至少应区分：

| 场景类型 | 必测内容 |
|---|---|
| EMPTY_ARTIFACT | 无挂载产物时，空状态说明、下一步与空间利用是否合理 |
| POPULATED_ARTIFACT | 有正文、结构化证据或来源时，主产物区是否可读、可滚动、可回溯 |
| OVERFLOW_SUMMARY | 进展、风险或下一步超过单行宽度时，是否可展开或查看详情 |

默认要求：

```text
只验证“去重成功”
但未验证“唯一主展示区可读”
→ 不允许冻结

只在无产物 Fixture 上评审工作台
→ 不足以证明科研产物阅读体验可用
```

## 14. 人工反馈如何回写规则

人工验收不是终点。人工发现的新问题必须落入以下至少一种形式：

| 反馈类型 | 回写方式 |
|---|---|
| 反复出现的体验问题 | 新增或修改评分子项，并补充同类页面扫描 |
| 不能被平均分掩盖的问题 | 新增硬门槛 |
| 特定任务下才出现的问题 | 新增真实场景 |
| 历史 Bug | 新增 Regression Case |
| 视觉层级、信息密度或空间挤压问题 | 新增 UI / UX 检查项，并优先转为多视口截图基线、DOM 度量或 Agent 证据评审 |
| 同一语义跨区域重复 | 新增信息架构规则，明确唯一主展示区、摘要区与入口区 |
| 状态提示重复或冲突 | 新增提示分层规则，区分全局来源、局部状态、异常和风险 |
| 互动历史难以查看 | 新增互动区最小可用视口、滚动回看和扩展查看规则 |
| 证据不够完整 | 新增证据采集字段 |
| Agent 评分与人工差异大 | 修改评分锚点或 Agent 指令 |
| 某领域长期不适配 | 新增领域适配规则或结果块规范 |

每轮人工验收后应记录：

```text
新增规则
修改规则
新增场景
新增回归用例
新增 Harness Gate
同类页面与同类状态扫描范围
批量修复边界
评分锚点调整
不再适用的旧规则
```

## 17. 外部参考依据

本标准参考并结合 OpenAIR 产品特点进行裁剪：

1. ISO 9241-11:2018：在明确使用情境中理解和评价可用性。
2. ISO 9241-210:2019：围绕用户、用户需求和使用情境持续开展以人为中心的设计。
3. ISO/IEC 25010:2023：使用产品质量模型检查功能适合性、可靠性、性能效率、交互能力、安全性等质量特征是否遗漏。
4. GOV.UK Service Standard：理解用户需求、解决完整问题、让服务易用、持续迭代并定义成功指标。
5. Nielsen Norman Group：系统状态可见、贴合真实世界、用户控制、一致性、错误预防、减少记忆负担、提升效率、简洁、错误恢复和帮助文档。
6. WCAG 2.2：基础可访问性应考虑可感知、可操作、可理解和稳健，并关注键盘焦点、错误识别和错误建议。
7. NIST AI RMF 与 Playbook：记录数据来源、转换过程、限制、测试方法、性能结果和系统透明度。
8. Microsoft HAX Guidelines：明确 AI 能力边界、表达系统表现水平，并在 AI 出错时支持高效纠错。
