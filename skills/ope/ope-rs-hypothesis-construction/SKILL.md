# 假设构建（L3 — OPE）

将凝练后的研究问题转化为可证伪的假说，建立理论框架，完成可行性评估。

## Method

### 子任务 1：建立理论模型
1. **识别核心变量**：
   - 自变量：研究方法（如新估计器形式、新的奖励变换）
   - 因变量：评估指标（MSE / Bias / Variance / 样本效率 / 覆盖度）
   - 控制变量：行为策略、数据规模、网络结构、随机种子
   - 中介/调节变量：奖励分布稀疏性、动作空间维度

2. **建立变量关系**：
   - 用箭头表示方向（`A → B`）
   - 标注关系性质（`+` 正相关、`-` 负相关、`?` 待验证）

3. **构建概念框架**：
```markdown
### 核心变量定义
| 变量名 | 类型 | 操作化定义 | 测量方式 |
|--------|------|-----------|---------|
| X（新估计器） | 自变量 | DR + 自适应权重 | 实现版本号 |
| Y（MSE） | 因变量 | 估计值与真值均方误差 | 离线评估对照真值 |

### 变量关系假设
- H1: X → Y（X 相比 DR 基线降低 Y）
- H2: 数据规模 N 调节 X → Y 的强度
```

### 子任务 2：可行性预评估
从四个维度评估：

| 维度 | 评估点 |
|------|--------|
| 数据 | D4RL/RecoGym/私有数据是否可获取，规模与质量 |
| 计算 | GPU/TPU 资源需求，现有硬件是否满足，云成本预估 |
| 环境/工具 | PyTorch/TensorFlow/JAX 选型，d3rlpy/ogle 等库的复现难度 |
| 时间 | 各阶段工期分解，总工期是否可接受 |

输出综合可行性结论（高/中/低 + 主要风险点 + 应对方案）。

### 子任务 3：生成可验证假说
假说必须满足四个硬条件：
1. **可证伪**：必须有被反驳的可能（拒绝"也许"、"可能"等模糊表述）
2. **具体**：变量、关系、方向都明确
3. **可测量**：有明确的评估指标
4. **有理论依据**：基于文献或数学推导，不是凭空想象

假说陈述格式：
```markdown
### H1：[主假说]
**陈述**：在[条件]下，[自变量]相比[基线]在[因变量]上有[方向]改进。
**变量定义**：X=...，Y=...
**验证方法**：实验/分析/模拟
**预期结果**：具体数值（如"MSE 降低 ≥20%"）
**理论依据**：来自文献 [citation]
```

每个假说评估：
```markdown
| 假说 | 可证伪性 | 具体性 | 可测量性 | 理论依据 | 优先级 |
|------|---------|--------|---------|---------|-------|
```

## Input

- 研究问题（来自 `ope-rs-question-formulation` 的 `proposal/question.md`）
- 可选：用户已有的初步理论想法

## Output

按 `schemas/ope/specs/proposal.md` 模板产出，使用 Write 工具写入 `proposal/proposal.md`，结构：
- 理论框架（概念框架图 + 变量定义 + 关系假设）
- 可行性评估（四维度 + 综合结论）
- 可验证假说（假说列表 + 评估矩阵）
- 下一步行动

## Constraints

- 逻辑推导驱动：理论框架要有文献或数学支撑，不凭空构造
- 假说必须可证伪：无法被反驳的陈述要明确拒绝
- 可行性要诚实：不满足的条件明确指出，不迎合用户过度乐观
- 多个假说时标注哪个是核心、哪个是探索性
- 多轮讨论：用 AskUserQuestion 反复确认，直到双方共识
- 结果落盘到 `proposal/proposal.md`
