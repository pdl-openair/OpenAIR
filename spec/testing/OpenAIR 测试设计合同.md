# OpenAIR 测试设计合同

> 状态：已确认  
> 更新时间：2026-09-20  
> 职责：规定一项测试或科研评测何时成为正式测试资产，以及正式资产必须声明什么、取得什么证据、怎样形成测试结论。

---

## 1. 正式测试资产

正式测试资产承担长期、可重复的证明责任。

一项正式资产沿下面的关系建立：

```text
正式 Authority
→ 受保护结果（protected_outcome）
→ 失败类别（failure_class）
→ 最低测试主责（minimum_owner）
→ 当前资产的测试责任（test_responsibility）
→ 测试对象与运行条件
→ 所需证据 + 判定规则
→ 测试结论
```

测试文件名、目录、测试框架和运行命令不构成测试资产身份。

---

## 2. 正式依据与受保护结果

### 2.1 正式依据

正式测试资产的 `authority_refs` 指向定义其受保护结果或测试责任的正式依据，包括当前有效的正式设计，以及已经明确确认并需要长期保护的工程不变量。

当前实现、历史测试、日志、覆盖率和既有验收结果可以提供事实或证据，不能反向定义产品正确性或新的长期测试责任。

正式设计与当前实现不一致时，测试按照当前有效正式设计形成结论。

### 2.2 受保护结果

**受保护结果（protected_outcome）**是这项资产需要长期证明成立的产品结果、系统行为或科研能力。

长期断言面向正式可观察行为和稳定合同。内部函数调用次数、固定代码形状、临时字段或某条具体内部路径，只有在正式依据本身对其有长期约束时，才成为受保护结果。

---

## 3. 失败类别与测试责任

**`failure_class`**说明这项资产负责发现哪一类受保护责任没有成立。

**`minimum_owner`**说明这类失败最低由哪一种测试责任承担长期主责，由《OpenAIR 测试架构》确定。

**`test_responsibility`**说明当前这项正式资产具体证明什么。

因此：

```text
minimum_owner
= 这类失败最低归哪一种测试责任主责

test_responsibility
= 当前这项资产实际承担的证明责任
```

多个正式资产可以具有相同的 `minimum_owner`，但必须分别具有清楚、稳定的 `test_responsibility`。

---

## 4. 正式资产的合同载体

### 4.1 组件测试与 Verification

组件测试和 Verification 以 **Suite** 作为正式测试资产，`suite.yaml` 是其结构化合同入口。

至少包括：

| 字段 | 含义 |
| --- | --- |
| `suite_id` | Suite 的稳定唯一身份 |
| `protected_outcome` | 需要长期证明成立的产品结果或系统行为 |
| `authority_refs` | 支撑受保护结果和测试责任的正式依据 |
| `failure_class` | 本 Suite 负责发现的失败类别 |
| `minimum_owner` | 按测试架构确定的最低测试主责 |
| `production_targets` | 本 Suite 实际验证的 Production 责任或系统边界 |
| `test_responsibility` | 本 Suite 具体承担的证明责任 |
| `execution_profiles` | 允许使用的 Harness 运行配置 |
| `required_dependencies` | 取得有效证据所需的运行依赖；无依赖时为空 |
| `evidence_required` | 形成测试结论必须取得的证据 |
| `verdict_rule` | 证据与观察事实怎样映射为通过、失败或未形成有效证据；可以直接声明规则或引用稳定的版本化规则 |
| `triggers` | 哪些变化或场景要求重新运行该 Suite |

Suite 内的测试代码与 `suite.yaml` 共同组成该正式资产。测试代码实现已经声明的测试责任和判定规则，不能通过断言形成第二套产品规则或判定合同。

### 4.2 Eval

Eval 可以使用不同的版本化合同载体，但同样必须明确：

- 正式依据；
- 受保护的科研或能力质量；
- `failure_class` 或等价失败责任；
- `minimum_owner`；
- 评测责任；
- 评测对象；
- 判定标准；
- 运行条件；
- 所需证据；
- 触发条件；
- 版本身份。

---

## 5. 测试对象、材料与运行条件

正式软件测试直接验证受保护责任对应的 Production 代码或正式运行入口。

Fixture、Fake、Replay、Dataset 和 Live dependency 等属于测试材料或运行依赖。它们可以提供输入、受控依赖行为、历史场景、评测案例或真实外部条件，但不替代被测 Production 责任。

测试辅助代码可以准备条件、触发执行、采集证据并应用资产已经声明的 `verdict_rule`；它不能形成与 Production 并行的业务实现。

正式测试资产声明自己需要的运行配置和依赖。Harness 按这些声明提供运行条件并记录实际运行事实。

---

## 6. 证据与测试结论

测试结论必须由与受保护事实匹配的有效证据支持，并按资产已经声明的判定规则形成。

| 被测事实 | 主要证据或判定方式 |
| --- | --- |
| 明确规则、结构和状态 | 精确断言、Schema 校验、性质测试 |
| 真实执行、持久化和资源事实 | API、数据库、Artifact、运行记录、资源使用证据 |
| 跨组件或完整产品结果 | 本次真实执行形成的关键状态、产物和用户可见结果 |
| 科研、语义和开放性质量 | 版本化案例、明确评分标准、经校准的模型评分或人工复核 |

确定性事实优先使用确定性判定。科研语义和开放性质量使用与目标质量对应的正式评测标准，不能用方便取得的代理指标替代真正需要证明的质量。

一次执行形成三类正式结论：

| 结论 | 含义 |
| --- | --- |
| **通过** | 声明的运行条件成立，取得所需有效证据，并按既定判定规则证明受保护结果成立 |
| **失败** | 取得足够有效证据，并按既定判定规则证明受保护结果不成立 |
| **未形成有效证据** | 本次运行不足以按既定判定规则证明通过或失败 |

必要依赖不可用、正式运行条件未满足、trial 无效或关键证据未取得，均属于**未形成有效证据**，不能计为通过。

预期失败标记只记录已知缺口的管理状态；本次真实观察到的失败仍然是失败证据。

[经典注记] 本条 ≈ 已知失败治理（pytest xfail marker 与 flaky 测试经典实践）——差异：本合同的预期失败标记只登记缺口管理状态、不吞掉真实失败证据，且三态结论含“未形成有效证据”，比 xfail 的 strict/非 strict 二态多一层证据有效性判定。

通过结论只证明当前正式资产声明的受保护结果在本次有效运行条件下成立。更高范围的产品或科研结论，需要对应范围自己的正式测试资产和有效证据。

---

## 7. 测试资产生命周期

测试与评测资产按长期责任成熟度处于以下状态：

| 状态 | 含义 |
| --- | --- |
| **正式** | 正式依据、受保护结果、测试责任、测试对象、运行条件、所需证据和判定规则完整，承担长期验证责任 |
| **阶段性** | 服务当前诊断、迁移、验收或观察，尚未承担长期测试责任 |
| **待定（HOLD）** | 受保护目标具有长期价值，但正式依据、责任归属或有效证据条件尚未闭合 |
| **退役** | 不再承担长期验证责任；对应责任已经退出，或已有新的正式资产完整接管 |

长期存在、频繁运行或曾经发现真实问题，不会使阶段性或 HOLD 资产自动成为正式资产。

一次真实失败要沉淀为新的正式长期测试资产，必须进一步形成稳定的受保护结果、正式依据、`failure_class`、`minimum_owner`、具体测试责任、可重复取得的有效证据和明确判定规则。
