# OpenAIR 测试执行基座（Harness）设计

> 状态：已确认  
> 更新时间：2026-09-20  
> 职责：规定正式测试与评测怎样获得稳定、隔离、可追溯的运行条件，以及 Harness 必须保存哪些运行身份和原始证据。

---

## 1. Harness 运行模型

Harness 接收已经定义好的测试或评测资产及其运行要求，完成真实执行并保存运行事实：

```text
正式测试 / 评测资产
+ 运行配置
+ 测试材料与依赖
→ 准备隔离环境
→ 执行
→ 保存运行身份
→ 采集原始证据
→ 记录本次执行结果
```

Harness 提供运行条件和证据，不重新定义受保护结果、`minimum_owner` 或判定规则。

同一正式测试资产可以使用不同运行配置；运行配置变化不改变它的测试责任。

---

## 2. 运行配置

Harness 提供以下长期运行配置：

| 运行配置 | 主要用途 | 典型依赖 |
| --- | --- | --- |
| **确定性配置** | 明确规则和受控单组件行为 | 本地代码、受控 Fixture / Fake |
| **服务集成配置** | 事务、持久化、服务交接和 Worker 协作 | PostgreSQL、MinIO、Durable、服务进程 |
| **回放配置** | 固定历史输入、事故复现和下游消费行为 | Fixture、Replay、捕获结果 |
| **真实运行配置** | Provider、模型、runtime、恢复和资源实际使用 | Provider、模型、真实 Worker / runtime、正式资源 |
| **科研评测配置** | Agent、Skill 和科研能力质量评测 | 版本化 Dataset、模型、评分器、人工复核 |
| **完整产品链配置** | 从正式入口运行完整用户链 | 正式服务栈、全新研究项目和本次执行实例 |

正式测试或评测资产声明允许或要求的运行配置。Harness 按声明执行并记录本次实际使用的配置。

---

## 3. 测试材料与真实依赖

Harness 管理测试材料和运行依赖的身份、版本和实际用途。

| 材料 / 依赖 | 运行语义 |
| --- | --- |
| **Fixture** | 提供稳定、受控的测试输入 |
| **Fake** | 提供确定、可控的依赖行为 |
| **Replay** | 提供固定历史输入或已捕获结果 |
| **Dataset** | 提供版本化科研 / Agent 评测案例 |
| **Live input / dependency** | 提供当前真实外部输入、Provider、模型、服务或资源条件 |

Fixture、Fake、Replay 和 Dataset 都必须保留自己的身份或版本。

需要证明“当前真实 Provider、模型、外部系统或资源实际参与执行”时，必须使用对应的 Live dependency 并保存实际运行身份；Replay 或 Fake 只能证明其自身代表的受控运行条件。

[经典注记] 本条 ≈ 测试替身分类学（Meszaros《xUnit Test Patterns》dummy/fake/stub/spy/mock 谱系）——差异：本表按材料/依赖的运行语义分五类（Fixture/Fake/Replay/Dataset/Live）并要求身份与版本可追溯，不按“调用验证方式”（stub/mock 之别）分类。

---

## 4. 环境与隔离

每次 Harness 运行都有独立、可识别的资源范围。

按实际运行需要隔离：

- 临时工作目录和文件；
- 数据库 schema、事务或 namespace；
- 对象存储 bucket 或 object prefix；
- 网络端口和服务实例；
- 研究项目和本次运行身份；
- Provider 调用预算和并发范围。

共享资源必须具有明确的只读范围、稳定版本或独立 namespace。

可靠隔离的运行可以并行执行。同一测试在不同数据版本、运行配置或资源条件下执行时，每次运行保持独立身份，结果不得互相覆盖。

---

## 5. 运行身份与原始证据

每次执行都形成独立运行记录。凡是会改变本次证据含义或可比较性的条件，都必须能够追溯。

| 类别 | 需要能够追溯的内容 |
| --- | --- |
| **运行身份** | 运行标识、测试或评测资产身份、测试对象 |
| **代码与能力版本** | 源码或镜像、服务 / Worker / runtime、Provider、模型、推理配置、Skill、Prompt、Schema |
| **材料与资源** | Fixture、Replay、Dataset、关键依赖和正式资源身份 |
| **运行条件** | 实际运行配置、预算、并发、超时和恢复配置 |
| **输入与结果** | 本次实际输入、实际结果 |
| **证据与判定上下文** | 原始证据位置、实际应用的判定或评分规则版本、本次判定输出 |

原始证据可以包括 API 返回、数据库记录、Artifact、日志、运行轨迹、截图、资源使用记录和评测评分明细。

Harness 的证据链保持：

```text
测试 / 评测资产
→ 本次运行身份与条件
→ 实际输入
→ 实际执行
→ 实际结果
→ 原始证据
→ 本次判定输出
```

影响行为或判定含义的模型、Prompt、Schema、Skill、运行框架、关键输入、资源边界或判定规则发生实质变化时，新运行必须具有新的可比较身份，并建立新的可比较基线。旧结果继续按原运行条件解释，不与新条件下的结果混为同一基线。

哪些证据足以形成通过、失败或未形成有效证据，由对应正式测试或评测资产的判定规则决定。

---

## 6. 非确定性运行与 Eval Harness

真实模型、Agent 和外部 Provider 可以产生自然波动。

当正式测试或评测资产声明 trial 数、有效运行条件、评分方式或人工复核要求时，Harness 按这些规则执行，并为每个 trial 保存独立运行身份、实际结果和原始证据。

公共 Harness 提供环境准备、隔离、材料身份、运行身份、证据采集和执行记录。

**Eval Harness** 在这些公共能力上增加评测需要的版本化案例装载、重复 trial、评分执行、人工复核记录和基线比较能力。

科研能力的质量标准仍由对应 Eval 合同定义；Eval Harness 负责按既定规则执行并留下可追溯证据。
