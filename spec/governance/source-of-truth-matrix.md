# 真相源矩阵与冲突判定优先级（source-of-truth-matrix）

> 同一事实存在多份材料时，按本矩阵找唯一真相源；冲突按固定优先级裁决，不开会争论。

## 职责

定义每类信息的真相源、可否直接判事实，以及冲突判定优先级。

## 适用场景

两份文档/配置/平台说法打架；判断某文档是否权威；写新文档前决定"引用还是新写"。

## 真相源矩阵

| 信息类型 | 真相源 | 可否直接判事实 |
|---|---|---|
| 工程规则与方法论（编码/门禁/流程/安全/协作经验/测试先验） | `spec/`（含收编的 collaboration/ 与 testing/） | 是 |
| 门禁执行事实 | CI run 结果 + `scripts/gates/` 退出码 | 是 |
| 产品设计合同 | `docs/01_核心设计/`（最接近的设计合同优先，承 docs/README 既有 Authority 关系） | 是 |
| 任务规格/设计文档（新产出） | `docs/task_specs/`、`docs/dev_plans/` | 是 |
| skill 行为（开发侧） | `docs/dev_skills/` | 是 |
| 长程任务实时状态 | GitHub Issue + 飞书多维表格（双轨平台为实时源） | 是 |
| 实时协作状态 | GitHub（merged PR、分支）+ 飞书 | 是 |
| AI 入口导航 | AGENTS.md（+ CLAUDE.md 导入桥）、根 README.md | **否（永远不是规则源）** |

## 冲突判定优先级

`spec/`（工程规则意图）＞ `docs/01_核心设计/` 设计合同（产品行为）＞ 远端平台实时事实（是否合入/状态）＞ CI 运行结果（自动化验证事实）＞ 入口导航文档。

## spec 与工具配置的关系

- spec 定义**意图**；工具配置（ruff.toml、mypy.ini、eslint.config.ts、.pre-commit-config.yaml、.gitleaks.toml）是**投影**；**执行事实以工具运行为准**。
- 三者不一致 = bug：spec 说不清为何如此 → 修 spec；配置没跟上 spec → 修配置。都走 PR。
- enforcement-matrix 中"规则→正文锚点→配置项"的路径引用纳入指针完整性检查（防投影悄悄失联）。

## 防什么失效模式

- 第二真相源产生（spec 与 docs 与工具配置各自漂移）→ 单源结构 + 本矩阵 + 指针检查。
- "以最新聊天记录为准"的口头裁决 → 优先级固定，裁决可复现。
- 导航文档被当规则引用 → 矩阵显式声明导航"永远不是规则源"。

## 同步点

- 新增文档类型或权威迁移 → 本矩阵同 PR 更新，且相关入口（AGENTS.md、docs/README.md）指路同步。

## 不负责什么

- 具体规则正文 → 各域文件
- 历史材料的"待专项更新"定位（不作为当前正式依据）→ `docs/` 各 README
