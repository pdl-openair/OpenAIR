# OpenAIR 科研判断与结构化输出设计合同

> 状态：已确认  
> 更新时间：2026-10-10
> 职责：规定科研判断、LLM 可见输入、确定性代码与结构化输出之间的正式关系，以及 Formal Schema 与 Provider Schema 的合同关系。

---

## 1. 科研判断与确定性处理

OpenAIR 将**需要科研理解的判断**与**能够按明确规则唯一确定的处理**分开。

> **需要理解科研含义、比较证据、解释机制、处理冲突或判断不确定性的内容，由具备相应科研判断能力的 Agent / Skill 负责；能够根据已有正式事实和明确规则唯一确定的内容，由代码完成。**

Agent 或 Skill 使用 LLM 时，LLM 在该能力已经声明的科研判断职责、正式输入和模型输入范围内完成相应推理。**使用 LLM 本身不会产生科研判断资格或新的科研 Authority。**

典型分工如下：

| 科研判断 | 确定性代码 |
| --- | --- |
| 理解科研问题和语义 | 生成稳定 ID、固定字段和确定性系统字段 |
| 判断证据是否相关、适用或充分 | 按明确规则建立身份、来源和引用关系 |
| 比较、选择和取舍 | 执行公式、换算和其他唯一确定的计算 |
| 解释机制、因果关系和差异 | 完成确定性的字段投影和数据对应 |
| 判断风险、不确定性和适用边界 | 组装正式结果 |
| 形成科研结论 | 检查能够按明确规则直接判断的结构和业务条件 |

必须保持以下合同：

- 代码不能使用关键词、正则或其他机械规则替代需要科研理解的判断；
- 代码不能重新解释、改写、降级或替换已经形成的科研判断；
- 缺失的科研事实或执行事实不能通过默认值补造；
- 系统运行默认值只能用于不会改变科研事实、实际执行内容、资源身份、已确认成本或风险边界的运行参数；
- 结构处理可以改变技术表达，不能取得科研判断 Authority。

复杂机器结构本身不是要求模型生成某个字段的理由。只要字段能够由已有正式事实和明确规则唯一确定，就由代码形成。

## 2. LLM 可见输入

### 2.1 从正式执行输入形成模型输入

本次研究工作的正式执行输入由 WorkUnit 冻结。

LLM 实际可见的内容不是完整 WorkUnit，也不默认包含完整 ResearchDesign、ScientificState、Artifact、Evidence 或其他正式对象，而是从本次正式执行输入中形成的**最小充分投影**。

这个投影至少满足两个条件：

1. 包含完成当前科研判断所必需的信息；
2. 不因为“可能有用”而扩大模型可见范围。

模型可见内容通常包括：

- 当前需要完成的科研判断；
- 与该判断直接相关的正式事实和证据；
- 当前需要使用的已有科研判断；
- 适用边界、限制、冲突和不确定性；
- 当前判断必须遵守的硬约束；
- 输出需要绑定的必要稳定身份。

### 2.2 能力定义决定模型可见范围

使用 LLM 的 Agent 或 Skill，应在自身正式能力定义中明确：

- 当前能力需要哪些正式输入；
- 哪些内容需要提供给模型；
- 模型需要形成哪些科研判断。

运行时按这一正式声明，从 WorkUnit 已冻结的输入中进行确定性读取、投影和组装。原职责允许的内部工具调用可提供本次真实观察及错误反馈，作为后续推理上下文；必须保留工具、来源及时间，不回写冻结输入，也不绕过 Result 接受直接成为 ScientificState。改变本次正式要求、能力或冻结输入时，仍须形成新的正式快照。

代码不能通过隐藏筛选自行决定哪些科研内容“更相关”。存在来源冲突、多个合理解释，或者需要判断科研相关性时，应由具备相应科研判断能力的 Agent / Skill 处理。

### 2.3 已有科研判断的使用

当前正式执行输入中已经包含可直接使用的上游科研判断时，下游应直接使用其：

- 正式结论；
- 适用边界；
- 限制和不确定性；
- 必要证据关系。

只有当前科研判断明确需要重新检查原始依据时，相关原始资料或详细中间内容才重新进入模型输入。

因此：

```text
已有正式科研判断
≠
每个下游节点都重新从原始资料推导一次
```

### 2.4 模型执行说明

面向 LLM 的执行说明只保留模型完成当前科研判断必须理解的内容：

- 任务目标；
- 科研规则；
- 必须遵守的硬约束；
- 必要的输出语义。

运行协议、Schema 传输方式、稳定 ID 和固定字段生成、来源恢复以及其他确定性结构处理，由相应代码和基础设施完成，不重复要求模型处理。

## 3. Formal Schema 与 Provider Schema

Formal Schema 和 Provider Schema 服务于同一个正式结果，但承担不同职责。

| Schema | 正式含义 |
| --- | --- |
| **Formal Schema** | 规定最终正式结果必须满足的完整结构合同 |
| **Provider Schema** | 从 Formal Schema 和当前模型生成职责中形成，规定本次模型需要实际生成什么 |

### 3.1 Formal Schema

Formal Schema 可以规定：

- 正式字段和类型；
- 必填项和允许取值；
- 稳定 ID 和引用关系；
- 条件约束；
- 数量和范围约束；
- 其他正式结构要求。

Formal Schema 是正式结果的最终结构校验依据。

模型服务是否支持某种复杂 Schema 表达，不改变 Formal Schema 本身的要求。

### 3.2 Provider Schema

Provider Schema 是 **Formal Schema 面向本次模型生成职责的投影**，不是第二套业务合同。

它只保留：

- 必须由模型形成的科研判断；
- 模型正确表达这些判断所必需的结构。

能够由代码根据正式事实和明确规则唯一确定的内容，不要求模型生成，例如：

- 稳定 ID；
- 固定系统字段；
- 已知来源和引用关系；
- 确定性计算结果；
- 可以从正式输入恢复的身份信息；
- 最终结构组装字段。

Provider Schema 必须满足：

- Formal Schema 中需要模型判断的内容，在 Provider Schema 中有明确承载；
- Provider Schema 中每项模型输出，都能明确映射回正式结果中的语义或正式结果形成所必需的科研判断；
- 结构可以为了模型生成需要进行组织，但不能新增与 Formal Schema 无关的独立业务语义；
- 模型输出能够通过明确规则进入后续正式结果组装。

只有 Formal Schema 足够简单，而且其中全部字段都确实需要模型判断时，Formal Schema 才可以直接作为 Provider Schema。

**Provider Schema 也不等同于某个模型服务原生接受的 Schema 格式。** 发送给具体模型服务前，可以由公共 Schema 基础设施转换为该服务支持的技术表达；这种转换只能改变表达方式，不能改变 Provider Schema 的语义和约束。

## 4. 正式结果形成

结构化科研结果按照以下主链形成：

```text
WorkUnit 中的正式执行输入
→ 按能力定义形成 LLM 最小充分输入
→ LLM 按 Provider Schema 形成科研判断
→ 代码恢复确定性字段、身份和来源关系
→ 组装正式结果
→ 按 Formal Schema 校验
→ 形成结构合法的正式结果
```

代码组装只能补充能够根据已有正式事实和明确规则唯一确定的内容。

代码不能：

- 改变模型已经形成的科研含义；
- 把缺失的科研判断补写成确定结论；
- 为通过校验而降低 Formal Schema 要求；
- 把 Provider Schema 中不存在或未形成的科研判断静默补齐。

按 Formal Schema 校验通过，只说明该结果满足正式结构合同。

```text
结构合法
≠
科研内容已经被当前项目接受
```

科研内容是否被接受并进入 ScientificState，继续按照研究执行机制中的结果接受规则处理。

## 5. 缺失、不确定性与结构失败

### 5.1 缺失事实

缺少正式科研事实时，应保持缺失。

如果某项内容能够根据已有正式事实按唯一明确规则得到，可以由代码确定性形成；存在多个合理解释时，属于科研判断，不能由代码选择一个值补齐。

### 5.2 科研不确定性

证据不足、条件未知、结论暂时无法确定、存在冲突或具有合理不确定性，属于科研内容本身，不属于结构错误。

Formal Schema 已定义相应表达方式时，应如实保留这些状态，不能为了得到确定值而改写科研含义。

```text
科研结论不确定
≠
结构化输出失败
```

### 5.3 结构失败

模型输出缺失、结构错误，或者最终结果无法满足 Formal Schema 时，该内容不能作为合法机器输入进入消费该结构的动作。原始输出与失败事实仍须保存，可读正文、独立有效条目及限制继续展示，不因机器结构失败丢掉整份成果。坏项不能取得合法正式结果或已验证 Evidence 的地位。

可读科研交付不普遍要求复杂机器 Schema；必要结构仅由真实消费者及正式合同决定。机器消费字段仍按该版本 Formal Schema 检验，合法字段不等于语义正确。简化 Schema 应修改其正式合同并保留版本，不能在运行中静默降低要求。最终交付的最小必要结构及身份仍保留。

结构、参数或内容问题交回有工具的原职责 Agent 处理，失败位置、原始内容及缺失事实同时提供。代码只处理唯一确定的转换，模型处理科研理解，二者均不补造来源或实际执行。检查仅限制相关动作或结论，不形成科研成功才能继续的普遍门禁。

基础设施的确定性结构恢复或补充只允许处理能够按明确规则唯一确定的内容，并且必须同时满足：

- 不改变已经形成的科研含义；
- 不补造缺失科研事实；
- 不降低 Formal Schema 的正式要求。

Provider Schema 的技术适配、Schema 解析和最终结构校验由公共 Schema 基础设施执行，但这些处理不能改变本文规定的科研语义或 Formal Schema / Provider Schema 合同。

Agent依据真实工具观察重新形成判断或修正输出属于原职责执行，保留前后结果及来源；不能伪装成基础设施的确定性补齐，也不能覆盖旧Result。

结构处理最终只需要形成真实结果：**结构合法的正式结果，或结构失败事实**。发生结构失败后，本次研究工作是否恢复、重试、继续其他结果或等待用户，由研究执行机制根据当前正式状态决定。
