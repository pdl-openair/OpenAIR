# OpenAIR 术语表

> 状态：已确认  
> 更新时间：2026-09-20  
> 职责：统一 OpenAIR 核心设计文档中反复使用的正式术语。

---

## 1. 研究项目与研究方案

| 正式术语 | 含义 |
| --- | --- |
| **研究项目（Project）** | 用户发起的一项完整研究及其正式身份。 |
| **研究项目生命周期** | 一个研究项目从建立到最终完成所经历的正式阶段和阶段转换。 |
| **研究流程（Workflow）** | 针对某类研究可重复使用的研究工作结构，规定通常需要哪些研究工作以及它们之间的关系。 |
| **研究方案草案** | 用户确认前形成的研究方案候选；尚不是正式 ResearchDesign。 |
| **研究方案（ResearchDesign）** | 用户确认后的当前正式研究方案，规定研究目标、项目研究任务、研究工作要求、项目完成要求和需要遵守的正式边界。 |
| **研究工作类型（Substage）** | 一类可以在不同研究项目或 Workflow 中重复使用的研究工作。 |
| **研究工作要求（Definition）** | 某类研究工作必须满足的需求侧合同，包括所需输入、输出、质量和合格要求。 |
| **项目研究任务（SubstageInstance）** | 某类研究工作进入当前研究项目后形成的具体任务身份。 |
| **项目完成要求** | 当前研究项目满足什么条件时可以结束的正式要求。 |

## 2. 研究执行与科研状态

| 正式术语 | 含义 |
| --- | --- |
| **科研状态（ScientificState）** | 当前项目已经接受的科研认识，包括结论、假说、冲突、研究缺口、不确定性、证据关系和研究目标的当前完成情况。 |
| **执行决定（ExecutionDecision）** | 根据当前有效 ResearchDesign、相关 SubstageInstance 和最新 ScientificState 形成的下一步研究决定。 |
| **正式执行输入** | 一次研究执行合法使用的正式事实及能够按明确规则唯一得到的确定性结果。 |
| **执行工单（WorkUnit）** | 一次具体执行的正式输入快照，冻结本次研究工作、执行能力、正式输入及来源引用、工作要求和执行边界。 |
| **完成判断（CompletionDecision）** | 根据当前项目完成要求和最新 ScientificState，在确认项目已经满足结束条件时形成的正式判断。 |

---

## 3. Agent、Skill 与执行能力

| 正式术语 | 含义 |
| --- | --- |
| **Agent** | 适合结合研究上下文进行理解、判断、推理或组织执行的研究能力。 |
| **Skill** | 边界明确、可以重复使用的研究能力，可以直接执行研究工作，也可以作为 Agent 的内部执行组成。 |
| **Agent 能力说明（AgentDefinition）** | 描述一个具体 Agent 实际支持的研究工作、输入输出、专业范围、科研判断能力和运行条件。 |
| **Skill 能力说明（SkillDefinition）** | 描述一个具体 Skill 实际支持的研究工作、输入输出、专业范围、科研判断能力和运行条件。 |
| **专业范围** | 一个能力适用于哪些领域、研究对象或问题。 |
| **科研判断能力** | 一个能力在相应范围内能够承担哪些需要科研理解、比较、解释、取舍或形成结论的判断。 |
| **能力注册表（Registry）** | 登记系统当前正式可用的 Agent 和 Skill，并提供能力选择所需的正式能力事实和可用状态。 |
| **能力绑定（Binding）** | 在能力已经选定后，把已有正式事实或确定性结果映射到该能力输入的配置关系。 |
| **执行方法** | 多个正式能力角色需要稳定协同时使用的版本化方法，规定角色及其依赖、顺序、分支和控制关系，不固定具体 Agent、Skill 或模型。 |

## 4. 研究内容与结果

| 正式术语 | 含义 |
| --- | --- |
| **执行结果（Result）** | 一次具体执行实际产生的正式内容。 |
| **研究产物（Artifact）** | 研究过程中已经保存、可供查看、追溯或继续使用的具体产物。 |
| **证据（Evidence）** | 能够支持、反驳或限制某个科研判断的具体依据，并保留其来源、适用条件和不确定性。 |
| **最终结果（Final Result）** | 整个研究项目最终交付给用户的正式结果。 |

## 5. 结构化输出

| 正式术语 | 含义 |
| --- | --- |
| **Formal Schema** | 最终正式结果必须满足的完整结构合同，也是最终结构校验依据。 |
| **Provider Schema** | Formal Schema 面向本次模型生成职责的投影，规定本次模型需要实际生成的结构；它不是某个模型服务原生接受的技术 Schema。 |
| **模型服务技术 Schema 表达** | Provider Schema 转换为具体模型服务能够接受的技术表达；转换可以改变写法，不能改变 Provider Schema 的正式语义和约束。 |

## 6. 测试体系

| 正式术语 | 含义 |
| --- | --- |
| **正式测试资产** | 承担长期、可重复证明责任，并具有正式依据、受保护结果、测试责任、运行条件、证据和判定规则的测试或评测资产。 |
| **受保护结果（protected_outcome）** | 一项正式测试资产需要长期证明成立的产品结果、系统行为或科研能力。 |
| **失败类别（failure_class）** | 一项测试资产负责发现的受保护责任失败类型。 |
| **最低测试主责（minimum_owner）** | 某类 failure class 最低由哪一种测试责任承担长期主责。 |
| **测试责任（test_responsibility）** | 当前这项正式测试资产具体承担的证明责任。 |
| **Suite** | 组件测试或 Verification 的正式测试资产单元，由 `suite.yaml` 和对应测试代码共同组成。 |
| **判定规则（verdict_rule）** | 规定证据和观察事实怎样映射为通过、失败或未形成有效证据的正式规则。 |
| **测试执行基座（Harness）** | 按正式测试或评测资产声明的运行要求准备环境、执行测试并保存运行身份和原始证据的公共基座。 |
| **未形成有效证据** | 本次运行不足以按既定判定规则证明通过或失败的正式测试结论。 |

## 7. 关键区别

| 容易混淆的对象或事实 | 正式区别 |
| --- | --- |
| **ResearchDesign / ScientificState** | ResearchDesign 规定已经确认要研究什么和遵守什么边界；ScientificState 保存研究推进到当前时点已经被项目接受的科研认识。 |
| **SubstageInstance / ExecutionDecision / WorkUnit** | SubstageInstance 是项目研究任务身份；ExecutionDecision 决定当前下一步做什么；WorkUnit 冻结一次具体执行怎么做。 |
| **Result / Artifact / Evidence / ScientificState** | Result 是一次执行产生的内容；Artifact 是已保存的具体产物；Evidence 是支持、反驳或限制科研判断的依据；ScientificState 是当前项目已经接受的科研认识。 |
| **Result 已产生 / 内容已被接受 / ScientificState 已更新** | 三者是不同事实；执行已经发生，不等于其科研内容已经被项目接受，也不等于状态已经更新。 |
| **专业范围 / 科研判断能力** | 专业范围相符，不自动代表具备相应科研判断资格。 |
| **计划使用资源 / 程序实际使用资源** | WorkUnit 中冻结的计划资源不能单独证明程序实际使用了同一资源；实际使用关系需要根据真实运行身份事实核验。 |
| **Formal Schema / Provider Schema / 模型服务技术 Schema 表达** | Formal Schema 是最终正式结构合同；Provider Schema 是其面向当前模型生成职责的投影；模型服务技术 Schema 只是 Provider Schema 的服务适配表达。 |
| **minimum_owner / 测试代码目录 / Harness 运行配置** | minimum_owner 表示最低测试主责；代码目录表示测试代码归属；Harness 运行配置表示取得证据时使用的运行条件，三者不是同一维度。 |
