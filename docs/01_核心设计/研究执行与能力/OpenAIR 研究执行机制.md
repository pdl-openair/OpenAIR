# OpenAIR 研究执行机制

> 状态：已确认  
> 更新时间：2026-10-10
> 职责：规定 ResearchDesign 确认后，OpenAIR 如何决定下一步研究工作、冻结并执行一次具体工作、接受执行结果中的科研内容并更新 ScientificState，直到判断项目可以结束。

---

## 1. 研究执行主循环

ResearchDesign 确认后，研究围绕当前正式方案和最新科研状态循环推进：

```text
当前有效 ResearchDesign
+ 相关 SubstageInstance
+ 最新 ScientificState
        ↓
ExecutionDecision
决定下一步做什么
        ↓
WorkUnit
冻结这一次具体怎么做
        ↓
执行研究工作
        ↓
Result
记录这一次实际产生了什么
        ↓
判断 Result 中哪些科研内容可以被项目接受
        ↓
将已接受内容更新到 ScientificState
        ↓
判断项目是否还需要继续研究
        ├─ 需要继续 → 下一轮 ExecutionDecision
        └─ 可以结束 → CompletionDecision → Final Result
```

这条主线中的几个对象分别回答不同问题：

| 对象 | 回答的问题 |
| --- | --- |
| **ExecutionDecision** | 现在下一步做什么研究工作？ |
| **WorkUnit** | 这一次具体由谁、使用什么正式输入、按什么边界执行？ |
| **Result** | 这一次执行实际产生了什么？ |
| **ScientificState** | 当前项目已经接受了哪些科研事实、判断和不确定性？ |
| **CompletionDecision** | 为什么当前项目已经可以结束？ |

运行和恢复不能绕过这些正式对象直接改变研究方向或 ScientificState。

### 1.1 Task / Substage 正式状态收敛

Task 和 SubstageInstance 的正式状态由研究执行生命周期中的**唯一确定性状态收敛机制**形成。本节是这两类正式状态如何形成的唯一 Authority：

```text
生命周期事实变化
→ 唯一确定性状态收敛机制
→ canonical Task / SubstageInstance 状态
→ 页面、进度和运行视图只读消费
```

WorkUnit、Result、停止请求、Provider 回调、恢复记录和其他组件都可以产生真实生命周期事实，并触发同一状态收敛机制；它们不能分别计算或直接覆盖同一 Task 或 SubstageInstance 的正式状态。该机制按对象各自粒度和同一组确定性规则收敛全部相关事实，只有其输出能够写入 canonical Task / SubstageInstance 状态。

页面、进度投影、运行视图和其他只读投影只能消费 canonical 状态。它们不得根据回执、活动记录、局部执行对象、缓存、前端等待时间或自行维护的规则另行覆盖、回写或发布第二套正式状态。WorkUnit、ExecutionDecision 和 Provider 调用继续保留各自粒度的运行事实；这些事实与 Task / SubstageInstance 状态不同，不构成并列的状态 Authority。

## 2. 形成 ExecutionDecision

每一轮研究都根据当前有效的 ResearchDesign、相关 SubstageInstance 和最新 ScientificState，形成新的 **ExecutionDecision**。

ExecutionDecision 只回答一个问题：

> **当前下一步执行哪项研究工作？**

它决定研究工作，不提前固定具体 Agent、Skill、模型或其他底层实现。

同一个 SubstageInstance 可以根据研究需要执行多次。每次新的执行都形成新的 ExecutionDecision 和 WorkUnit，但不会因此创建新的项目研究任务。

职责型 Workflow 可以为某项稳定研究职责声明**支撑工作**。支撑工作不是固定 Workflow 职责节点；只有当对应职责在当前项目形成正式研究任务时，系统才按冻结的 Workflow 结构确定性地把所需支撑 Definition 加入 ResearchDesign。进入 ResearchDesign 后，它与其他项目研究任务一样形成正式 SubstageInstance、ExecutionDecision 和 WorkUnit，不能由 Binding 或运行时临时补造。

一项研究工作内部可以包含检索、整理、转换等多个技术步骤。只要这些步骤仍然服务于当前研究工作，而且中间结果还不需要改变后续研究方向，就可以在同一次执行中继续完成。

如果中间结果已经足以影响后续研究方向，就必须先完成：

```text
形成 Result
→ 判断哪些科研内容可以被接受
→ 更新 ScientificState
→ 再形成新的 ExecutionDecision
```

执行过程中的中间信息不能直接写入 ScientificState。已经在 ResearchDesign 中作为独立研究任务存在的工作，也不能因为某次执行顺带涉及，就被视为已经正式完成。

## 3. 准备并冻结 WorkUnit

ExecutionDecision 已经确定下一项研究工作后，系统准备这一次具体执行，并在正式执行前形成 **WorkUnit**。

准备过程完成三件事：

1. 按当前 Definition 和正式能力体系选择合格的执行能力；
2. 准备这次研究工作真正需要的正式输入；
3. 冻结本次实际使用的执行能力、输入、工作要求和执行边界。

### 3.1 正式执行输入

本次执行输入只能来自已经存在的正式事实，或能够按明确规则唯一得到的确定性结果，例如：

- 当前 ResearchDesign 和相关 SubstageInstance；
- 最新 ScientificState；
- 当前工作需要使用的 Result、Artifact、Evidence；
- 当前 Definition 和已经确认的执行边界；
- 其他由正式设计明确允许的输入。

凡是会影响科研结果、资源身份、实际执行内容、复现含义，或者已确认成本和风险边界的输入，都必须有可追溯来源。

来源唯一、规则明确的读取、换算、字段投影、身份对应和结构组装，由代码完成。

如果存在多个合理解释、来源之间有冲突，或者需要科研理解才能决定，应交给具备相应科研判断能力的能力处理。

有些纯运行细节必须在执行时确定，但不会改变科研含义，也没有被正式设计预先指定。这类细节可以由系统选择，但必须保留本次实际选择，保证后续能够追溯。

如果某个必要输入没有合法来源，也无法按明确规则得到，本次执行条件不足。系统不能通过猜测、语义默认值或临时兼容值补造正式事实。

Binding 只在能力已经选定后，把已有正式事实或确定性结果映射成该能力需要的输入。它不参与能力选择，也不能通过绑定创造新的科研事实或执行事实。

### 3.2 WorkUnit

WorkUnit 至少冻结：

- 对应的研究工作；
- 执行方法版本（存在时）；
- 本次实际选择的执行能力；
- 正式执行输入及必要来源引用；
- 当前工作要求；
- 执行边界。

WorkUnit 是**本次执行的正式输入快照**。

它用于真实执行、恢复和追溯，但不会成为其中输入事实新的 Authority，也不会修改 ResearchDesign 或 ScientificState。

WorkUnit 一旦冻结，其正式内容保持不变。恢复或重试可以继续使用同一 WorkUnit；需要改变执行能力、正式输入、工作要求或其他已经冻结的内容时，必须基于当前正式状态重新形成 ExecutionDecision 和新的 WorkUnit。

需要由真实程序读取的正式资源，在 WorkUnit 中记录本次**计划使用**的资源身份及必要来源关系；程序最终**实际使用**了什么资源，根据真实运行事实另行核验。

### 3.4 WorkUnit 进入执行

WorkUnit 冻结且执行条件满足后，立即进入公共耐久调度。耐久队列只承担保存、领取和恢复责任，不把彼此没有正式依赖的 WorkUnit 串行化。

不同项目、不同用户以及同一用户的多个独立 WorkUnit 可以并发执行。正式依赖尚未满足、必要资源不可用或已确认边界限制并发时，只约束受影响的 WorkUnit，不占用执行槽阻塞其他工作。

并发领取、执行隔离、容量扩展、故障恢复和 Provider 幂等遵循《OpenAIR 模型调用运行与故障恢复设计合同》。

---

## 4. 执行研究工作并形成 Result

WorkUnit 形成后，系统按照其中已经冻结的要求执行研究工作。

执行过程中必须保持：

- 当前 Definition；
- 已绑定的正式执行方法（存在时）；
- WorkUnit 中的正式输入；
- 已确认的执行边界。

执行过程不能自行扩大研究目标、改变正式执行方法，或者创建新的项目研究任务。

一次具体执行实际产生的正式内容形成 **Result**。

Result 回答的是：

> **这一次执行实际上产生了什么？**

只要一次执行已经真实发生并形成了 Result，这就是已经发生的执行事实。后续检查、Reviewer、恢复或调度可以决定其中哪些内容能够被项目接受，但不能把已经发生的执行改写成“没有发生”。

### 4.1 Result 形成与执行结算

Result 已经耐久保存，表示本次执行实际产生的内容已经被记录。本次执行随即完成结算；后续科研接受、ScientificState 更新、依赖释放或下一轮研究决定不能成为本次执行保持未结算状态的条件。

后续处理暂时失败时，系统恢复尚未完成的后续责任，不重新执行已经成功的 WorkUnit，也不重复已经完成的 Provider 调用。

---

## 5. 接受 Result 并更新 ScientificState

Result 形成后，系统判断其中哪些科研内容可以被当前项目接受。

这里必须保持三个层次：

| 层次 | 含义 |
| --- | --- |
| **Result 已产生** | 某次执行已经真实发生，并产生了结果 |
| **内容已被接受** | Result 中某些科研内容已经通过相应检查，可以进入当前项目正式状态 |
| **ScientificState 已更新** | 已接受内容已经写入当前项目最新科研状态 |

能够按明确规则唯一判断的结构、来源、身份和固定约束，使用确定性检查。

确实需要科研理解才能判断是否接受的内容，由具备相应科研判断能力的能力处理。

只有已经通过相应检查并被当前项目接受的科研内容，才能更新 ScientificState。

不同内容可以分别处理：

- 不被接受的内容不进入 ScientificState；
- 被接受的内容进入 ScientificState；
- 证据不足、合理冲突和科研不确定性，只要它们本身是真实科研状态，也可以被正式保留。

### 5.1 外部来源身份的确定性接受

当 Result 含有 Skill 正式输出合同声明的外部来源记录时，来源真实性检查发生在 Result 已经形成并耐久保存之后、相关内容被接受为 Artifact / Evidence 或进入 ScientificState 之前。

```text
Skill 产生实际输出
→ Result 原样耐久保存
→ 读取本次执行冻结的 SkillDefinition / 正式输出合同
→ 按 external source record 声明定位记录和身份字段
→ 按 identity_type 确定性检查
→ 各记录分别形成 accepted / rejected 接受事实
→ 只有通过相应检查的内容可以形成已验证来源的 Artifact / Evidence
```

公共 validator 的职责仅是执行这份正式声明：

- 只读取声明中的 `record_path`、`field_path` 和 `identity_type`，并按对应身份类型执行确定性检查；
- 不根据 `source`、`doi`、`url` 等字段名或任何内置字段名清单猜测来源身份；
- 不扫描摘要、标题、正文、分析、说明或其他自由文本来推断来源身份，因此普通文字中的 `Unknown source` 或类似内容本身不是来源身份失败；
- 不补齐、替换、修复或伪造来源身份，也不把 Registry、Binding、示例或历史输出当成声明 Authority；
- 不在检查前过滤或改写 Result，也不以检查后的子集替代原始 Result。

如果本次冻结的正式输出合同没有相应声明，validator 不执行来源身份猜测，也不把看起来像来源的内容标记为“已验证来源身份”。实际 Result 继续原样保存；相关内容不能仅凭字段名、格式或正文出现来源信息而作为已验证来源进入 Evidence。需要这些内容取得来源身份语义时，应修正产生它的 SkillDefinition / 正式输出合同，并在后续执行中使用新版本，不能由 validator 临时增加规则。

接受粒度以声明的 `record_path` 为边界。多记录 Result 中某条记录的来源身份非法时，只拒绝该记录进入需要真实来源的 Artifact / Evidence，并保留拒绝原因、对应记录位置和所依据的合同版本用于追溯；同一 Result 中其他通过检查的记录可以继续被接受。原始 Result 始终保留全部实际输出。只有当前 Definition 或正式职责明确要求这些记录必须整体成立时，单条失败才可以阻塞该职责整体接受；这种整体要求不能由 validator 自行推导。

来源身份通过确定性检查，只证明声明字段所表达的来源身份符合对应规则，不自动证明内容真实、科研判断成立或研究职责完成。后续仍按既有 Artifact、Evidence、科研判断和职责完成规则处理。拒绝事实属于本次接受处理的追溯记录，不创建第二套 Result、Artifact 或 Evidence Authority。

### 5.2 检查限制动作，不设科研内容的普遍门禁

科研内容失败、未知、不完整或未达预期，不构成整个研究停止的条件。检查须明确真实消费者及其必要事实：结构非法只限制消费该结构的动作；未验证来源不能支持已验证来源的结论；权限、资源身份、环境或运行入口不足只限制确实依赖它们的真实动作。其他合法研究、纠错、补证和可读内容交付继续进行。

不能补造未知事实，也不能删除真实动作依赖以宣称执行发生。失败记录与已取得内容分别保留；检查不取得新的科研判断 Authority。

错误反馈交回承担原职责的合格 Agent，同时提供合法工具、原始证据、具体失败位置和剩余预算。原职责内取得输入、核对参数及准备环境是正常内部工作，不默认要求新项目任务、历史实例重入或重新确认方案。改变冻结输入时按§3.2形成新 ExecutionDecision / WorkUnit，不改写旧执行及其结果。

### 5.3 部分结果与职责完成

Result 或 Artifact 通过结构检查，只说明其结构合法。Artifact 可以被保存、查看或用于合同允许的局部工作，但这不自动证明对应研究职责已经完成。

当正式结果表达 `partial`、`incomplete`、证据不足、仍有必要 unknown，或其他未满足必要验收条件的状态时：

- 已取得内容继续保留；
- 已经独立接受的科研内容可以进入 ScientificState；
- 未完成的研究职责保持未完成；
- 下游按其真正消费的事实、结论或动作条件判断依赖；不得仅凭 Artifact 类型存在释放真实动作，也不得仅凭上游职责未完成禁止所有下游。方案明确要求整体完成的正式依赖仍保留，改变该依赖须方案变更；纠错、补证和诚实交付不伪称依赖已满足。

Definition 要求专业判断时，完成判定必须取得对应的正式判断。缺少 evaluator 或专业判断能力时，保留未完成事实，不能静默降级为 Schema 通过、字段存在或 Artifact 类型存在；继续其他合法工作或交付无法取得该判断的原因，不无限保持待判断。

### 5.4 `readiness = not_ready`

当执行准备核验形成 `readiness = not_ready` 时，它表示基于当前科研认识，真实执行所需条件尚未满足。该结论以及对应的 `blocking gaps`、`unknowns` 是正式研究状态：通过结果接受后如实保留，并更新到当前 ScientificState，不能改写成一次真实执行能力选择失败。

```text
readiness = not_ready
→ 保存 blocking gaps / unknowns
→ 更新当前 ScientificState
→ 下一次 ExecutionDecision 根据缺口决定补证或继续研究
```

下一次 ExecutionDecision 可以在当前 ResearchDesign 边界内选择取得缺失证据、核对代码 / 资源 / 环境事实、处理可消除的 unknown，或继续其他仍可开展的研究工作；只有缺口确实属于用户掌握且系统无法自行取得的必要信息时，才请求用户补充。

`readiness = not_ready` 时，仅对条件不足的实际实验、训练或测量动作停止能力选择、角色解析、Registry 匹配或 Binding。取得资源、核验代码、准备环境和修正输入按自身必要条件继续，不要求先满足实际实验 readiness。Binding 不能把 readiness 缺口补造成正式输入，也不能把 `not_ready` 间接转换成 capability failure。为补证或继续其他研究而由新的 ExecutionDecision 确定的研究工作，可以按其自身 Definition 正常选择能力。

以下三类事实必须保持区分：

| 事实 | 含义 |
| --- | --- |
| **`readiness = not_ready`** | 当前科研认识表明真实执行条件尚未满足，并保留具体 `blocking gaps` / `unknowns` |
| **当前没有合格能力** | 对已经确定的研究工作，没有能力满足其 Definition 和资格要求 |
| **capability unavailable** | 已有合格能力，但本次运行环境、资源、预算或其他可用条件不足 |

`not_ready` 不证明能力不存在，也不证明已有合格能力当前不可用；反过来，能力资格或可用性事实也不能覆盖 readiness 的科研结论和缺口。

## 6. 判断继续研究还是结束

ScientificState 更新后，系统重新判断当前项目是否还需要继续研究。

仍有研究工作需要完成时，形成下一轮 ExecutionDecision，并继续进入新的 WorkUnit 和执行循环。

当前项目已经满足正式结束条件时，形成 CompletionDecision，并进入 Final Result。

ResearchDesign 确认后，系统可以根据最新 ScientificState 调整当前方案边界内的执行安排，例如执行顺序、执行次数、合格执行能力，以及当前执行的恢复或重试。

这些调整不能改变 ResearchDesign、Definition 或已经绑定的正式执行方法。

如果需要改变已经确认的研究目标、项目研究任务、研究工作要求、项目完成要求或其他正式方案边界，必须进入 ResearchDesign 变更流程。

### 6.0 后续责任与有界出口

每次执行结算后，既有耐久调度必须持有可追溯的后续责任：继续已确认工作、恢复原职责内可修复问题、形成诚实交付，或等待用户能回答的必要问题。源 ExecutionDecision 关闭、没有 READY 实例、没有历史重入授权本身均不能证明研究已结束。不得重复执行已成功工作来制造后续责任，也不得强制 READY 或暗建研究任务。

纠错先在当前职责的内部工具回路进行；已结束来源只作为证据，不被重新打开。后续已确认职责可在其自身范围内取得、核验和修正所需输入，以新 Result 保留新增事实，按正式接受更新状态。系统依据既有顺序、依赖、正式输入和注册能力派发，不让模型重新规划或审批任务。无专用 Skill 的纯研究职责由满足同一 Definition 的通用 Agent 承担。

恢复消费已确认预算及既有恢复机制，不另建重试策略；同一错误且事实、输入和可用能力均无变化时，不再次启动相同动作。预算穷尽、能力实现缺失或原目标不可达时，责任进入诚实交付，明确区分无法取得结果与系统未实现应有恢复能力。不得把内部故障伪装成必须由用户回答的问题。进程中断按既有运行恢复合同核对真实结果；外部结果未知不得盲目重复动作。

CompletionDecision 与 Final Result 记录本轮结束依据、原目标达成情况、有效成果、失败证据和未完成事项。本轮结束不自动证明原目标达成；唯一 canonical 状态机制继续负责收敛，具体终态不能由前端或 continuation 自行推导。

### 6.1 停止与项目终态

用户停止当前研究任务并成功提交后，canonical Task 进入 `cancelled`，系统停止形成新的 ExecutionDecision 和依赖工作。停止回执只保存原因和审计事实。

停止前已经发生的 WorkUnit、Provider 调用、Result 和 Artifact 保持其真实状态。在途执行无法可靠取消时，系统继续记录其运行和终态事实；晚到结果可以保存，但不能重新打开已经取消的 Task，也不能继续释放新的研究工作。

Task 的 `completed`、`failed` 和 `cancelled` 由同一生命周期收敛规则形成。页面和其他只读投影只能读取这一正式状态，不能根据回执、活动记录或局部执行对象另行生成第二套任务状态。
