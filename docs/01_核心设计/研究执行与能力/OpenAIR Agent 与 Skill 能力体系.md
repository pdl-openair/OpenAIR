# OpenAIR Agent 与 Skill 能力体系

> 状态：已确认  
> 更新时间：2026-10-10
> 职责：规定 OpenAIR 如何定义、登记和选择研究能力，以及需要多个正式能力角色协同时如何使用版本化执行方法。

---

## 1. 能力体系的核心关系

能力体系把**研究工作要求**和**具体执行能力**分开管理：

```text
已经确定的研究工作
→ Definition：这项工作必须满足什么要求
→ 执行方法：需要哪些正式能力角色以及怎样协同（如需要）
→ AgentDefinition / SkillDefinition：具体能力能够提供什么
→ Registry：当前有哪些正式可用能力
→ 能力选择：本次由哪个合格能力执行
→ WorkUnit 冻结本次实际选择
```

核心关系是：

> **Definition 是需求侧合同；AgentDefinition / SkillDefinition 是供给侧能力事实。**

能力选择判断当前供给是否满足当前需求。具体执行能力可以变化，但不能因此降低 Definition 或改变已经确定的研究工作。

| 对象 | 本文中的正式职责 |
| --- | --- |
| **Definition** | 给出当前研究工作必须满足的输入、输出、质量和合格要求 |
| **AgentDefinition / SkillDefinition** | 声明一个具体能力实际支持的范围、条件和质量能力 |
| **执行方法** | 定义多个正式能力角色及其稳定协同关系 |
| **Registry** | 登记当前正式可用的 Agent 和 Skill |
| **能力选择** | 为已经确定的研究工作或正式能力角色选择本次实际执行能力 |

---

## 2. 能力定义与 Agent / Skill

具体 Agent 和 Skill 分别通过 **AgentDefinition** 和 **SkillDefinition** 描述自己的正式能力。本文统称二者为**能力定义**。

能力定义至少应明确：

- 能够完成哪些研究工作；
- 可以接收什么输入；
- 可以产生什么输出；
- 适用于哪些专业范围；
- 能够承担哪些科研判断；
- 需要哪些运行条件；
- 有哪些正式质量要求。

能力定义描述的是具体能力真实能够提供什么，不能因为其声明范围更宽而反向修改当前 Definition。

### 2.1 Agent

**Agent**适合承担需要结合研究上下文进行理解、判断、推理或组织执行的研究工作。

Agent 可以直接成为当前研究工作的执行能力，也可以在自身能力定义允许的范围内调用一个或多个 Skill 完成内部步骤。Agent 被直接选中时，仍由该 Agent 对本次执行是否满足 Definition 负责。

### 2.1.1 原职责内纠错与取得输入

承担研究职责的 Agent 必须有实际可用且经授权的工具及输入取得路径，才能修正参数、核验代码、检索证据、获取资源或准备环境。能力定义应说明允许使用的工具、输入来源、工作目录、权限与预算边界。只有错误消息或工具名称声明，不证明恢复能力已可运行；选择执行者时须核验其真实可用条件。

这些步骤属于原职责的内部执行，不新增研究任务或正式角色，不取得重新规划或降低验收要求的权力。新观察以真实工具结果保留来源，并经既有 Result 接受链形成正式事实；不能由 Binding 或模型猜测补齐。补证可以发生在当前内部回路或后续已确认职责自身范围内，不依赖重开已结束来源实例。

确定性 Skill 不具备纠错工具时，由当前职责合法选定的合格 Agent 在其内部调用该 Skill；已冻结能力不能悄悄替换，须依研究执行合同形成新快照并保留原失败。无专用 Skill 的纯研究工作选择满足 Definition 的通用 Agent，不凭“通用”越过专业资格或外部权限。没有实际合格能力时保留实现缺口，由既有后续责任交付原因，不默认转成用户待办。

### 2.2 Skill

**Skill**承担边界明确、能够重复使用的研究能力，可以直接成为当前研究工作的执行能力。

一个 Skill 可以同时包含模型推理和确定性代码；二者共同实现同一项正式能力，不因此拆成两套独立研究职责。

### 2.3 Agent 内部调用与正式多能力协同

Agent 和 Skill 都可以作为正式执行能力；Agent 能够调用 Skill，不形成二者的项目任务层级。

Agent 在自身能力定义内调用 Skill 时：

- Agent 仍是当前研究工作的正式执行能力；
- 被调用 Skill 只是该 Agent 的内部执行组成；
- 内部调用不会自动形成新的正式能力角色或新的项目研究任务。

如果一项研究工作需要多个能力分别承担正式角色，并按照稳定的依赖、顺序、分支或控制关系协同执行，则使用 Definition 已绑定的正式执行方法。

```text
Agent 内部调用 Skill
≠
正式多能力执行方法
```

### 2.4 Skill 正式输出合同与外部来源身份声明

SkillDefinition 中的正式输出合同说明该 Skill 可以产生什么结构化输出。输出 Schema 规定字段、类型和结构；如果输出包含论文、数据集、网页或其他外部来源记录，产生该输出的 Skill 还必须在同一份正式输出合同中声明：

- 哪个 `record_path` 选中一条可独立接受或拒绝的外部来源记录；
- 记录内哪个 `field_path` 承担来源身份；
- 该字段的 `identity_type`。

最小声明语义如下；具体序列化可以沿用当前 SkillDefinition 对正式输出合同的表达方式，不另建 Schema 系统：

```text
external_source_records:
  - record_path: <正式输出 Schema 中的记录路径>
    identity_fields:
      - field_path: <相对该记录的字段路径>
        identity_type: <DOI | arXiv identifier | URL / locator | provider-observed source identity>
```

`record_path` 和 `field_path` 必须指向该版本正式输出 Schema 中实际存在的结构。字段是否必填、允许几个身份字段以及它们的组合关系仍由该 Skill 的输出 Schema 规定；来源身份声明只赋予这些字段明确身份语义，不复制字段结构。

不同 `identity_type` 对应不同的确定性真实性检查规则。声明 URL / locator 不会把正文中的任意 URL 提升为来源身份；声明 provider-observed source identity 也只表示该正式字段承载 Provider 实际观察并返回的来源身份，不允许系统据此补造未观察到的值。

这份声明的 Authority 关系是：

- 产生外部来源记录的 Skill 是其输出中来源身份语义的唯一声明方；
- Registry 可以登记或引用这份正式能力事实，但不能根据字段名、Skill 名称、示例或历史结果猜测来源字段；
- Binding 只能映射已经存在的正式输入，不能增加、改写或发明输出中的来源身份；
- 公共 validator 只消费本次执行所冻结 SkillDefinition 版本中的正式声明，不维护字段名清单或其他并列声明。

Skill 没有声明外部来源记录或来源身份字段时，不表示实际输出中不可能出现 DOI、URL 或其他看起来像来源的信息；它只表示这些内容没有取得正式来源身份语义。系统仍如实保存实际 Result，但不能仅凭字段名、值的格式或正文内容把它们提升为已验证来源身份。

## 3. 执行方法

当一项研究工作需要多个正式能力角色协同完成，并且这种协同关系本身已经成为稳定研究方法时，Definition 可以绑定一个**明确版本的执行方法**。

执行方法定义：

- 必要和可选的正式能力角色；
- 角色之间的依赖关系；
- 顺序和并行关系；
- 条件分支；
- 停止条件；
- 失败处理；
- 必须保持的质量和执行约束。

执行方法定义的是**角色和控制关系**，不固定具体 Agent、Skill 或模型。

```text
Definition
→ 绑定明确版本的执行方法
→ 执行方法给出正式能力角色和控制关系
→ 为各角色选择合格 Agent / Skill
→ WorkUnit 冻结本次方法版本和实际能力
```

Definition 已绑定执行方法时，本次执行必须保持该版本规定的正式角色和控制关系。能力选择只能为既有角色填入合格能力，不能临时新增、删除或改写角色，也不能通过能力替换改变依赖、顺序、条件分支或停止规则。

不需要正式多能力协同的研究工作，直接选择一个能够独立满足 Definition 的 Agent 或 Skill，不增加额外执行层。

---

## 4. Registry

**Registry**登记系统当前正式可用的 Agent 和 Skill，供能力发现和选择使用。

Registry 可以登记或引用能力选择需要的正式能力事实和当前可用状态，但具体能力语义仍以对应的 AgentDefinition 或 SkillDefinition 为准。

```text
Definition
= 当前研究工作需要什么

AgentDefinition / SkillDefinition
= 某个具体能力能够提供什么

Registry
= 当前有哪些正式可用能力
```

Registry 不根据能力名称、所用模型、文件路径、Prompt、运行方式或历史运行结果自行推断能力范围和科研判断资格。

凡是会影响能力选择的能力事实，都必须来自正式能力定义或其他已有正式 Authority；Registry 只登记和提供这些事实，不重新解释它们。

---

## 5. 能力选择

能力选择发生在 ExecutionDecision 已经确定当前研究工作之后，只回答：

> **本次由哪个合格能力执行已经确定的研究工作。**

它不决定下一项研究工作，也不改变 Definition。

### 5.1 单能力研究工作

Definition 未绑定正式执行方法时，选择一个能够独立满足当前 Definition 的 Agent 或 Skill。

能力选择阶段不能临时组合多个正式执行能力创造新的协同方法。Agent 被选中后，可以按照自身能力定义组织内部 Skill 调用。

### 5.2 使用执行方法的研究工作

Definition 已绑定执行方法时，对执行方法规定的各正式能力角色分别选择合格的 Agent 或 Skill。

能力选择分两步判断。

**能力资格**要求候选能力：

- 支持当前研究工作或当前正式能力角色；
- 能够满足对应 Definition；
- 专业范围与当前工作相符；
- 能够承担当前工作需要的科研判断。

缺少必要能力事实或无法确认资格时，不把该能力用于相应研究工作或角色。

**本次可用条件**继续确认：

- 当前正式输入符合该能力要求；
- 所需运行环境当前可用；
- 符合已经确认的预算和成本边界；
- 不突破已经确认的外部动作和风险边界。

能力具备资格但本次可用条件不足时，不启动该能力；这不改变其正式能力定义。

多个能力同时具备资格并满足本次可用条件时，可以根据当前执行需要比较匹配程度、预期质量、可靠性、成本、耗时和当前可用性，选择本次实际执行者。

同一能力可以跨项目和 Workflow 复用，只要它仍满足当前 Definition、专业判断要求和项目执行边界。需要替换能力时，新能力必须重新满足同一资格条件；能力替换不能降低 Definition，也不能改变已经绑定执行方法的正式角色和控制关系。

Binding 在能力已经选定后解析正式输入，不参与能力资格判断，也不通过输入绑定扩大能力自身的正式范围。

---

## 6. 专业范围与科研判断能力

**专业范围**和**科研判断能力**是两个不同的能力事实：

- **专业范围**说明能力适用于哪些领域、研究对象或问题；
- **科研判断能力**说明该能力在相应范围内能够承担哪些需要科研理解、比较、解释、取舍或形成结论的判断。

专业范围相符，不自动代表具备相应科研判断能力。使用了 LLM、采用某种模型或运行方式，也不能单独证明一个能力具备科研判断资格。

需要由人类 Authority 明确授权或确认的判断，仍由相应人类 Authority 负责；Agent、Skill 或模型不能仅凭技术能力取得该权限。
