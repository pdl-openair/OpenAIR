# OpenAIR 模型调用运行与故障恢复设计合同

> 状态：已确认  
> 更新时间：2026-09-22  
> 职责：规定已经形成的模型调用要求如何进入真实 Provider 执行，系统如何使用运行预算观察与管理执行，如何区分本地连接生命周期与远端模型执行生命周期，以及发生网络或 Provider 故障时如何保留调用事实、核对远端状态、控制恢复并避免不可追溯的重复提交。

---

## 1. 运行主线与核心合同

模型调用运行层接收已经形成的调用要求和当前能力的正式运行配置，负责发起真实 Provider 执行、持续保存执行事实，并根据 Provider 的真实状态完成结果取得、故障处理或恢复。

```text
已经形成的模型调用要求
+ 当前能力的正式运行配置
→ 发起 Provider 执行
→ 保存 submission / transport / Provider execution 事实
→ 持续观察或查询远端执行状态
→ running / completed / failed / cancelled / unknown
→ 按真实状态继续等待、取得结果、记录失败或进入恢复
→ 如发生新的真实 Provider 提交，独立留证
```

整个过程必须保持以下区分：

```text
任务运行预算
≠
自动终止模型执行的截止时间

网络连接生命周期
≠
Provider 模型执行生命周期

未取得 Provider 结果
≠
可以确认请求没有发生

本地响应等待结束
≠
可以确认远端模型执行已经结束

Provider 调用已经完成
≠
上层正式输出已经有效

新的真实 Provider 提交
≠
此前的 Provider 提交
```

运行恢复可以处理模型调用故障，但不能因此改写已经形成的模型输入、科研判断或研究决策。

模型调用运行层不得仅因为固定秒数到期，就把仍可能正常运行的 Provider 执行判为失败或结束。

### 1.1 并发调度与执行隔离

耐久调度记录用于保存待执行工作、领取事实和恢复依据，不规定研究工作必须串行执行。

WorkUnit 已具备执行条件后，对应执行应立即进入可领取状态。调度器只负责发现、领取和分配执行槽；Provider 调用、结果恢复和后续推进等长耗时工作在可独立扩展的执行槽中运行，不能占用调度器并阻止它发现其他工作。

同一用户可以同时运行多个彼此独立的研究任务；多个用户的任务也可以同时运行。只有正式依赖、已确认资源上限或安全与成本边界可以限制并发，系统不能因为采用单个同步 Worker 而把无关任务隐式串行化。

执行容量遵循以下规则：

- Worker 和执行槽可以横向扩展；
- 新执行与故障恢复都必须有公平的领取机会，单个任务、用户、Workflow 或持续失败的恢复项不能长期占用全部容量；
- 恢复项使用明确的下次执行时间、受控退避和有界单轮工作量；
- 在已声明的支持容量内，无关的在途工作不能延迟新执行启动；
- 超出容量时，系统保存真实排队原因和等待时长，并通过增加执行容量恢复及时启动，不能把尚未领取的工作显示成已经运行。

公开部署至少需要验证单个用户四项独立任务并行，以及多用户混合任务并行。具体部署必须声明支持的并发容量和启动时延目标，并用真实 Worker 运行验证；只证明任务最终被领取，不代表并发能力成立。

多个 Worker 领取同一工作时，必须通过耐久 lease、fence 和幂等执行身份保证只有合法持有者能够产生正式写入。长耗时执行持续维护 lease；已经失去 fence 的执行者不得提交结果。扩展 Worker 数量不能导致同一 Provider 调用被重复提交。

## 2. 任务运行预算、网络保护与执行状态

### 2.1 任务运行预算是软预算

任务运行预算表示当前能力对一次正常模型执行的**预计运行范围**，用于运行规划、进度表达、性能观测、异常长尾识别、资源治理和后续效率优化。

任务运行预算不是普通模型执行的自动终止 Authority。

超过任务运行预算时，系统可以：

- 标记本次执行已经超过预计运行范围；
- 记录实际耗时和长尾事实；
- 更新用户可见进度；
- 触发性能诊断、运行观测或后续优化；
- 在产品允许的情况下向用户提供继续等待或主动停止的选择。

系统不得仅因为任务运行预算耗尽，就自动终止一个仍被 Provider 或公共执行层确认处于正常 `running` 状态的模型执行。

如果系统确实需要自动终止某类执行，必须由独立、明确的正式产品、安全、成本或资源合同定义终止条件和 Authority；不能从通用任务运行预算、HTTP read timeout 或页面等待时间隐式推导。

### 2.2 网络阶段保护边界

网络阶段保护边界用于避免连接建立、连接池等待和请求写入等本地传输阶段无限卡住。

其中：

- 建立连接和等待连接池可以使用较短的失败边界；
- 请求写入应有有限保护边界；
- 单个 HTTP 响应观察连接可以有技术性保护或重连机制，但该边界只能结束当前本地观察通道，不能据此宣告远端模型执行已经结束；
- 响应观察中断后，系统应优先依据已经持久化的 Provider execution identity / correlation identity 核对远端执行状态。

网络阶段保护只处理本地连接和传输问题，不重新定义模型任务本身是否仍在运行。

### 2.3 执行状态是运行事实 Authority

模型执行是否继续、完成、失败或取消，优先依据可确认的 Provider / durable execution 事实，而不是依据固定时间数字推断。

公共运行层至少区分：

```text
running
completed
failed
cancelled
unknown
```

只要系统能够确认远端执行仍处于 `running`，就继续保持该执行并继续观察，不因 90s、120s、180s 等固定值自动终止。

超过软预算但仍在正常运行，属于**性能与体验问题**，不是自动失败事实。

## 3. Provider execution identity 与状态核对

### 3.1 公共执行身份

每次真实 Provider 提交必须尽可能建立并持久化能够唯一关联本次远端执行的身份，例如：

- Provider request id；
- Provider job / response / execution id；
- OpenAIR correlation id；
- OpenAIR durable provider execution id；
- 其他能够确定性关联本次提交和后续查询的稳定标识。

身份必须与具体 Provider、模型、调用 attempt 和请求安全标识关联。

### 3.2 状态查询与 reconcile

公共 Provider execution 层必须提供统一的状态核对语义：

```text
execution identity
→ query / observe / reconcile
→ running / completed / failed / cancelled / unknown
```

Provider 原生支持异步执行或状态查询时，优先使用 Provider 的正式查询能力。

Provider 不直接提供可查询 job 时，OpenAIR 公共 Provider execution 层应承担耐久观察责任，使上层科研执行不依赖某一次短生命周期 HTTP 会话存活。具体实现可以是 durable worker、受控长连接、网关执行句柄或其他能够保持执行事实的公共机制。

如果当前 Provider 技术能力确实无法建立可查询或可持续观察的执行身份，系统必须明确记录这一能力边界，不得伪装成已经能够核对远端状态。

## 4. 失败事实与恢复

模型调用发生故障时，恢复动作必须依据已经观察到的事实，而不是把所有失败都处理成同一种重试。

| 已观察到的事实 | 运行层处理 |
| --- | --- |
| 连接未建立或连接池等待失败，能够确认尚未完成真实 Provider 提交 | 可以按当前恢复规则重新尝试 |
| Provider 明确返回限流、服务端错误或其他允许恢复的失败响应 | 保留本次提交事实；只有当前恢复规则允许时，才进行新的提交 |
| Provider 明确返回请求、认证、权限或合同错误 | 保留明确失败事实；不得重复发送同一个已知错误请求 |
| 已取得 execution identity，远端状态为 `running` | 保持当前执行，继续观察或查询；不得因为软预算或本地 read 边界到期而自动重提 |
| 已取得 execution identity，远端状态为 `completed` | 取得或恢复结果，进入上层结果处理 |
| 已取得 execution identity，远端状态为 `failed` | 保存明确失败事实，按正式恢复规则处理 |
| 已取得 execution identity，远端状态为 `cancelled` | 保存取消事实，不把取消改写成失败或结果未知 |
| 请求可能已经提交，但本地写入、读取、连接或协议过程异常中断，且远端状态尚不能确认 | 记录为调用结果不确定；进入 reconcile；不得由 transport / Provider 适配层直接隐藏重复提交 |
| Provider 响应已经完整取得，但上层结构或正式输出检查失败 | 保留本次 Provider 调用已经完成的事实；不得把上层输出失败改写成 transport 失败 |

恢复不能覆盖已经发生的调用事实。

需要再次提交 Provider 请求时，新的真实提交必须作为新的调用事实记录，具有独立身份，并由 durable recovery 的正式 Authority 决定是否允许。

恢复使用的 Provider、模型及运行配置必须处于当前能力已经授权的运行范围内；运行层不能为了恢复临时扩大这一范围。

### 4.1 执行结算与后续推进

Provider 结果已经取得并耐久保存后，本次 Dispatch 对应的执行事实立即结算。Result 的结构检查、科研内容接受、依赖释放和下一轮 ExecutionDecision 属于后续处理，不能反向阻止本次 Dispatch 进入终态。

后续推进需要恢复时，应形成独立、耐久、可退避的继续工作。继续工作失败或暂时不能执行时：

- 已保存的 Result 和 Artifact 保持不变；
- 已结算的 Dispatch 不重新打开；
- 不重新提交已经成功的 Provider 调用；
- 只恢复尚未完成的接受、依赖释放或下一步研究决定。

## 5. 调用结果不确定与自治收敛

当请求可能已经到达 Provider，但系统因为写入、读取、连接或协议中断，无法确认 Provider 是否已经接受、执行或完成本次请求时，本次调用属于**调用结果不确定**。

它表示：

> 当前证据不足以确认本次 Provider 调用成功，也不足以确认它没有发生。

调用结果不确定不是模型失败事实，也不是重新提交授权。

调用结果不确定必须保持以下规则：

- 保留已经获得的提交、transport、execution identity 和 Provider 证据；
- 不把结果不确定改写成“调用未发生”；
- transport / Provider 适配层不得因此自动隐藏第二次真实提交；
- 优先通过 execution identity 查询或持续观察原执行；
- 查询为 `running` 时继续等待；
- 查询为 `completed` 时恢复结果；
- 查询为 `failed` 或 `cancelled` 时记录明确终态；
- 当前确实无法查询或无法确认时，由 durable recovery 保持 `unknown` 并决定后续动作；
- 如果后续恢复决定再次提交，新提交必须具有独立身份，并能与此前的不确定调用区分；
- 多次真实 Provider 提交不能合并成一个无法追溯的调用事实。

系统应尽可能自治收敛 `unknown`。只要系统仍有能力继续核对，就不把内部执行状态判断责任交给用户。

## 6. 用户停止与系统终止

用户可以主动停止当前研究执行或模型执行。

收到用户停止请求后：

- 上层立即停止继续创建依赖该执行的新工作；
- Provider 支持取消时，公共 Provider execution 层发出正式取消并保存取消结果；
- Provider 不支持可靠取消时，系统保存“已请求停止”与远端实际状态之间的区别，继续核对必要的执行事实；
- 系统不得在无法确认远端已经取消时，伪称远端执行已经停止。

系统自动终止模型执行必须有独立正式依据。

以下事实本身不能单独成为自动终止依据：

- 页面等待时间到期；
- HTTP read timeout；
- 通用 90s / 120s / 180s 等固定秒数；
- 任务运行预算超出；
- 用户暂时离开页面。

### 6.1 停止后的正式收敛

用户停止请求成功提交后，当前研究任务的 canonical lifecycle 进入 `cancelled`。停止回执保存请求原因、幂等身份和审计事实，不形成与 canonical lifecycle 并列的状态 Authority。

停止发生时已经在 Provider 侧运行的执行保持其真实运行状态。系统继续保存必要的远端状态和最终执行事实，但不再创建依赖于该执行的新工作。晚到的 Result 可以持久化和追溯，不能把已经取消的研究任务重新改为 `running`。

停止提交和任何在途执行的终态回调都必须触发同一套生命周期收敛规则，使 Task、ExecutionDecision、SubstageInstance 和 WorkUnit 保留各自准确粒度，同时让公开任务状态及时、稳定地来自 canonical lifecycle。

## 7. Provider 调用与执行证据

每次真实 Provider 提交都必须有独立、可追溯的调用和执行证据。

证据至少应能够确定：

- 本次提交的独立身份；
- Provider 和模型身份；
- 本次能力运行配置和软运行预算；
- 调用开始时间、当前持续时间、结束时间或等价耗时；
- 已观察到的 transport 结果；
- Provider execution / request / correlation identity；
- Provider 是否支持查询、取消或结果恢复；
- 已观察到的远端执行状态及其时间点；
- 可以确定的失败类别；
- 已观察到时的 HTTP 状态；
- 是否已经超过预计运行预算；
- 后续 reconcile / recovery / cancellation 动作；
- 与任何后续新提交的关联关系；
- 用于识别本次请求的安全标识，例如 hash 或必要结构摘要。

密钥和恢复、追溯并不需要的原始 Prompt 不进入调用证据。

Provider 调用与执行证据只证明模型调用运行过程中实际发生了什么。它不能证明模型输出已经满足正式结构要求，也不能形成科研结论或科研 Authority。

## 8. 向上层交付的运行事实

模型调用运行层向上层交付的是**运行事实**，不能用本地时间推断替代真实执行状态。

至少包括：

- 当前远端执行仍在运行；
- 已完整取得可进入后续结果处理的 Provider 响应；
- 已确认具体运行失败；
- 已确认取消；
- 调用结果不确定。

当执行仍为 `running` 时，上层保持任务运行或等待状态，不把它投影成科研失败、用户缺信息或正式结果失败。

当执行进入 `unknown` 时，上层保留已有可信结果，并进入系统侧 reconcile / recovery 语义。

只有完整取得可用于结果处理的 Provider 响应后，上层才进入结构、内容和科研结果的后续判断。

运行层不得把 Provider、网络、恢复或长尾性能问题转换成“用户缺少科研信息”。

---

## 9. 产品体验与性能优化边界

产品体验优化不能通过提前终止正常模型执行实现。

系统可以持续优化：

- 模型与 reasoning 配置；
- Prompt；
- 输入规模；
- 任务拆分；
- 并行方式；
- Provider 路由；
- structured output；
- 缓存；
- 资源预算和成本。

但这些优化必须以真实执行事实和能力质量为依据。

执行时间超过预计预算，只能说明当前能力需要性能审查；不能单独证明本次科研执行已经失败或应该被终止。
