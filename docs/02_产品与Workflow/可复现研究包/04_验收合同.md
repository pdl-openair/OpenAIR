# 04｜Research Package 验收合同

> 状态：v0.3 定稿  
> 日期：2026-09-28

Research Package 的完成需要分别证明两件事：用户确实获得了复用价值，以及实现遵守了 OpenAIR 的正式研究边界。

## 1. 两类完成结论

| 结论 | 要证明什么 |
|---|---|
| **Product Done** | 科研人员真实减少了接手成本，并能从可信研究起点继续工作 |
| **Engineering Done** | Package 按正式设计进入 OpenAIR，正式对象和职责关系保持正确 |

结构校验、单元测试或“流程跑完”不能单独证明 Product Done；一次真实案例成功也不能单独证明 Engineering Done。

## 2. 首个真实案例开始前固定比较基线

首个真实 Package 形成之前，先记录本案例的比较基线（baseline），至少包括：

- 不使用 Package 时，贡献者或接手者需要完成哪些关键人工工作；
- 本案例准备观察哪些成本或重复工作指标；
- 什么变化可以认为具有实际产品价值；
- 哪些时间属于不可避免的真实实验或计算，不计入 Package 带来的人工效率收益。

不同研究案例可以使用不同指标，不要求统一数字阈值。比较标准在结果出现前确定。

## 3. Product Done

一个完整真实案例至少通过 P1—P5。

### P1｜贡献成本可接受

Package 主要利用已有研究成果形成。贡献者新增工作集中在系统无法可靠确定的科研语义、验证边界、适用条件和限制，而不是重新录入整个旧项目。

验收应证明：可追溯且语义未变化的已确认成果及其确认依据能够复用；新增或变化的重要语义由系统先核查，只将无法可靠确定且影响复用判断的项交用户；包的范围确认能够与最终成果确认合并，或对确需单独动作给出具体理由。不得把逐包全面重审已确认产出作为默认完成条件。外部来源不因缺少内部记录而自动变成整份人工重审要求，系统仍负责来源整理与有界核查。

至少记录：系统复用了什么、贡献者人工补了什么、新增了多少关键步骤或时间，以及是否达到案例开始前确定的可接受标准。

### P2｜新使用者能够独立理解

未参与原研究的目标用户，仅依靠 Package 的人类可读视图就能说清：

- 方法解决什么问题；
- 有哪些参考实例；
- 每个实例对应什么研究对象和条件；
- 每个实例实际验证了什么、依据和边界是什么；
- 关键结果是什么性质，并能回到具体来源位置核查；
- 哪些资源可以继续利用；
- 哪些内容需要保持、可以调整或仍未验证；
- 面对当前问题，哪些已有内容可以作为规划输入，哪些需要重新核验。

如果关键含义仍依赖原作者口头补充，或只能通过直接阅读 YAML 才能获得，本项不通过。

### P3｜重复工作明显减少

与从论文、代码和零散资料重新恢复研究起点的公平对照相比，至少一类重要重复工作达到案例开始前确定的改善标准。

可以记录人工时间、步骤数、需要重新恢复的关键事实数量或其他适合当前场景的可核验指标。大型计算、训练或真实实验本身不可避免的运行时间单独记录。

### P4｜研究起点可信

使用者能够明确区分：

- 原研究已经取得和验证到什么程度，以及没有验证什么；
- 当前项目已经重新核验并接受了什么；
- 当前仍有哪些推断、冲突、未知和限制；
- 当前条件与参考实例有哪些会影响可信度的重要差异。

参考实例的关键结果应能回到具体来源位置，并保留对应研究对象、条件、方法、科研性质和重要不确定性。

需要重新执行才能建立当前可信度时，必须有真实执行证据；不需要重新执行时，应能说明为什么现有依据足以支持当前使用。

### P5｜能够进入新的研究

用户能够把 Package 与当前问题、条件、Workflow 和已有事实一起进入正式规划，并形成至少一项新的真实研究工作或有依据的“不需要继续”判断。

新研究最终是否成功，不作为本项通过条件。

## 4. Engineering Done

工程验收至少证明 E1—E6。

### E1｜内容与来源保真

影响科研判断的关键方法、参考实例、结果和适用边界能够回到真实来源，并保持原研究的对象、条件、结果性质和重要限制。

至少确认：

- 实验、计算、预测、作者解释等不同科研性质没有被静默混写；
- 不同研究对象或实质不同的条件集合没有被静默合并为一个参考实例；
- 每项关键结果既能回到来源身份，也能定位到来源中的具体位置，或明确保留当前无法定位的真实状态；
- 原来源中的重要条件、方法、不确定性和限制没有在整理时消失；
- 缺失、冲突和未确认信息没有被默认值补成确定事实；
- `verification` 的说明能够回到真实来源，并保持实际验证强度和边界。

Package 的来源关系本身不取得当前项目 Evidence 身份。

### E2｜身份、版本与往返一致

经过创建、保存、读取、导出、分享、导入和再次读取后，Package `id`、Package `version`、`spec_version`、关键科研语义和来源关系保持一致。

同一个已发布 `id + version` 不允许原地改写；内容变化产生新版本。

### E3｜协议读取可靠

至少证明：

- 标准字段按 `spec_version: "3"` 正确读取；
- 可选字段缺失与明确记录的未知、限制或不确定性不会被混为一谈；
- `sources`、`reference_cases`、`results` 和 `resources` 的确定性引用关系能够校验；
- `reference_case.subject + conditions + results` 的对应关系能够往返保留；
- 每项结果的 `nature`、来源身份和 `source_location` 能够往返保留；
- 关键资源版本已知时能够保留，未知时不会被默认成“最新版”；
- 不支持的协议版本不会被错误解释；
- 扩展字段不会改变标准字段语义；
- 导入不会自动执行外部代码、脚本或命令；
- 结构非法的 Package 不会被静默删除坏项后继续当作同一 `id + version` 的合法 Package。

### E4｜规划接入正确

规划接入必须符合 [02｜Research Package 架构设计](02_架构设计.md) 中“Package 怎样进入新项目”一节定义的正式关系。验收重点证明：

- Package 只是规划来源之一，当前项目仍形成自己的 ResearchDesign；
- 实际采用的 Package 身份、版本和内容能够追溯；
- 未采用或需要重新核验的内容不会被静默当作已确认方案事实；
- 追溯沿用现有规划来源关系，不以 Package 专用字段形成新的规划事实来源。

### E5｜执行和资源边界正确

ResearchDesign 确认后，下一项研究继续由 ExecutionDecision 决定，WorkUnit 冻结本次正式执行输入。Package 的能力需求不把具体 Agent、Skill 或 Provider 固定进执行。

当可信度或复现含义依赖资源版本时，要分别证明：

```text
Package 记录的原研究资源
≠ 当前项目计划使用的资源
≠ 程序实际使用的资源
```

Package 中存在资源名称、链接或历史版本，不能被解释成当前项目已经取得、计划使用或程序已经实际使用。

### E6｜失败边界和追溯成立

先区分两类失败：

**Package 协议 / 结构失败**

- 必需字段缺失、确定性引用非法、不支持协议版本等问题，使当前文档不能成为合法 Package；
- 不能删除坏项后把剩余内容继续作为同一 `id + version` 的合法 Package；
- 原始输入和诊断可以保留用于修复，已发布内容发生变化时产生新版本。

**合法 Package 在使用过程中的局部失败**

- 外部资源暂时不可取得、来源当前无法访问、当前项目不采用某个实例、后续研究工作失败等，只隔离真实影响；
- 其他仍可信且合同允许独立使用的内容继续保留；
- 继续使用受影响内容会形成错误正式结果时，停止对应路径。

同一真实案例还应能从当前研究结果回溯到实际采用的 Package、版本和来源。

## 5. 单案例结论

同一真实案例的 P1—P5 和 E1—E6 全部有证据并通过，才标记该案例 Done。

某一项没有证据时保持“未验证”；不能用其他项目通过的证据替代本案例缺失的证据。

## 6. 首轮产品级完成

首轮发布采用“完整首案 + 异形第二案”的最小通用性证明：

- 一个真实案例完整通过 P1—P5、E1—E6；
- 第二个研究形态明显不同的真实案例，证明同一核心协议、来源追溯、规划接入和正式边界仍然成立；
- 第二案例不需要新增领域专用 Package 字段或专用执行旁路；
- 用户能够完成形成、分享、导入、理解、采用和继续研究的关键路径；
- 尚未覆盖的科研类型明确标记为未验证。

第二案例用于排除“只对首案成立”的特判，不要求重复首案全部产品效率证明。
