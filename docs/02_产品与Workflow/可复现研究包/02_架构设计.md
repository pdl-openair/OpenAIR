# 02｜Research Package 架构设计

> 状态：v0.3 定稿  
> 日期：2026-09-28

## 1. 阅读本文件需要知道的 OpenAIR 对象

| 对象 | 这里需要知道的含义 |
|---|---|
| **Workflow** | 跨项目复用的研究工作结构，帮助当前项目规划需要完成哪些类型的研究工作 |
| **ResearchDesign** | 当前项目已经确认要研究什么、遵守什么要求和边界 |
| **ScientificState** | 当前项目已经接受了什么科研认识，还存在哪些缺口和不确定性 |
| **ExecutionDecision** | 基于当前方案和科研状态，决定下一步做什么研究工作 |
| **WorkUnit** | 冻结某一次具体执行实际使用的正式输入、能力和边界 |
| **Result** | 某次执行实际产生的内容 |
| **Artifact** | 已保存、可查看和继续使用的研究产物 |
| **Evidence** | 当前项目中能够支持、反驳或限制科研判断的具体依据 |
| **CompletionDecision** | 根据完成要求和最新科研状态，判断项目为什么现在可以结束 |
| **Final Result** | 项目最终向用户交付的正式结果 |

Research Package 是这些正式对象之外的一类**版本化研究资产**。本文件只需要这些最小含义；更完整的对象定义仍以 OpenAIR 核心设计为准。

## 2. 核心关系

Research Package 保存已有研究中值得复用的方法、参考实例、资源来源和适用边界，并作为可追溯来源参与新的研究规划。

```text
已有研究成果
      ↓
Research Package
      ↓
Package + 当前问题 + 当前条件 + 适用 Workflow + 已有正式事实
      ↓
形成研究方案草案 → 正式检查 → 用户确认
      ↓
ResearchDesign
      ↓
ResearchDesign + ScientificState
      ↓
ExecutionDecision → WorkUnit → Result
      ↓
结果接受 / Evidence / Artifact / ScientificState 更新
      ↓
CompletionDecision → Final Result
```

Package 保存已有研究资产；新的项目仍由 OpenAIR 的正式规划、执行、科研状态和完成判断机制决定这一次研究什么、怎么继续、什么时候结束。

## 3. Package 保存什么

| 内容 | 含义 |
|---|---|
| **方法** | 已有研究中值得复用的目标、输入、研究逻辑和通常输出 |
| **参考实例** | 在什么研究对象和真实条件下验证了什么、得到了什么结果，以及验证依据和限制 |
| **资源来源** | 原研究使用或引用的代码、数据、模型、配置、SOP、文档等 |
| **适用边界** | 适合什么时候使用、哪些内容应保持、哪些可调整、哪些范围仍未知 |
| **能力需求** | 完成这类方法通常需要什么研究能力 |

当前项目的研究方案、科研状态、下一步决定和完成判断继续由 OpenAIR 相应正式对象保存。

## 4. Package 怎样形成

Package 可以来自 OpenAIR 项目中已经形成且可追溯的研究成果，也可以来自来源能够确认的外部论文、实验、计算或其他真实研究材料。

```text
已有研究来源
→ 识别值得跨项目复用的方法、参考实例、资源和边界
→ 保留来源、身份和版本关系
→ 补充机器不能可靠确定的科研语义
→ 组装并校验 Package
→ 贡献者确认并发布
```

需要科研理解、比较、解释或判断不确定性的内容，由**具备相应科研判断能力的 Agent / Skill**负责；它们可以在自身正式能力定义允许的范围内使用 LLM。稳定身份、版本、引用关系、结构组装和确定性校验由代码处理。

内部已有成果形成 Package 时，应以可追溯的已接受成果及精确版本为输入，复用其已有内容和确认依据；生命周期状态“运行完毕”本身不足以证明成果已接受。系统自动准备内容并检查映射，不因重新表述而扩大原确认或验证强度。新增、变化或冲突的科研语义先由正式能力处理，只有重要且无法可靠确定的项请求贡献者确认。

“贡献者确认并发布”是确认包的纳入范围、必要新增内容及其限制，不是再次全面审核已确认产出。可以与最终成果确认合并，但必须明确绑定实际 Package 内容和版本；公开分享权限另行按现有机制处理。内容或来源变化时重新处理受影响部分，未变化的确认和已发布版本保持稳定。具体草稿对象、触发点和接口由实施方案决定，不预设必须另建审阅流程。

参考实例记录的是原研究实际完成过的验证及其边界。进入新项目后，这些内容仍需按当前项目的正式机制决定如何使用。

## 5. Package 怎样进入新项目

```text
Package 作为来源
+ 当前研究上下文
→ 形成研究方案草案
→ 正式检查
→ 用户确认
→ 当前 ResearchDesign
```

规划追溯至少应能回答：使用了哪份 Package 和哪个版本、实际采用了哪些内容、哪些内容没有采用、哪些内容因条件不同需要重新核验。

这些关系使用 OpenAIR 现有的规划来源和追溯机制表达。长期合同只依赖“形成草案 → 正式检查 → 用户确认”的语义链，不绑定具体实现组件。导入本身只恢复研究资产，不更新 ScientificState，也不产生当前项目 Evidence。

Package 发布新版本后，已经确认的 ResearchDesign 不会被静默改写；当前项目若要采用新版本，按 ResearchDesign 的正式变更规则处理。

## 6. 资源保持三种事实

```text
Package 记录的原研究资源
        ↓
当前项目计划使用的资源
        ↓
程序实际使用的资源
```

三者分别回答：

1. 原研究使用或引用了什么；
2. 当前项目准备使用什么；
3. 程序运行时实际使用了什么。

Package 负责第一项。当前项目计划使用的资源进入正式执行输入并由 WorkUnit 冻结；程序实际使用的资源由真实运行事实和资源使用核验确认。

当参考实例的可信度或复现含义依赖具体资源版本时，Package 保留足以识别该版本的已知信息；版本无法确认时，如实保留这一限制。

真实文件继续由 OpenAIR 现有文件、Artifact 或资源基础设施承载。

## 7. 多 Package、版本与冲突

一个项目可以引用多份 Package，也可以只采用某份 Package 的一部分。

多来源同时存在时：

- 每份 Package 的身份和版本分别保留；
- 各自适用条件分别检查；
- 科研内容冲突时保留原来源和差异，由科研判断处理；
- 代码只处理能够确定性确认的身份、版本和引用关系。

已发布的 `id + version` 表示同一个不可原地改写的 Package 版本。内容变化时产生新版本；已经采用旧版本的项目不会被新版本静默替换。
