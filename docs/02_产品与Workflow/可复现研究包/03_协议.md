# 03｜Research Package 协议

> 状态：v0.3 定稿  
> 协议版本：`spec_version: "3"`  
> 日期：2026-09-28

本协议定义 Research Package 的机器可读结构和字段语义。

## 1. 最小结构

```yaml
spec_version: "3"

id: example-research-package
name: 示例研究方法
version: "3.0"
summary: 一句话说明这份 Package 能为后续研究提供什么起点。

sources:
  - id: source-main
    name: 原始研究、论文、实验或其他真实来源
    ref: 可追溯引用

method:
  goal: 这套方法主要解决什么研究问题
  inputs:
    - 开展这套方法通常需要的研究输入
  logic:
    - 值得跨项目复用的研究逻辑或关键判断
  outputs:
    - 这套方法通常形成的研究结果
  validation_criteria:
    - 可选。原方法或参考实例采用过的验证要求
  source_refs:
    - source-main

reference_cases:
  - id: case-main
    subject: 这个实例对应的研究对象、样品、模型、数据集或运行对象
    target: 这个实例实际验证了什么
    source_refs:
      - source-main
    verification:
      summary: 为什么这个实例可以作为已验证参考实例
      source_refs:
        - source-main
      limits:
        - 这次验证没有覆盖什么，或结论受什么条件限制
    conditions:
      - 对结果有重要影响、且适用于本实例全部结果的条件
    results:
      - description: 实际获得的结果
        nature: 结果的科学性质，例如实验观测、计算结果或模型预测
        source_refs:
          - source-main
        source_location:
          status: located
          ref: 表 2 / 图 4 / 第 3 页 / Artifact 定位符或其他具体位置
        method: 可选。理解该结果所必需的测量、计算或评价方法
        uncertainty: 可选。原研究明确报告的不确定性、误差或限制
    resource_refs:
      - code-main

resources:
  - id: code-main
    name: 可复用资源名称
    role: code
    ref: 资源来源或稳定引用
    revision: 可选。版本、commit、release、数据版本或其他稳定修订标识
    note: 可选说明

applicability:
  use_when:
    - 适合采用这套方法的情况
  preserve:
    - 复用时对方法含义或结果可信度重要、应保持的内容
  adaptable:
    - 可以结合当前研究调整的内容
  limits:
    - 已知限制、未验证范围或重要未知
  source_refs:
    - source-main

capabilities:
  - 完成这套方法通常需要的研究能力
```

## 2. 顶层字段

| 字段 | 是否必需 | 含义 |
|---|---|---|
| `spec_version` | 是 | Research Package 协议版本 |
| `id` | 是 | Package 稳定身份 |
| `name` | 是 | 面向用户的名称 |
| `version` | 是 | 当前 Package 版本 |
| `summary` | 是 | 这份 Package 提供的研究起点 |
| `sources` | 是 | 支撑 Package 科研内容的可追溯来源 |
| `method` | 是 | 可复用研究方法 |
| `reference_cases` | 是 | 一个或多个已验证参考实例 |
| `resources` | 否 | 可复用资源的来源和版本线索 |
| `applicability` | 是 | 适用条件、保持项、可调整项和限制 |
| `capabilities` | 是 | 完成方法通常需要的能力语义 |

`id`、`version` 和 `spec_version` 分别表示 Package 身份、Package 内容版本和协议版本，不能混用。

同一 `id + version` 表示同一个已发布 Package 版本，其内容保持不可变；内容变化时产生新的 `version`。

## 3. 来源

`sources` 保存 Package 内使用的来源身份。每个来源至少包含：

- Package 内唯一 `id`；
- 可读名称 `name`；
- 能够回到真实来源的 `ref`。

来源可以指向 OpenAIR 内部正式研究事实，也可以指向论文、实验、计算记录、数据集或其他外部真实材料。

`sources` 表示“Package 的内容从哪里来”，不表示这些内容已经被当前项目接受为 Evidence。

引用不存在的 `sources.id` 属于结构错误。

## 4. 方法

`method` 描述跨项目仍值得复用的方法语义：

- `goal`：主要解决什么研究问题；
- `inputs`：通常需要什么研究输入；
- `logic`：值得复用的研究逻辑或关键判断；
- `outputs`：通常形成什么研究结果；
- `validation_criteria`：原方法或参考研究采用过的验证要求，可选；
- `source_refs`：支撑这些方法语义的来源。

`method.logic` 描述研究方法，不定义固定 Workflow、Substage、Agent、Skill、Provider 或调用顺序。

`validation_criteria` 只记录原方法或参考实例的验证语义，不成为当前项目的完成要求。

## 5. 已验证参考实例

每个 `reference_cases[]` 保存一个**原子参考实例**：一个明确研究对象，加上一组对该实例全部结果共同成立的重要条件。

如果同一来源包含多个样品、模型、数据集、实验组、运行对象，或者不同结果依赖实质不同的条件集合，应拆成多个 `reference_cases[]`，不能为了结构简化把不同对象或条件静默合并。

### 5.1 实例字段

| 字段 | 是否必需 | 含义 |
|---|---|---|
| `id` | 是 | Package 内实例身份 |
| `subject` | 是 | 该实例对应的研究对象、样品、模型、数据集或运行对象 |
| `target` | 是 | 该实例实际验证了什么 |
| `source_refs` | 是 | 该实例对应的真实来源 |
| `verification` | 是 | 为什么它可以作为已验证实例，以及验证边界 |
| `conditions` | 是 | 对该实例全部结果含义或可信度共同重要的条件 |
| `results` | 是 | 该实例真实取得或报告的结果 |
| `resource_refs` | 否 | 与该实例直接相关的资源引用 |

### 5.2 `verification`

`verification` 不表示当前项目已经接受这些内容，它只说明**原研究中实际完成了什么验证**。

- `summary`：验证是怎样成立的；
- `source_refs`：支撑该验证说明的来源；
- `limits`：该验证没有覆盖什么，或结论在哪些条件下才成立。

`verification.summary`、`verification.source_refs` 和 `verification.limits` 均为必需字段。`summary` 为非空说明，保留实际验证含义与强度；`source_refs` 必须非空并引用已定义来源；`limits` 为字符串列表，允许为空，但空列表不表示无限适用或原研究不存在限制。已知且影响复用的限制或未确认信息必须显式保留，不得用空列表隐藏。代码只校验结构，不裁决验证是否科学成立。

“论文中出现过某个结果”“贡献者重新检查过”“原项目实际运行得到”“第三方独立复现过”具有不同含义，应按真实情况描述，不能统一写成没有边界的“已验证”。

### 5.3 `results`

每项结果至少包含：

- `description`：原研究实际取得或报告了什么；
- `nature`：结果的科学性质。该字段是科研语义，不是闭合枚举；例如实验观测、计算结果、模拟结果、模型预测、来源直接报告等；
- `source_refs`：支撑这项具体结果的来源；
- `source_location`：能够定位这项具体结果在原来源中的位置，或明确说明当前为什么无法定位。

`source_location` 至少包含：

- `status`：`located`、`source_not_reported` 或 `currently_unavailable`；
- `ref`：当 `status: located` 时必需，指向表格、图片、段落、页码、实验记录、Artifact 或其他具体位置；
- `note`：当具体位置当前无法取得或原来源没有提供时，用于保留原因和影响，可选但推荐。

`source_refs` 回答“来自哪份来源”，`source_location` 回答“这项具体结果在来源的哪里”。二者不能互相替代。

`reference_case.subject` 与 `conditions` 对该实例内全部 `results` 生效。某项结果对应不同对象或实质不同的条件时，应拆成新的 `reference_case`，而不是让结果继承错误上下文。

以下信息在会影响结果含义时必须保留：

- `method`：测量、计算、评价或汇总方法；
- `uncertainty`：原研究报告的误差、不确定性或适用限制。

Package 只能忠实保存原研究已有的科研属性。不能把作者解释写成直接观察，把模型预测写成实验结果，也不能为了结构完整补造原资料没有提供的条件、方法或不确定性。

## 6. 资源

每个 `resources[]` 使用 Package 内唯一 `id`。

| 字段 | 是否必需 | 含义 |
|---|---|---|
| `id` | 是 | Package 内资源身份 |
| `name` | 是 | 资源名称 |
| `role` | 是 | 资源在原方法或参考实例中的作用 |
| `ref` | 是 | 资源来源、位置或稳定引用 |
| `revision` | 否 | 版本、commit、release、数据版本等修订信息 |
| `note` | 否 | 需要保留的补充说明 |

常见 `role` 可以是 `code`、`data`、`model`、`config`、`environment`、`script`、`template`、`document`、`sop`；其他场景使用清楚的语义名称即可。

`revision` 一般可选，但如果某个参考实例的可信度或复现含义依赖具体资源版本，则必须满足以下之一：

1. 提供足以稳定识别该版本的 `revision` 或等价身份；
2. 明确记录版本当前无法确认，以及这一缺口对复用或复现的影响。

只有资源名称、会变化的标签或“最新版”不足以替代已知且重要的稳定版本身份。

`resources` 记录原研究的资源来源事实，不表示当前项目已经取得、计划使用或实际使用该资源。

## 7. 适用边界与能力需求

`applicability` 表达：

| 字段 | 含义 |
|---|---|
| `use_when` | 适合采用这套方法的情况 |
| `preserve` | 复用时对方法含义或结果可信度重要、应保持的内容 |
| `adaptable` | 可以结合当前研究调整的内容 |
| `limits` | 已知限制、未验证范围和重要未知 |
| `source_refs` | 支撑这些适用性判断的来源 |

这些内容为后续规划和科研判断提供输入，不直接成为当前项目的硬编码执行约束。

`capabilities` 描述“完成这套方法通常需要什么研究能力”。这里不填写具体 Agent、Skill、Provider、服务 ID 或运行时入口。

## 8. 缺失、未知和兼容规则

1. Package 使用 YAML 或等价 JSON 表达；
2. 可选字段未提供，只表示该信息没有随当前 Package 提供或当前不适用，不能自动解释成科研上的“未知”；
3. 已知某项信息与复用或可信度相关但当前无法确认时，应在对应 `limits`、`uncertainty`、`note` 或其他适当科研内容中明确保留，不得通过省略伪装成“不需要”；
4. 标准字段按当前协议解释，扩展字段不能改变标准字段含义；
5. 不支持的 `spec_version` 必须明确识别，不能按其他协议静默继续；
6. 导入 Package 只读取和保存研究资产，不自动执行其中引用的代码、脚本、命令或外部动作；
7. Package 可以被多个项目引用，每个项目分别记录实际采用的 Package 版本；
8. 引用不存在的 `sources.id`、`resources.id` 或其他确定性身份关系属于结构错误，必须在正式读取或发布前发现；
9. **协议或结构错误不会被“局部隔离”自动改写成合法 Package。** 如果一个文档不能满足本协议的必需字段、引用完整性或其他确定性结构要求，就不能删除坏项后把剩余内容继续当作同一 `id + version` 的合法 Package。系统可以保留原始输入和错误诊断用于修复，但修正后的内容必须重新形成合法 Package；已发布版本发生内容变化时产生新 `version`。
10. v2 与 v3 按各自协议读取。已有 v2 的原文、身份、内容哈希、导入导出及既有采用记录保持有效；新的产品贡献入口形成 v3。新项目可以在明确旧协议限制的前提下采用 v2 实际提供的内容，仍走正式规划检查和用户确认。缺少 v3 的对象、验证或结果定位语义时，不得补造或当作已知事实；当前研究确需这些信息时，须补齐并确认新的内容版本，或在当前正式研究中重新核验。升级不得原地改写旧发布版本。

## 9. 与 OpenAIR 当前项目事实的关系

Research Package 不保存当前项目的：

- 正式 ResearchDesign；
- 当前 ScientificState；
- 当前项目的 Evidence 接受状态；
- ExecutionDecision；
- WorkUnit；
- 程序实际资源使用事实；
- CompletionDecision；
- Final Result。

这些内容进入新的项目后，继续由 OpenAIR 对应正式对象和机制形成。
