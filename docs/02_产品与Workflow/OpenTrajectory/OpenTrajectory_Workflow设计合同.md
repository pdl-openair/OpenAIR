# OpenTrajectory Workflow 设计合同

> 状态：定稿　｜　版本：v3.1　｜　日期：2026-09-16  
> 本合同规定 OpenTrajectory 在 OpenAIR 中的研究结构、职责、依赖和交付要求。产品取舍遵循《产品第一原则》；通用对象、能力与执行机制遵循 `docs/01_核心设计/**`。

## 1. 产品目标与范围

OpenTrajectory（OT）面向需要综合多项研究结果、比较条件差异、处理冲突与不确定性的科研问题，帮助用户减少资料整理和无效研究的成本，形成有依据的判断，并决定下一步最值得推进什么。

一轮研究交付四项核心信息：**当前判断、判断依据、关键未知、下一步建议**。信息的深度和研究投入以用户问题需要解决的程度为准。

OT 可以分析论文、实验、计算、数据库和代码运行结果。单一事实查询、概念说明和资料定位采用轻量处理。具体实验、仿真、制备或测量方案及其专业执行由相应专业 Workflow 承担；OT 提供待验证问题、依据、关键条件和判别目标，并接收真实结果继续判断。服务于证据核查的通用检索、阅读、数据整理和工具验证可以在 OT 内完成。

## 2. 研究结构与规划

OT 沿用 OpenAIR 的四个通用阶段。各阶段组织的研究内容如下：

| 通用阶段 | OT 研究内容 |
|---|---|
| 问题建模 | 确定主研究问题、判断目标、已有信息和约束 |
| 方案设计 | 确定证据需求、比较维度、必要研究任务和完成要求 |
| 执行与验证 | 建立研究记录，评估与综合证据，按需解释机制 |
| 洞察形成 | 形成当前结论、关键未知和下一步研究建议 |

首次研究以“问题与证据计划 → 研究记录 → 证据评估与综合 → 当前结论 → 关键未知 → 下一步建议”为基准路径。机制解释在影响判断时进入。已有成果和后续新结果可以从相应位置接入；具体依赖见第 4 节。

Router 选择适用的 OT Workflow 后，Planner 结合用户问题和已有材料形成项目计划，Compiler 检查并形成 ResearchDesign。计划至少明确：

- **判断目标**：主研究问题、对象、约束、目标产出，以及需要回答到什么程度。辅助研究维度服务主问题，不自动增加项目完成要求。
- **证据需求**：需要查证什么、比较什么，已有材料哪些可用或待核实，什么缺口会改变判断，以及补证的优先级和投入边界。
- **执行与结束要求**：具体研究任务、适用的研究工作要求、必要依赖、可复用成果，以及充分回答和仍有缺口时各自的收口条件。

问题澄清和证据规划优先在方案形成时完成。执行中发现实质歧义或新缺口时，仍可开展必要的澄清和重新规划；已确认内容不机械重做。方案中的预期证据和预期结论保持待验证语义。

用户确认 ResearchDesign 后开始真实研究。Planner 可在 Workflow 允许的结构内补充适用的通用研究工作；专业范围和方案变更遵循 OpenAIR 正式合同。

## 3. 正式研究职责

以下六类职责构成 OT 的研究骨架，分别具有明确的输入和结果要求。它们不等于每个项目必须新建六项任务或执行六次。某项职责能否由已有成果满足，按第 4 节检查。

### 3.1 研究记录建立

**输入：** 当前问题需要使用的原始研究材料，以及已有研究记录。

**结果：** 可追溯的研究记录（ResearchRecord），保持“研究对象—条件—结果—来源”的对应关系。来源须能定位到支撑内容；一篇论文中的不同实验、样品或运行不能默认合成一个比较对象。原始观测、作者解释和用户提供的信息保留各自身份与核验程度。

**进入条件：** 有相关材料尚未整理，或新结果需要补充、纠正已有记录。已有记录经当前项目接受且适用时直接复用。缺少材料或关键字段时保留缺口，不补造结果。记录建立只确认材料报告了什么，证据用途由下一项职责判断。

### 3.2 证据评估与研究综合

**输入：** 当前判断目标、研究记录、已有证据及其来源和条件。

**结果：** 围绕具体判断建立证据（Evidence）的支持、反驳或限制关系，说明来源质量、独立性、适用条件、冲突和证据缺口，并综合形成主要发现。每项证据关系均可回到研究记录和原始来源；同一原始结果的重复转述不作为多份独立支持。

涉及跨研究比较时，说明比较对象、指标口径、条件差异及其影响，区分可直接比较、仅能有限参考和不能直接比较。可比性针对具体判断成立，不给研究记录贴永久可比标签。不涉及跨研究比较时说明其适用性，不强制生成比较表。

缺少证据、未找到证据和反向证据分别表达；相关性、因果性和推断分别表达。证据为空或不足时，可以形成有依据的不足评估，说明已核查范围及关键缺口，不把检索范围内未发现推广为不存在。

### 3.3 机制解释

**输入：** 待解释现象、相关研究记录、证据评估和候选解释。

**结果：** 可能的作用路径、支持或限制这些路径的证据，以及尚未验证的关系。已有证据支持、作者解释和 OT 推断分别标明，不为补全机制链增加无依据的连接。

**进入条件：** 用户核心问题需要回答“为什么”，或机制解释可能实质影响证据解读、当前结论、关键未知或下一步建议。证据不足时保留机制未知；能力暂时不可用不等于机制问题已经解决。

### 3.4 当前研究结论

**输入：** 当前研究问题、已接受的证据评估与研究发现，以及适用时的机制解释。

**结果：** 对用户主问题的直接回答，并保留每个关键判断的依据、适用条件、重要冲突、限制和不确定性。不同判断的证据强度分别表达，结论强度不超过对应证据。

当前无法确定是合法结果，应说明不能确定的具体问题和原因。既有结论的复用范围以当前目标、条件和新证据为准。

### 3.5 关键未知与候选解释

**输入：** 当前结论、冲突、限制和证据缺口。

**结果：** 会实质改变结论或用户下一步行动的关键未知，并说明它影响哪个判断、缺少什么信息和优先处理的理由。一般性未研究问题不自动成为本项目待办。

有合理依据时形成候选解释、假说或判别预测，保留提出依据和验证缺口；同时说明哪些新结果能够支持、削弱或仍无法区分这些解释。没有足够依据时只保留未知；不存在影响本轮目标的关键未知时如实说明，不强制凑出假说。

### 3.6 下一步研究建议

**输入：** 当前结论、关键未知，以及用户的时间、资源、成本、风险和已确认边界。

**结果：** 优先推进的研究方向及其理由，说明需要获得什么证据、重点观察什么结果，以及不同结果将怎样改变当前判断。存在多个合理方向时给出可解释的优先顺序或并列选择，不制造唯一最优。

建议可以是定向补证、复核结果、区分解释、交给专业 Workflow 获得新结果、等待必要信息，或当前范围无需继续研究。新增信息预期难以改变判断且成本较高时，不因流程仍可运行而继续扩展。

本职责向用户提供科研建议；系统实际执行什么由 ExecutionDecision 决定，项目是否结束由 CompletionDecision 判断。建议、用户授权和实际执行分别记录。

## 4. 依赖、复用与持续推进

### 4.1 依赖所需信息，不依赖固定前一步

研究记录支撑证据评估；证据评估及适用的机制解释支撑结论；结论和证据缺口支撑关键未知；结论、未知和资源边界共同支撑下一步建议。下游可以引用所需的全部正式来源，不只读取紧邻节点的摘要。

依赖可由本次研究结果或已被当前项目接受的已有成果满足。需要形成确定结论时，必须有相应证据；形成“当前无法确定”时，可以使用已接受的证据不足评估与缺口记录。来源或结果真实性无法确认的内容，不作为可信结论的依据。

### 4.2 覆盖、跳过与复用

项目收口时，证据评估、当前结论、关键未知和下一步建议均应有符合本合同的结果；研究记录建立和机制解释按其进入条件处理。

复用前检查成果的来源、版本、适用条件、当前目标和新增证据，确认仍满足相应工作要求。复用依据在正式项目记录中可追溯；复用不伪装成本次重新执行。被跳过、暂不可用或执行失败，也不等于职责已满足。

检索、筛选、阅读等按真实缺口选择，不要求每轮必经。共同服务同一研究工作的技术步骤可在其执行内部完成；需要独立科研判断时，可按正式能力适用范围形成通用研究任务。

### 4.3 新信息与局部失败

每次结果经检查接受后更新 ScientificState，由新的 ExecutionDecision 决定下一步。新证据或纠错只触发受影响的记录、评估、结论、未知和建议更新；历史结果保留，失效判断不继续作为当前依据。

局部读取、模型或工具失败时，隔离受影响内容，保留有效成果，并说明缺口对当前判断的影响。系统故障由系统处理；只有确需用户提供专有信息或确认边界时才请求用户参与。仍可可信回答的部分继续交付。

同一研究任务再次执行时复用原任务身份，由新执行决定产生新工单。调整顺序、次数或执行能力遵守已确认依赖；新增或删除任务、修改依赖、工作要求、完成要求或已确认边界，均按 OpenAIR 规则形成新方案并重新确认。

## 5. 用户成果与研究结束

已形成的有效成果应持续可见，并清楚标明当前可确认内容、尚待核查内容和后续变化。用户可以从关键判断逐层核查证据、研究记录和原始来源；内部节点与执行日志不替代研究成果。

本轮交付应使用户能够直接理解：当前对主问题的回答、主要依据与重要条件差异、仍影响判断的未知，以及有依据的下一步建议。没有必要继续研究时明确说明；尚有关键缺口时明确缺口、影响和后续取得信息的方式。

研究达到已确认完成要求，或满足方案中允许保留明确缺口的收口条件时，交由 CompletionDecision 判断是否结束。最终结果按 OpenAIR 正式机制生成、校验并保存。停止检索、等待新实验、预算耗尽或执行受阻，本身不表示研究目标已经达成。

“已充分回答”和“证据不足、尚不能确定”均可如实交付，但必须分别说明目标达到的程度。当前方案不允许带缺口结束时，保留未完成状态或按正式流程调整方案；不在收口时降低要求。

## 6. OpenAIR 接入约束

OT 复用 OpenAIR 的规划、执行、科研状态和完成判断机制。Workflow 定义保存本合同对应的研究结构、必要依赖及 Definition 版本或稳定引用；ResearchDesign 保留所使用的 Workflow 引用。文档章节、阶段展示和成果分组不直接生成工单，也不形成第二套研究状态或完成依据。

各正式职责通过 Definition 明确输入、输出和质量要求；已有 Definition 满足本合同的优先复用，职责实质变化时更新正式定义及引用。项目特定目标由 Planner 写入 ResearchDesign。执行时由 Resolver 选择满足要求的 Agent 或 Skill。研究内容由 Agent 或 LLM 判断，代码负责确定性的身份、来源、结构、约束校验和数据连接；运行层不另行作科研取舍。

已定义为独立项目研究任务的职责，分别通过正式 ExecutionDecision 和 WorkUnit 执行并接受结果。一个任务可有多个结果字段或内部技术步骤，但不能以减少调用为由顺带完成并标记其他独立任务。未经过相应正式执行或合法复用检查的内容，不计入下游任务完成状态。

职责、输入来源和产物要求以正式合同为准，测试据此判断正确行为。结构校验只证明结构合规；研究结果还须满足对应的科研要求。节点数量、文件数量、调用成功或流程走完，均不能替代这些要求。

本版替代此前 OT Workflow 设计说明和候选稿中的职责、结构与运行规则；产品、能力、资料整理及通用机制继续遵循各自正式合同。定稿表示目标设计确定，不表示仓库配置、代码和真实运行已完成对齐。
