# Dev: 提交 Bug / 需求到飞书底表

## When to use

用户要把 Bug、需求、改进建议登记到飞书「需求及 Bug 管理 底表」。本 skill 的目标不是把用户的话原样搬进表，而是产出**后续人员能够直接评估、实施和验收**的条目——复现清楚、期望行为明确、带根因信号。典型触发：

- 用户列了几个 bug，说"加到表里" / "提上去"
- 用户描述一个需求想法，要进需求管理表
- 用户要修改某条记录的优先级、状态、修复版本

## 为什么要补全（行动性原则）

写进表的条目应让后续评估、实施和验收无需重新猜测问题本体。重点字段包括：

- **标题**（`Bug 名称` / `需求名称`）→ 清楚标识问题或需求
- **优先级**（`优先级`）→ 决定处理顺序
- **5 个长文本字段**（见下表）→ 提供实施与验收所需事实

所以**缺复现、缺期望行为、缺根因信号**的条目会让后续工作无法可靠收敛。本 skill 的职责就是把这些补齐：

| 长文本字段 | 所在表 | 用途 | 缺了的后果 |
|-----------|--------|---------------|-----------|
| `Bug 描述` | Bug 管理 | 背景与复现步骤 | 无法确认问题如何触发 |
| `理想状态（修复目标）` | Bug 管理 | 验收标准 | 无可核对的完成标准 |
| `错误日志/堆栈` | Bug 管理 | 根因定位线索 | 定位成本高且容易误判 |
| `需求描述` | 需求管理 | 背景、方案与**验收清单** | 需求本体和验收范围不明 |
| `需求理由` | 需求管理 | 非目标（界定范围） | 范围失控 |

## 必备字段清单（行动性诊断用）

诊断 = 逐条对照下表，判断每个承重字段是已有 / 需探索 / 需提问 / 走默认。这是缺口驱动补全的落点。

### Bug 管理

| 字段 | 类型 | 作用 | 缺了怎么办 |
|------|------|------|-----------|
| `Bug 名称` | text（标题） | 分支/PR/spec 名 | **归纳**成 ≤20 字（对象+故障），见「Bug 名称归纳规则」 |
| `Bug 描述` | 长文本 | 复现 | **提问**：让用户说清触发条件、步骤；探索代码确认症状真实 |
| `理想状态（修复目标）` | 长文本 | 验收标准 | **提问**：「修好之后应该是什么样？」——必填，否则无法验收 |
| `错误日志/堆栈` | 长文本 | 根因线索 | 用户给了日志→原文粘全；没给→**探索**给疑似 `文件:行` 提示（标注疑似） |
| `优先级` | 单选 | 处理排序 | **默认** `P2-一般`；阻塞类提升。必须取 `P0-阻塞/P1-严重/P2-一般/P3-建议/P4` 之一 |
| `状态` | 单选 | 生命周期 | **默认** `未解决`；关闭后更新为 `已关闭` |
| `Bug 类型` | 单选 | 分类 | **默认**：界面/交互→`界面问题`；按钮/流程/逻辑→`逻辑问题` |
| `对应模块` | 单选/多选 | 提示 | **探索**代码后填准：前端/后端/Agent/Skill/OpenAIR |
| `修复版本` | 单选 | 迭代 | **默认** `v0.8 Public Alpha` |

### 需求管理

| 字段 | 类型 | 作用 | 缺了怎么办 |
|------|------|------|-----------|
| `需求名称` | text（标题） | 分支/PR/spec 名 | **归纳**成 ≤20 字 |
| `需求描述` | 长文本 | 需求本体（背景/方案/**验收清单**） | **提问+探索**：说清要什么 + 现状 + 验收清单；按「需求补全模板」补全 |
| `需求理由` | 长文本 | 非目标（界定范围） | **提问**：为什么 + 场景 + 非目标；按「需求补全模板」补全 |
| `迭代版本` | 单选 | 规划信息 | 新需求默认 `未定` |
| `状态` | 单选 | 生命周期 | 默认 `待讨论`；明确启动后更新为 `待启动`，再按实际进展更新 |
| `需求类型` | 单选 | 分类 | **默认** `新需求`；改造现有→`改进`；体验类→`体验优化` |
| `对应模块` | 单选/多选 | 提示 | **探索**后填准：前端/后端/Agent/OpenAIR/Skill |
| `优先级` | 单选 | 排序 | 同 Bug，取 `P0-阻塞/P1-严重/P2-一般/P3-建议/P4` 之一 |

## 标准流程（主动补全）

### 1. 判表 + 去重

按用户语境判表：bug/异常→Bug 管理；需求/想法/建议→需求管理。lark-cli **没有服务端搜索**，写前先 `+record-list` 按标题在内存比对，避免重复建条：

```bash
lark-cli base +record-list --base-token "<base_token>" --table-id "<table_id>" --as user --format json --limit 200
```

返回是列式结构（`data.fields` / `data.record_id_list` / `data.data`），按列重组后比标题；命中重复就走 `+record-batch-update` 补字段，而不是新建。

### 2. 行动性诊断

对照「必备字段清单」，逐条标出每个承重字段：已有 / 需探索 / 需提问 / 走默认。

### 3. 探索代码确认 + 根因提示

这是本 skill 与「转录」的关键区别。grep / 读代码做三件事：

- **确认症状真实**：用户说的现象在代码/产品里对得上，不是误解。
- **填准 `对应模块`**：基于真实代码归属，不瞎猜。
- **给疑似根因提示**：定位疑似 `文件:行`，作为 hint 写入 `错误日志/堆栈`（bug，用户没给真实日志时）或追加到相关长文本字段，**必须标注「疑似（collector 探索，未确认）」**。

> 别越界成"方案"：只给"哪里看起来可疑 + 为什么"，不给改法。完整诊断是下游 agent 的活。

### 4. 缺口驱动提问

只问诊断出来「缺、且探索也补不上」的字段——典型是复现、期望行为（`理想状态（修复目标）`）、真实日志、需求理由。用 `AskUserQuestion` 一次性把缺的几项问清，**不要为每条都跑固定问题集，也不要缺了就放弃**：

> 用户没说清时：用 `AskUserQuestion` 请用户提供复现 / 期望行为 / 日志，不要直接放弃。

（复用仓库惯用语，见 `dev-review/SKILL.md`。）

### 5. 归纳标题 + 填默认

- 标题归纳成 ≤20 字（对象+故障），见「Bug 名称归纳规则」。
- 优先级 / 模块 / 版本 / 状态 / 迭代版本 走「必备字段清单」的默认；优先级务必取 P0–P4。

### 6. Gate 核对 → 写入

先过「Gate: 行动性达标」，全绿再写。写前**必读字段结构**（不凭记忆，字段名/类型/可选项会变）：

```bash
lark-cli base +field-list --base-token "<base_token>" --table-id "<table_id>" --as user
```

批量建（单批 ≤200 条）：

```bash
lark-cli base +record-batch-create --base-token "<base_token>" --table-id "<table_id>" --as user --json '{
  "fields": ["字段名1", "字段名2"],
  "rows": [["值1", "值2"]]
}'
```

局部更新（改优先级 / 状态 / 补字段）用 `+record-batch-update`，同一份 patch 批量打到一组 record_id（**原子操作**，一个字段/选项写错整批失败）：

```bash
lark-cli base +record-batch-update --base-token "<base_token>" --table-id "<table_id>" --as user --json '{
  "record_id_list": ["recXXXXX"],
  "patch": {"优先级":"P1-严重"}
}'
```

## 字段类型映射坑点（必读）

飞书表不同字段的 CellValue 写入格式不同，写错报 `1254015` 或被忽略：

| 字段类型 | 写入格式 | 示例 |
|---------|---------|------|
| 文本 `text` | 字符串 | `"Bug 描述"` |
| 单选 `select`（multiple=false） | 字符串 | `"P2-一般"` |
| 多选 `select`（multiple=true） | **字符串数组** | `["前端","后端"]` |
| 人员 `user` | 对象数组 | `[{"id":"ou_xxx"}]`（open_id 用 `lark-cli contact +search-user` 查） |
| 附件 `attachment` | 不要用 record 写 | 走 `+record-upload-attachment`；且附件到不了下游 agent，关键信息要转写成文本 |
| 系统字段（created_at 等） | 不可写 | 跳过 |
| `formula` / `lookup` / `group_chat` | 只读 | 跳过 |

**多选字段一定要包成数组**——最常见的坑，当字符串写会失败或只写一个值。

## 名称归纳规则

用户口语往往很长，直接当标题体验差。归纳成 ≤20 字：

**Bug**：
- **去掉"用户体验不好"等结论性修饰词**——症状不是名称
- **保留对象 + 故障**：如"消息输出完后对话框立即收回"、"过长消息不渲染 Markdown"
- **保留动词 + 目标**：如"对话创建计划时多余按钮未隐藏"

**需求**：
- **用"动作 + 对象"，去掉"支持 / 可以 / 能够"等弱动词外套**：如"输入框可扩大"、"项目重命名"、"产物版本管理与回退"，而非"支持输入框扩大"、"用户可以重命名项目"。
- **术语对齐到代码语义**：用户说的"项目"=task、"会话"=session——标题用代码语义，下游 agent 更易检索定位。

注意：标题要归纳；但 `Bug 描述` / `错误日志/堆栈` / `需求描述` / `需求理由` 等**长文本字段要按原文保留**，别截别归纳——两件事别混。

## 需求补全模板（行动性结构）

需求条目天然容易写成"一句话想法"，下游 agent 拿到后既不知现状、也不知范围。新需求 / 改进 / 体验优化类条目，`需求描述` 与 `需求理由` 都按下表结构补全——**先保留用户原文，再追加结构化内容**（长文本字段下游 verbatim 读取，覆盖原话会丢信息）。

**`需求描述`（喂 spec 背景 / 方案）：**

```
【原描述】
<用户原话，原文保留>

【现状（已读源码）】
<探索代码确认的当前行为 / 现有能力 / 缺口；带 file:line；确认是缺口要写明"目前不支持"，别让 agent 误以为已实现>

【目标 / 方案】
<要做成什么样；多种实现可选时列 A/B/C 并标"建议优先 X"，但不越界成最终方案——方案是下游 agent 的活>

【涉及位置】
<前端 / 后端 file:line 落点；纯前端体验优化注明“不涉后端”>

【验收清单（reviewer 可逐条核对）】
<逐条、可观察、可核对的验收项；每条一个明确动作或可判定结果，复杂/多阶段需求按阶段分组。这是下游 reviewer 判定 loop 是否收敛的依据——缺了 reviewer 无可核对项、loop 不收敛。简单需求 3-5 条，复杂需求覆盖每个目标点。>
```

**`需求理由`（喂 spec 非目标 / 范围界定）：**

```
【原理由】
<用户原话，原文保留>

【为什么 / 场景】
<解决什么具体场景；不放空话>

【非目标 / 范围界定】
<明确不做什么，如"只改 X 不动 Y"、"不引入 Z"、"不强制唯一"——防止范围失控的关键>
```

> Bug 的「复现 / 验收 / 根因」对应需求的「现状 / 目标+涉及位置 / 非目标」，需求【验收清单】对应 Bug 的「理想状态（修复目标）」验收标准——同一套行动性逻辑，字段名不同而已。`需求类型=技术讨论` 可酌情简化，但【现状】+【非目标】+【验收清单】仍要有。

## Pre-checks

1. 判表：Bug 管理 vs 需求管理（bug/异常→Bug；需求/想法/建议→需求）
2. 读对应表字段结构（`+field-list`），不凭记忆写
3. `+record-list` 按标题去重，避免重复建条
4. 长文本字段按用户原文填全、不截断不归纳（下游 verbatim 读取）
5. 状态与迭代版本反映当前实际进展：bug 默认 `未解决`；新需求默认 `迭代版本=未定`、状态 `待讨论`
6. 优先级取 `P0-阻塞 / P1-严重 / P2-一般 / P3-建议 / P4` 之一
7. 附件中的关键信息已转写为文本

## Gate: 行动性达标

写入前逐项确认：

- [ ] 标题 ≤20 字，对象+故障清晰
- [ ] Bug：`Bug 描述`（复现）非空；`理想状态（修复目标）`（验收标准）非空；`错误日志/堆栈` 有真实日志 **或** 探索得到的疑似根因提示
- [ ] 需求：`需求描述` 含【现状+目标+验收清单】（不能只是一句空话；验收清单逐条可核对，是 loop 收敛依据）；`需求理由` 含【场景+非目标】；详见「需求补全模板」
- [ ] 优先级为 P0–P4 之一
- [ ] pickup-filter 字段设对（bug `状态=未解决`；需求 `迭代版本=未定` 且 `状态=待启动`）
- [ ] 附件关键信息已转写为文本；去重已做；未写 loop 自管字段
- [ ] 已读 `+field-list`，cell 类型 / 单选多选写法无误

**全部确认后再写入。** 若信息实在补不全（用户答不出、代码也定位不到），把条目建上但在 `Bug 描述` / `需求描述` 末尾注明 `information_insufficient: <缺什么>`，让下游 agent 有据可停，而不是裸条目进去卡死。

## 输出

- **创建**：返回 `record_id_list` + 简表（编号、标题、类型、模块、优先级）。
- **更新**：返回 record_id 与更新字段新值。
- 额外说明：本次探索得到的根因提示、向用户追问了什么、走了哪些默认值——便于后续追溯。

如果用户后续要批量调整（全部提升优先级、改修复版本），直接基于返回的 record_id 列表走 `+record-batch-update`。
