# Skill 与模型任务设计

用于：

- 新建或重构 Skill；
- 调整模型输入、输出或 Schema；
- Skill 职责越来越重；
- 上下游可以跑通，但用户价值不清楚；
- 模型调用过重、过慢或输出大量低价值内容；
- 快速检查一个现有 Skill 是否设计合理。

## 核心原则

> **Skill 从人的真实需求出发，只承担价值链中一个清晰、必要的专业职责。**

设计顺序：

**人的需求 → 用户最终判断或行动 → 必要专业工作 → Skill 职责 → 上下游边界 → 模型输入输出 → 代码确定性组装**

---

## 1. 先确认这个 Skill 为什么值得存在

先看人的需求。

明确：

- 最终用户要解决什么问题；
- 最终需要作出什么判断或行动；
- 当前 Skill 对这个结果有什么必要贡献。

用户不一定直接看到 Skill 的输出。

中间 Skill 可以服务下游，但它的存在价值必须能够追溯到最终用户结果。

上下游都依赖某个字段，只能说明系统内部存在依赖，不能单独证明它对用户有价值。

---

## 2. 划清 Skill 的职责和上下游边界

一个 Skill 只承担一个清晰的主要专业职责。

尽量能够一句话说明：

> **根据什么，完成什么专业工作，为后续什么判断提供支持。**

同时明确：

- 上游必须提供什么；
- 当前 Skill 负责什么；
- 结果直接给谁使用；
- 下游继续完成什么；
- 哪些工作属于其他 Skill 或系统模块。

用户价值决定 Skill **为什么存在**。

上下游关系决定 Skill **做到什么程度**。

职责持续扩张、需要同时完成多个专业判断时，优先重新检查边界。

---

## 3. 设计模型的最小判断闭环

只围绕当前 Skill 的职责设计模型任务。

### 输入

模型优先读取：

- 当前判断直接需要的事实；
- 关键约束；
- 必要上下文；
- 重要冲突；
- 影响判断的不确定性；
- 必要的稳定引用。

完整上游产物、重复事实、展示信息和运行元数据按实际需要进入模型。

### 输出

模型优先输出：

- 当前专业判断；
- 判断依据；
- 关键冲突；
- 适用边界；
- 重要不确定性；
- 当前职责真正需要的建议。

每项主要输出都应有实际用途。

### Schema

每个需要模型填写的字段都检查：

- 是否真的需要专业判断；
- 是否有人或下游实际使用；
- 是否会影响后续有效工作；
- 是否可以由代码确定恢复。

避免为了结构完整要求模型生成大量低价值占位结果。

---

## 4. 划清模型、代码和正式事实

模型负责需要专业推理的工作，例如：

- 科学解释；
- 证据判断；
- 机制分析；
- 研究方向；
- 假说；
- 专业取舍和不确定性判断。

代码负责可以唯一确定的工作，例如：

- ID；
- 数值；
- 单位；
- 来源；
- 引用关系；
- 固定字段；
- 确定性统计；
- 正式结构组装。

完整正式事实保存在系统中。

模型每次只读取当前任务需要的事实视图。

输入减小不等于事实减少。

模型无需重复抄写系统已经知道的确定性内容。

---

## 5. 控制复杂度、易用性和真实成本

一个好的 Skill 应该专业能力足够，同时容易理解、调用和维护。

检查：

- 输入是否容易准备；
- 调用方是否需要理解过多内部结构；
- 必需条件是否合理；
- 输出是否容易直接使用；
- 是否存在大量低价值字段；
- 模型调用次数是否合理；
- 实际请求是否异常膨胀；
- 增加的复杂度和成本是否带来相应价值。

性能分析以真实模型请求为准，重点看：

- 最终输入大小；
- Schema 实际开销；
- 模型调用次数；
- 输出大小；
- 模型耗时；
- 总耗时；
- 有效专业结果。

性能优化同时保护专业判断质量和最终用户价值。

# 快速检查一个 Skill

拿到一个现有 Skill，可以先问 6 个问题。

### 1. 有价值吗？

能否说清：

- 最终帮助什么人；
- 解决什么问题；
- 改变什么判断或行动。

说不清时，先检查 Skill 是否值得存在。

### 2. 职责清楚吗？

能否一句话说清：

> 根据什么，完成什么专业工作，为后续什么判断提供支持。

同时检查是否顺手承担了上下游职责。

### 3. 输入合理吗？

模型读取的内容是否真正服务当前判断？

重点检查：

- 整包上游产物；
- 重复事实；
- 无关上下文；
- 运行元数据；
- 为了保险全部塞入的信息。

### 4. 输出有用吗？

每项主要输出是否：

- 有明确使用者；
- 有实际用途；
- 会影响后续工作。

重点检查大量占位字段、重复事实和下游不用的输出。

### 5. 模型用对了吗？

模型是否主要承担专业判断？

身份、来源、数值、单位、固定结构等确定性工作是否由代码处理？

### 6. 值得这么复杂吗？

当前：

- 输入准备成本；
- Schema 复杂度；
- 模型调用次数；
- 模型成本；
- 使用难度；

是否与它创造的专业价值匹配？

---

## 快速判断

**第 1～2 项说不清：**

优先重新检查 Skill 的价值和职责。

**第 1～2 项成立，第 3～6 项有明显问题：**

Skill 方向基本成立，进入输入输出、职责边界或成本治理。

**6 项都比较清楚：**

设计层基本健康，进入 `07_评测驱动迭代.md` 做真实效果验证。

---

## 设计完成检查

- [ ] 用户问题和最终判断明确。
- [ ] Skill 的必要贡献明确。
- [ ] 职责和上下游边界清楚。
- [ ] 输入只覆盖当前判断需要。
- [ ] 主要输出都有实际用途。
- [ ] 模型和代码职责清楚。
- [ ] 正式事实没有因输入裁剪丢失。
- [ ] 复杂度和真实成本与价值匹配。

通过后进入真实评测。
