# 工程施工与脚本交付规范

> 适用于已经明确施工目标和设计方向，准备修改真实源码、生成施工脚本、运行验证、导出材料或完成集成提交的工程任务。  
> 适用范围包括 OpenAIR、PVD、OT、CS-S 及后续同类工程项目。  
> 目标不是“流程完整”，而是让用户主要负责**执行和裁决**，而不是修脚本、猜路径、拼命令或替交付工具调试。  
> 当前多线并行、演示收敛等高压阶段默认采用**战时模式**：用最短可靠路径拿到高质量结果，真实风险必须守住，形式完整和底层完美不能抢占关键路径。

---

# 一、十六条硬规则

1. **目标和风险决定复杂度。** 优先使用能可靠完成目标的最简单方法；每增加一层脚本、Gate、转换或验证，都必须对应一个真实风险。
2. **只基于当前 Source Truth，并显式锁定施工现场。** 新任务开始前确认仓库、分支、HEAD、远端 Authority、worktree、目标文件和正式生产入口；任何写入工具都必须显式显示并校验自己将要修改的真实 repo root / worktree，不能把目标目录藏在脚本默认值里。
3. **刷新 Source Truth 后，单轮施工要冻结基线。** 任务目标和施工基线确认后，Apply 阶段不持续追逐移动远端；集成前再检查最新远端。
4. **先写短任务合同，再施工。** 明确目标、根因、用户可见改善、允许修改、禁止修改、最小验证和停止条件。
5. **复杂修改才使用结构化施工。** 能直接完成就不用造工具；源码语义修改不用 patch、行号或猜测式替换。
6. **先验证，后写文件。** 所有与本次写入直接相关的结构、范围和语法检查先在内存完成，确认无误后再原子写入。
7. **Git 负责判断工作树和并行集成事实。** 是否存在本地修改由 `git status` / `git diff` 判断；是否存在真实并行冲突由 Git merge / rebase / cherry-pick 的结果判断。不要用整棵 tree、工作树原始字节哈希或“同一文件被别人修改过”替代真实冲突判断。
8. **优先使用仓库自己的执行环境。** 测试和运行使用项目正式采用的 `uv`、npm、Docker Compose 等方式，不用裸系统环境制造伪失败。
9. **测试失败必须先归因。** 相邻职责出现失败时，优先做最小 Before/After A/B；基线已有失败不能算本轮回归，更不能为了“全绿”扩大 WIP。
10. **同类交付工具失败只允许一次探索。** 第二次出现同类失败时，必须删除或绕过失败机制，回到直接 Git / 项目原生命令；禁止继续生成 v2 / v3 / v4 式同类包装层让用户试错。
11. **Apply、Verify、Integrate 分开。** Apply 只负责安全写入；Verify 只验证本轮风险；Integrate 只处理提交前远端关系与安全集成。
12. **用户不是第一轮调试者。** 能在当前环境验证的交付物必须先真实验证；路径、ZIP 内目录、runner、PowerShell 兼容、换行与 Git 状态都应在交付前自证，不能隐藏到用户首次执行里。
13. **战时模式只保留决定结果的硬门。** 只有真实代码冲突、不可替代事实缺失、科研可信风险、会造成错误/误导的回归，才阻塞关键路径。远端前移、tree OID 不同、目标文件被其他线修改但可自动合并、非关键 warning，都不是独立阻塞理由。
14. **完成的改动尽早形成真实 Git commit。** 已验证的施工结果不要长期停留在源码包、patch 或临时目录里；后续并行收敛优先交给 Git rebase / cherry-pick / merge，不从导出源码反向重建 commit。
15. **验证遵守“一次证据关闭”。** 已经通过且未被相关修改触碰的测试不重复跑；组合回归超时就拆分，只继续未覆盖项和失败项，不为了“再确认一次”重跑整套。
16. **达到停止条件就收口。** 用户结果已经可用、关键风险已有直接证据、没有新增回归时立即进入集成；不得为了底层更完美、证据更漂亮、Gate 更完整继续消耗关键时间。

# 0. 先选最短可靠路径

## 0.1 先判断工作模式

默认有两种模式：

- **标准模式**：时间充足，允许为长期维护性增加必要的结构化验证。
- **战时模式**：多线并行、演示收敛、明确时间压力或用户已要求提高效率时采用。

战时模式下，默认执行：

```text
WIP=1
→ 最短可靠施工
→ 最小高价值验证
→ 尽早 commit
→ Git 收敛到最新 test
→ 真实冲突才停
```

战时模式明确禁止：

- 为了追求“理论上更安全”增加没有真实风险对应的 Gate；
- 因远端正常前移反复重打施工包；
- 因整棵 Git tree / 文件哈希 / 旧基线不完全一致阻塞可自动合并的改动；
- 同一交付工具连续失败后继续造下一版包装层；
- 已经 PASS 的测试反复重跑；
- 为了全绿顺手治理与当前用户结果无关的历史红灯；
- 在关键结果已经达到质量底线后继续做底层完美化。

> **战时模式不是降低质量，而是把质量预算集中到真正影响用户结果、科研可信和主链稳定性的地方。**

开始前先回答：

> **完成用户当前目标，最少需要做什么？**

默认按下面的复杂度阶梯选择：

1. **直接命令 / 直接文件操作**  
   适合 1～3 个稳定动作，例如查看状态、复制文件、打包材料、运行单个测试。

2. **短脚本**  
   适合需要重复执行、明确守卫、批量文件处理或避免人工拼接的任务。

3. **结构化施工脚本**  
   适合跨文件源码变换、原子写入、复杂状态校验。

4. **服务 / 集成 / E2E 验证**  
   只有本轮修改真实触及相应运行风险时才增加。

每增加一层复杂度，都必须回答：

> **它具体防止什么失败？删掉这一层，当前任务会失去什么可靠性？**

回答不出来，就不要加。

### 三个减法规则

- **能直接完成，就不要先造工具。**
- **验证只覆盖本轮风险。**
- **辅助证据按消费需求生成，不为形式完整而生成。**

# 1. 锁定 Source Truth，并冻结本轮施工基线

## 1.1 新任务开始前

任何写操作或权威验证前，至少确认：

```text
repo root
branch
HEAD
origin / remote Authority
origin/<branch>
git status
目标文件
正式生产入口
```

多 worktree 时：

- 用 Git 事实确认目标分支绑定的 worktree，不按目录名猜；
- 同时比较本地分支与远端 / 指定 commit；
- 本地落后时，先判断是否需要明确授权的 fast-forward；
- Apply 默认不得自动 `merge`、`rebase`、`checkout`、切分支、`reset`、`clean`。

已有无关修改保持原样；目标文件存在未授权修改时，停止并重新判断。

## 1.2 Source Truth 刷新后要冻结施工基线

一旦本轮已经完成：

```text
最新 Source Truth
→ 问题定责
→ 设计确认
→ 允许修改范围确认
```

就把当前 commit 作为**本轮施工基线**。

推荐顺序：

```text
刷新最新 Source Truth
→ 定责
→ 冻结本轮基线
→ Apply
→ Verify
→ 提交前重新读取远端
→ 安全集成
```

禁止把 Apply 变成：

```text
fetch
→ 发现远端前进
→ 自动重定基线
→ 再修改
→ 再 fetch
```

否则容易进入：

```text
远端前进
→ 旧施工包失效
→ 重打包
→ 远端再前进
→ 再失效
```

### 什么时候允许重新定基线

只有出现以下情况时：

- 目标结构已被最新远端重写；
- 最新远端触碰了本任务目标文件且语义存在冲突；
- 当前 HEAD 已不包含原施工基线；
- 直接相关测试证明行为已经变化。

如果远端只是增加与本任务无关的提交，不自动重做施工设计。

多线并行时还要明确：

- **远端前移本身不是冲突；**
- **同一个文件被另一条线修改过，也不自动等于冲突；**
- 只有 Git 无法自动合并，或自动合并后出现明确语义冲突，才需要重新定基线或人工裁决；
- 不使用“整棵 tree 必须等于旧基线”“所有目标文件 blob 必须完全一致”之类额外守卫替代 Git 的真实冲突判断。

## 1.3 Source Truth 正确，不等于施工现场正确

必须同时确认两类事实：

```text
代码事实：这份源码 / commit 是不是当前 Authority
执行现场：接下来实际写入和验证的是不是目标 worktree
```

多 worktree 场景新增硬要求：

- 用户可见命令显式给出目标 repo / worktree 绝对路径；
- Apply / Verify 开始时打印并校验 `git rev-parse --show-toplevel`、当前 branch、HEAD；
- 工具不得内部静默切换到另一个 worktree，也不得依赖一个用户看不到的硬编码目录；
- 如果 manifest 中的目标文件在当前 repo 不存在，优先判断“现场错了”，不要继续解释成产品代码问题；
- 同一个任务的 Apply、Verify、commit 默认发生在同一目标 worktree；需要切换时必须显式说明原因和新的 Authority。

> **源码包对，不代表写入位置就对。施工前必须把“代码 Authority”和“物理执行现场”同时锁死。**

# 2. 施工前写短任务合同

至少明确：

```text
目标=
根因=
用户可见改善=
允许修改=
禁止修改=
最小验证=
停止条件=
```

要求：

- 只写当前施工真正需要的内容；
- 不为了“完整”加入无关历史；
- 不把候选问题自动变成施工范围；
- 需要改变正式设计、扩大核心职责或突破任务边界时，停止当前施工并重新判断。

---

# 3. 选择可靠的修改方式

优先级：

1. AST、JSON / YAML 解析、明确代码对象等结构化修改；
2. 完整生成职责单一的新文件；
3. 对大型既有文件做精确、可校验的结构化变换。

PowerShell 主要负责编排、调用、路径和环境检查。

复杂源码语义变换优先使用 Python / AST。

禁止：

- `git apply`、`.patch`、unified diff；
- fuzzy / force apply；
- 按行号修改业务代码；
- 用关键词或正则猜业务代码位置后直接替换；
- 从旧仓库整目录覆盖当前仓库；
- 从导出的源码 ZIP / 临时目录通过文本 patch 反向重建生产 commit；
- 为了处理正常并行前移，自造“base tree 完全一致”“所有 blob 完全一致”等全局硬门；
- 为了通过旧测试恢复已淘汰实现；
- 用大量例外分支、兼容层或补丁逻辑掩盖结构问题。

目标结构无法唯一定位时，停止施工。

---

# 4. Apply：先验证，再写入

Apply 的职责只有两个：

1. 确认当前现场仍满足本轮施工前提；
2. 安全写入已经明确的源码修改。

Apply 不负责：

- 自动追远端；
- 自动 merge / rebase；
- 修环境；
- 解释测试失败；
- 启服务；
- 做真实 E2E；
- 自动 commit / push。

## 4.1 写入前

确认：

```text
repo root
.git
branch
HEAD == 本轮冻结基线（或已明确允许的安全后继）
目标文件
目标结构
允许修改范围
当前工作树真实状态
```

任一关键条件不满足，立即停止。

## 4.2 Git 工作树事实由 Git 判断

### 正确的职责分工

- **commit / blob identity**：用 commit SHA / blob OID；
- **工作树是否 dirty**：用 `git status` / `git diff`；
- **payload 自身完整性**：可用 SHA256；
- **staged 范围**：用 `git diff --cached`。

### 不要这样做

不要用：

```text
Git blob bytes SHA
==
Windows working tree file SHA
```

判断工作树是否被修改。

原因：

- Git blob 通常保存 LF；
- Windows 工作树可能按 `core.autocrlf` 转成 CRLF；
- Git 可以正确判断 clean，但原始字节哈希会不同；
- 这会制造“并行修改”的假冲突。

如果确实需要比较 Git 对象内容，使用 Git blob / OID 作为 Git 对象 Authority，而不是拿它和工作树原始 bytes 直接等价。

## 4.3 内存校验

写文件前完成：

- 目标结构检查；
- 修改数量检查；
- 新内容结构检查；
- Python AST / JSON / YAML 等必要语法检查；
- 修改范围检查；
- 其他确定性校验。

> **先验证，后写文件。**

## 4.4 原子写入

单文件：

```text
同目录临时文件
→ 完整写入
→ 最终校验
→ 原子替换
```

多文件：

```text
先生成并校验全部新内容
→ 准备全部临时文件
→ 再正式替换
```

写后校验失败时：

- 恢复本轮修改；
- 或确保不会留下半应用状态。

## 4.5 第二次执行

第二次执行必须：

- 明确识别“已经应用”并安全退出；
- 或安全 no-op。

不得重复插入、重复追加或扩大修改范围。

## 4.6 Apply 成功必须由目标仓库事实证明

Apply 结束时至少确认：

```text
实际 repo root
branch
HEAD
git status --short
本轮预期目标文件确实存在
```

不要只相信工具打印的“写入成功”。

如果 Apply 声称成功，但用户随后在目标 repo 中看不到预期文件或 diff：

1. 先检查是不是写到了别的 worktree；
2. 再检查 payload / manifest 与当前 repo 是否匹配；
3. 在施工现场未确认前，不进入 Verify、commit 或 push。

# 5. Verify：只验证本轮真实风险

Verify 不负责修改生产源码。

验证强度与本轮风险匹配：

- 文档 / 治理资产：结构检查 + 必要 owner 回归；
- 确定性业务代码：专项测试 + 直接相关回归；
- runtime / 数据库 / Provider / 网络 / 用户流程变化：再增加集成或真实运行；
- system-testing-design 已明确层级时，按正式设计执行。

每个测试都要能回答：

> **它在验证本轮什么风险？**

每个没有运行的测试，也要能解释：

> **为什么本轮不需要覆盖那个风险？**

## 5.0 验证账本：通过一次就关闭

验证过程中维护最小事实：

```text
已通过
未覆盖
失败待归因
```

规则：

- 已通过的测试文件或风险点，在相关代码未再次变化时不重复跑；
- 合并批次因时间上限中断时，保留已经完成的 PASS，只续跑剩余项；
- 大回归优先拆成按文件 / 按风险的小组，避免一次超时导致从头再来；
- 新增回归只重跑最小相关测试，修复后再补一个直接相邻回归；
- 全量回归只有在它真的会改变当前集成判断时才运行。

## 5.1 验证依赖 Git 状态时，按真实生命周期验证

有些正式机制会读取 Git tracked / staged 状态，例如 Registry 只接受正式跟踪的定义文件。

这类测试失败时先问：

> **它是在证明产品行为错误，还是仅仅说明当前文件还处于“未进入正式 Git 生命周期”的状态？**

处理原则：

- 如果文件本来就要在下一步 `git add` 后成为正式定义，优先按真实集成顺序暂存本轮明确文件，再运行对应测试；
- 不为了绕过 tracked 约束去修改 Registry；
- 不优先制造临时 index、影子 Git 状态或新的验证层，除非它确实能降低真实风险；
- `untracked_spec`、`untracked_definition` 一类失败，在确认文件内容正确前提下，应先归因为“当前 Git 生命周期状态”，不是直接归因为产品回归；
- 暂存前先验证目标路径全部存在；任一路径缺失，先检查 worktree / repo 是否选错。

# 6. 测试失败先归因，再决定是否施工

测试失败分三类：

## A. 本轮新增回归

特征：

```text
Before: PASS
After: FAIL
```

处理：

- 归入当前 WIP；
- 定位本轮修改直接根因；
- 修复后重跑最小相关测试。

## B. 基线已有失败

特征：

```text
Before: FAIL
After: 同样 FAIL
```

处理：

- 不算本轮回归；
- 不阻塞当前任务；
- 不为了测试全绿顺手改相邻模块；
- 当前 WIP 关闭后再重新排序其价值。

## C. 环境 / 工具失败

例如：

- 缺依赖；
- runner 选错；
- Docker / 数据库不可用；
- 脚本解析错误；
- 临时 worktree / 路径错误。

处理：

- 先确认是否选错正式 runner（例如 OpenAIR API 应优先 `uv run --project services/api ...`）；
- 能用仓库正式环境直接解决时，不先安装另一套临时环境；
- 不解释成产品失败；
- 修正环境后只续跑受影响测试，不重跑已经确认通过的部分。

## 6.1 Before / After A/B 规则

当失败落在相邻职责边界、归因不清时，优先做：

```text
同一测试
+ 同一运行环境
+ 干净施工前基线
```

只要一次最小 A/B 就能判断，不默认跑全量回归。

# 7. 外部工具与正式运行环境

## 7.1 配置声明不等于运行事实

例如：

- Compose 声明端口，不代表当前容器实际发布；
- `.env` 有变量，不代表进程已加载；
- 容器内 ready，不代表宿主机可达；
- Git 有分支，不代表当前 worktree 绑定到它。

正式 Gate 要验证实际效果。

## 7.2 项目执行环境优先

仓库已有正式 runner 时，优先复用。

例如 OpenAIR API 使用：

```powershell
uv run --project services/api ...
```

而不是先运行：

```powershell
python ...
pytest ...
```

再把缺包解释成产品失败。

runner 的选择属于运行 Authority，应从当前仓库事实确认。

## 7.3 原生命令

调用 `git`、`docker`、`python` 等命令时：

- 以 exit code 判断成功失败；
- stderr 有内容不等于失败；
- harmless warning 不阻塞；
- 关键步骤同时检查 exit code + 输出结构 + 实际效果；
- 测试过程中即使已经打印 `N passed`，只要最终被 `KeyboardInterrupt`、异常清理或非零 exit code 中断，就不能把这次运行记为完整 PASS；需要时只重跑最小相关测试，不重跑整套。

---

# 8. 机器可读输出必须保留协议结构

以下输出不能先做通用 `Trim()` / `strip()` / 正则清洗后再解析：

- `git status --porcelain`；
- `git worktree list --porcelain`；
- `git diff --raw -z`；
- Docker / Compose inspect；
- JSON / NDJSON / TSV / 固定列文本。

规则：

1. 标量输出（如 `git rev-parse HEAD`）可以去除首尾换行；
2. 机器可读输出必须先保留原始结构；
3. 不用路径“恰好长这样”等偶然事实补特判；
4. 解析结果再与实际文件 / Git 事实做一次确定性核对。

---

# 9. Git 修改范围校验

如果 Gate 目标是确认“本轮真实改了哪些物理路径”，使用：

- `git diff --no-renames --name-only`
- `git diff --cached --no-renames --name-only`
- 或 `git status --porcelain=v1 -z`

不要让 Git rename / copy 推断改变允许路径集合。

删除旧文件 + 新建 owner 文件时：

- 删除路径和新增路径分别计入允许范围。

提交前确认：

- 所有预期路径已暂存；
- 没有额外 staged 路径；
- 没有残留未暂存的本任务修改。

# 10. 同类工具失败只允许一次探索

如果用户执行后发现是施工工具或验证脚本自身问题：

### 第一次失败

1. 停止产品判断；
2. 定位失败层；
3. 判断这层工具是否真的需要；
4. 能删就删，不能删才修；
5. 修复后必须在与用户一致的路径、runner、PowerShell/Git 状态下先自测成功。

### 第二次同类失败

> **立即判定为交付设计失败。当前会话禁止继续让用户试同类工具。**

此时必须：

- 回到最短原生路径；
- 优先直接 Git / `uv` / Docker / 文件操作；
- 删除不必要的 patch、bundle 包装器、临时转换器、额外 Gate；
- 如果必须保留工具，先在当前环境完整复现成功路径，再交付；
- 不生成 v2 / v3 / v4 / FINAL / FINAL2 式连续试错版本。

### 典型必须降复杂度的信号

出现任一项就优先删工具，而不是继续补工具：

- ZIP 解压路径和脚本调用路径不一致；
- CRLF / LF 导致文本 patch 失效；
- `git apply --3way` 依赖的 base blob 不存在；
- 自造 tree/hash 守卫挡住了 Git 本可自动合并的改动；
- 同一脚本同时负责 Apply、Verify、Rebase、Push，任一小问题导致整条链重来；
- 用户已经连续两次回传的是工具错误，而不是产品/测试错误。

> **交付工具的价值是减少用户工作。只要它开始让用户替 GPT 调试，它就已经失去存在价值。**

---

# 11. 脚本保持单一职责

| 类型 | 主要职责 |
|---|---|
| Apply | 应用明确源码 / 配置修改 |
| Verify | 验证明确代码 / 数据 / 行为 |
| Run | 启动服务或创建真实运行 |
| Collect | 收集已知位置结果 |
| Diagnose | 诊断当前状态 |
| Export | 精准导出任务材料 |
| Integrate | 提交前检查远端关系并安全集成 |

原则：

- 一个脚本通常只承担 1～2 个紧密相关目标；
- Apply 与 Verify 默认分开；
- Verify 不修改生产源码；
- Apply 不自动追远端；
- Integrate 不重新设计业务修改；
- Run / E2E 不顺手修环境或代码。

# 12. Export：先简单，再保证字节安全

Export 的目标是：

> **把验收或新对话真正需要的材料原样交出去。**

不是顺便建设一套证据系统。

## 12.1 导出明确 Git commit / branch

优先使用：

```text
git archive <commit-or-branch>
```

适合：

- 正式提交后的源码包；
- 新对话 Source Truth；
- 指定 commit 独立验收。

## 12.2 导出当前未提交工作区

如果验收对象是当前工作区：

- 使用直接二进制复制 / ZIP；
- 当前已删除的 tracked 文件保持删除；
- 不机械使用 `git archive HEAD`；
- 不经过 `Set-Content` 等会改变编码 / 换行的文本管道。

## 12.3 Git 基线文件

需要 Git 原始 bytes 时：

- `git cat-file`；
- Python `subprocess(..., text=False)`；
- 其他二进制安全方式。

禁止：

```powershell
git show HEAD:path | Set-Content file
```

因为会引入编码 / 换行转换风险。

## 12.4 校验强度与风险匹配

普通源码包：

```text
范围正确
+ 字节安全导出
+ ZIP 可读取
```

通常足够。

只有以下情况再增加逐文件 SHA / blob OID：

- 哈希本身是验收证据；
- 跨层转换；
- 编码敏感文件；
- payload 完整性需要严格证明。

> **Export 首先是交付材料，不是重新实现 Git。**

# 13. PowerShell 与 Python 交付标准

## PowerShell

默认：

```text
Windows PowerShell 5.1
powershell.exe
UTF-8 with BOM
```

交付前必须：

```text
PARSE_ERRORS = 0
```

重点检查：

- here-string；
- 引号；
- 括号；
- 中文 / Unicode；
- PowerShell 5.1 兼容性；
- 交互式粘贴时 `if/else` 等语法是否需要作为完整代码块执行。

复杂外部工具编排出现多层 quoting、正则和 shell 嵌套时，优先下沉到 Python。

### PowerShell 用户执行块

用户终端初始目录、已有变量和上一轮命令状态都视为不可靠。

因此：

- 每个可复制执行块默认自包含：自己定义 `$repo` / `$downloads` / `$delivery` 等必要绝对路径；
- 不依赖上一条回复里残留的 `$delivery`、`$manifest` 或当前目录；
- 交付包版本变化时，先验证目标文件真实存在，再调用；
- ZIP 交付必须先实际列出压缩包根目录结构，并用与用户完全相同的 `Expand-Archive` 目标验证最终脚本路径；
- 不允许一边把 ZIP 解压到 `Downloads` 根目录，一边又假设脚本位于 `$dst\...`；脚本调用路径必须由真实解压结果决定，而不是按包名猜；
- 如果只需要一条稳定命令，优先直接调用已存在文件，不为“看起来完整”再套一层解压/启动脚本；
- 会发生写入、commit、rebase、push 的长序列，不要依赖交互式 PowerShell 中前一段 `throw` 自动阻止用户继续粘贴后续段；
- 要么拆成“Apply / Verify / Integrate”三个独立执行块，要么把同一阶段包在一个真正的脚本块 / `.ps1` 中，并确保失败后该阶段整体停止；
- 用户不应在一次失败后还看到后续“继续 commit / fetch / push”的命令等待执行。

> **失败必须让流程真的停，不只是打印一句“停止”。**

## Python

仓库内 Python 任务优先通过当前项目正式 runner 启动。

源码变换 / 验证编排脚本交付前至少完成：

- 语法检查；
- 关键解析函数确定性自检；
- 真实文件路径验证；
- 常见失败路径验证；
- 能在当前环境真实运行的成功路径至少跑一次。

# 14. 应用后先看真实 diff

Apply 完成后，不先看“脚本说成功”，先看 Git 事实：

```powershell
git status --short
git -c core.whitespace=cr-at-eol diff --check
git diff --stat
git diff
```

确认：

- 修改范围正确；
- 没有无关文件；
- 没有临时调试代码；
- 没有编码 / 换行问题；
- 正式合同没有被意外改变。

对于新增 untracked 文件，注意：

```text
git diff --name-only
```

默认不会显示它们。

因此修改范围判断必须结合：

```text
git status --short
```

# 15. Integrate：提交前再检查最新远端

本轮 Verify 通过后，再进入 Integrate。

推荐顺序：

```text
确认当前 repo / worktree
→ 验证本轮目标路径全部存在
→ git add 明确目标文件
→ git diff --cached --check
→ git diff --cached --stat
→ commit
→ fetch 最新远端
→ 判断远端关系
→ 无冲突则安全收敛到最新 test
→ push
```

规则：

- 不 force push；
- 如果最新 `origin/test` 仍是当前 commit 的祖先，可以直接 push；
- 如果 `origin/test` 只是被其他施工线前进，而本任务已经形成独立 commit、工作区 clean，可以在 **Integrate 阶段**执行标准 `rebase origin/test`；
- **同一文件被远端修改过不等于冲突。** 先让 Git rebase / cherry-pick / merge 判断；Git 能自动合并就继续；
- **禁止使用整棵 tree OID、全仓文件哈希、旧基线完全一致作为并行集成前置硬门。** 这些只能作为诊断信息，不能替代真实合并结果；
- Git 能无冲突完成 rebase 时，不因“远端前进”本身停工；只重跑一个最直接、能覆盖本轮接线风险的高价值测试，然后 push；
- rebase / cherry-pick 一旦出现真实代码冲突，立即 abort 并停止自动集成，由总控判断；
- 已安全形成的本地 commit 保留，不 reset / clean 掉；
- Apply 阶段仍禁止自动追远端或 rebase；允许 rebase 只属于已完成施工后的 Integrate 收敛动作。

> **并行施工的目标是尽快收敛到最新 `test`。无冲突就收敛，有冲突才停。**

# 16. 权威真实运行前再确认

如果本轮需要真实运行 / E2E，执行前确认：

```text
正确 repo 和 HEAD
当前 worktree 状态
运行服务实际加载的代码版本
build / recreate 状态
health
Provider / 关键配置
实际端口
网络可达性
真实数据位置
新的 run_id
```

权威结果必须来自本轮新运行。

旧容器、旧缓存、旧 Run、旧日志只作参考。

# 17. 失败分层

## A. 交付工具问题

例如：

- Parser；
- 路径；
- 编码；
- CRLF / LF；
- Source Truth Gate；
- Git / PowerShell 调用；
- 导出脚本；
- 施工器状态判断。

处理：

> **先修交付工具，不解释成产品失败。**

同类第二次失败时，优先降低复杂度。

## B. 环境问题

例如：

- Docker daemon；
- 数据库；
- Provider；
- 网络；
- 正式 runner 缺失。

处理：

- 先确认环境 Authority；
- 再判断任务是否允许修环境。

## C. 产品 / 测试问题

只有：

```text
交付工具正确
+
必要环境正确
```

之后，才进入正式产品判断。

# 18. 四个 Gate

四个 Gate 是风险检查清单，不是为了追求形式完整的审批流程。

## 18.0 战时模式下的四个真正硬门

战时模式只保留以下四个会改变结果的阻塞条件：

1. **施工现场错了**：repo / worktree / branch / Source Truth 明确不对；
2. **写入范围失控**：出现未授权文件、无法解释的 diff、生产代码被意外覆盖；
3. **本轮真实回归**：直接相关测试 Before PASS / After FAIL，或结果会误导用户；
4. **真实集成冲突**：Git 无法自动收敛，或自动合并后存在明确语义冲突。

除此之外，默认继续推进：

- 远端前移；
- tree OID 不同；
- 同一目标文件被其他线修改但 Git 可自动合并；
- 基线已有红灯；
- 非关键 warning；
- 已经关闭风险的重复验证需求。

> **Gate 的职责是挡错误，不是挡进度。**

## Gate A｜施工前

- [ ] repo、branch、HEAD、远端 Authority、worktree 已确认；
- [ ] 最新 Source Truth 已读取；
- [ ] 本轮施工基线已冻结；
- [ ] 目标文件与正式入口来自当前源码；
- [ ] 目标、根因、允许 / 禁止修改范围明确；
- [ ] 最小验证和停止条件明确。

## Gate B｜Apply 交付前

- [ ] 修改方式足够简单且可靠；
- [ ] 前置检查和新内容校验在写入前完成；
- [ ] 不会留下半应用状态；
- [ ] 第二次执行安全 no-op；
- [ ] PowerShell Parser Error = 0（如适用）；
- [ ] Python 语法 / 关键自检通过（如适用）；
- [ ] Git 工作树事实使用 Git 判断，没有使用 blob-vs-working-tree 原始哈希误判；
- [ ] 原生命令以 exit code 判断；
- [ ] Apply 没有混入自动 fetch / merge / rebase / 环境修复 / E2E。

## Gate C｜Verify / 交付前

- [ ] Apply 已在隔离副本或等价环境真实成功执行；
- [ ] diff 和必要语法检查通过；
- [ ] 专项测试覆盖本轮真实风险；
- [ ] 失败已区分新增回归 / 基线已有 / 环境工具问题；
- [ ] 相邻失败必要时已做最小 Before/After；
- [ ] 正式 runner 已使用；
- [ ] 用户拿到一条可直接执行的命令；
- [ ] 无理由的 Provider / E2E / 全量回归没有叠加。

## Gate D｜集成 / 真实运行前

- [ ] staged 路径与预期一致；
- [ ] commit 已形成；
- [ ] 最新远端关系已重新检查；
- [ ] 未使用 force push；
- [ ] 如需真实运行，运行环境已加载最新代码；
- [ ] health、Provider、端口、网络、数据位置真实成立；
- [ ] 权威结果来自本轮新运行。

# 19. 给用户的交付标准

每次交付至少让用户明确知道：

```text
本轮目标
当前 Source Truth / 冻结基线
要执行什么
成功时看什么
失败时只需回传什么
下一步是什么
```

用户不需要自己：

- 猜脚本路径；
- 猜当前到底应该在哪个 worktree 执行；
- 修改脚本变量；
- 依赖上一轮 PowerShell 会话里残留的变量；
- 拼大量命令；
- 修脚本语法；
- 判断 warning 是否可忽略；
- 猜服务端口；
- 为施工工具临时改正式环境；
- 反复导出源码来帮助 GPT 调试交付脚本；
- 连续执行多个“修正版”“最终版”交付工具来替 GPT 做探索；
- 判断整棵 Git tree / base blob / CRLF 等底层集成细节是否可忽略；
- 在已知多线并行场景中替 GPT 判断“同文件修改”是否等于真实冲突。

用户可见命令还应满足：

- 默认从任意当前目录可运行；
- 明确写出目标 repo / worktree；
- 执行前验证关键文件 / manifest / runner 存在；
- 失败后不继续展示或执行后续破坏性阶段；
- 成功时给出最少但足以核查的 Git 事实：HEAD、branch、`git status --short`。

# 20. 战时模式下必须避免的重复浪费

以下问题在高压并行施工中最容易反复消耗时间，后续一律按这里处理。

## 20.1 远端前移导致反复重打包

错误模式：

```text
施工完成
→ origin/test 前移
→ 旧包判失效
→ 重做包
→ origin/test 再前移
→ 再重做
```

正确做法：

```text
冻结施工基线
→ 完成并验证
→ 尽早形成真实 commit
→ Integrate 阶段 rebase / cherry-pick 到最新 test
→ Git 无真实冲突就继续
```

## 20.2 用“更严格”代替“更正确”

以下都不能单独成为阻塞理由：

- base tree OID 与历史值不同；
- 全仓文件 hash 不完全一致；
- 同一文件被别的施工线修改；
- Windows 工作树字节与 Git blob 字节不同；
- 远端比施工开始时多了若干提交。

它们可以触发检查，但最终 Authority 是：

> **真实 diff + 真实测试 + Git 真实冲突。**

## 20.3 交付工具比施工本身更复杂

当施工逻辑已经完成，而大量时间耗在：

- patch 是否能 apply；
- ZIP 根目录在哪里；
- wrapper script 路径；
- CRLF / LF；
- bundle / base tree 守卫；
- 第四版、第五版集成脚本；

说明工具已经反客为主。

此时直接回到项目原生命令，不再优化包装器。

## 20.4 为了全绿扩大 WIP

看到相邻红灯时：

1. 先做一次最小 Before/After；
2. 基线同样失败 → 记录，不阻塞；
3. 当前修改新引入 → 才进入 WIP。

不因为“既然看到了”就顺手修。

## 20.5 重跑已经通过的东西

已经有直接 PASS 证据后：

- 不因组合批次超时而从头再跑；
- 不因远端无关前移而重跑全部；
- 不因“想更放心”重复跑同一风险；
- 只在相关代码再次变化时重新打开该验证。

## 20.6 追求完美挤占产品关键路径

当以下条件已经满足：

- 用户核心结果可用；
- 科研可信底线满足；
- 关键链路没有新增回归；
- 并行集成没有真实冲突；

当前任务应收口。

剩余优化进入后续排序，不用“这次顺便做到最完美”。

# 21. 最终标准

> **可靠不是复杂。优先用最短、最直接、足以覆盖真实风险的方法完成目标。**

> **Source Truth 要及时刷新，但单轮施工必须有稳定基线；不要一边施工一边追逐移动目标。**

> **Git 负责 Git 工作树事实，测试负责行为事实，设计合同负责产品边界；不要让自造 Gate 取代这些 Authority。**

> **基线已有失败不是本轮回归；只有新增失败才需要当前 WIP 负责。**

> **同类工具第二次失败时，优先删掉复杂度，而不是继续生成下一版工具。**

> **Source Truth、目标 worktree、Git 生命周期状态是三类不同事实；任何一类弄错，都可能制造假失败或把代码写到错误现场。**

> **并行线集成以“无冲突就快速收敛、有冲突才停止”为原则；不要把远端前进本身当成阻塞。**

> **用户负责执行、观察真实结果和做重要裁决；GPT 负责把施工与验证工具本身做到安全、准确、清楚、可核查。**

> **战时模式下，真实风险优先于形式完整，最高时间价值优先于底层完美。**

> **停止条件一旦满足就收口；继续优化必须有新的用户价值或真实风险作为理由。**
