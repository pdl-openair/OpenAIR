# Review 与验收规则

## 1. 文档作用

本文用于约束 OpenAIR 的 PR Review 和任务验收。

目标不是增加流程负担，而是避免多人和 AI coding 并行开发时出现边界不清、字段不一致、功能不可验收的问题。

## 2. PR 必须说明

每个 PR 至少说明：

- 本次改了什么；
- 本次没有改什么；
- 修改了哪些文件；
- 是否改动业务代码；
- 是否影响前后端共享类型；
- 是否影响 API 契约；
- 是否影响 fixtures；
- 是否影响 Skill registry；
- 是否影响 `.claude/skills/`；
- 如何本地验收；
- 是否存在未完成项。

## 3. Review 重点

Review 时优先看：

- 是否符合 task spec；
- 是否越界修改无关文件；
- 是否写死材料、计算机或 OpenTrajectory 专用逻辑；
- 是否破坏任务状态、产物、能力调用记录等核心契约；
- 是否新增无用架构占位；
- 是否同步必要文档；
- 是否影响 fixtures 或测试样例；
- 是否给出清楚的验收方式。

## 4. 前端验收

前端任务至少检查：

- 页面是否符合四个核心页面职责；
- 是否把场景流程写死进通用页面；
- 是否能使用 fixtures 展示；
- 是否正确展示任务状态；
- 是否正确展示阶段结果；
- 是否有产物入口；
- 是否有能力调用记录入口；
- 是否能处理空状态、失败状态和加载状态。

## 5. 后端验收

后端任务至少检查：

- API 是否可调用；
- 状态流转是否清楚；
- 错误是否结构化返回；
- 是否写入任务记录；
- 是否写入能力调用记录；
- 是否写入产物记录；
- 是否影响共享类型；
- 是否有最小验收方式。

## 6. Skill 验收

Skill 相关任务至少检查：

- 是否位于 `skills/` 源目录；
- 是否有 `SKILL.md`；
- 是否有 `skill.yaml` 或等价 metadata；
- 是否说明适用阶段和领域；
- 是否有输入输出说明；
- 代码型 Skill 是否说明脚本入口和依赖；
- 是否提供可回放样例或说明暂不提供的原因；
- 是否需要同步到 `.claude/skills/`；
- 是否需要更新 registry。

## 7. Fixtures 验收

fixtures 相关任务至少检查：

- 是否说明样例来源；
- 是否是流程级样例或 recorded run；
- 是否包含任务状态；
- 是否包含阶段结果；
- 是否包含能力调用记录；
- 是否包含产物引用；
- 是否能被前端或后端读取；
- 是否避免把普通随手 mock 当作正式流程样例。

## 8. Claude SDK 接入验收

Claude SDK 相关任务至少检查：

- 后端是否能发起 SDK 调用；
- 请求结构是否可追踪到 task_id / run_id；
- 返回结果是否结构化；
- 是否写入任务状态；
- 是否写入能力调用记录；
- 是否写入产物记录；
- 失败时是否记录失败原因；
- 是否没有把密钥、内网地址或敏感配置写入仓库。

## 9. 文档验收

文档任务至少检查：

- 是否有明确作用；
- 是否和现有文档重复；
- 是否过长；
- 是否能指导开发或验收；
- 是否避免空泛描述；
- 是否标明当前不做什么；
- 是否放在正确目录。

## 10. 合并前检查

合并前至少确认：

- PR 有清楚说明；
- 文件改动范围合理；
- 必要文档已同步；
- 不确定内容已标 TODO；
- 没有提交密钥、真实 token、私有接口地址；
- 没有无关格式化大改；
- 没有破坏当前可运行骨架；
- AI 协作的 commit 已加 `Co-authored-by` 标记。

## 11. 不适用项

如果某项验收不适用，应在 PR 中标注：

```text
N/A：原因
````

不要直接忽略。
