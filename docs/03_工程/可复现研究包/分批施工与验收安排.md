## 3. 协议升级必须覆盖的情景

`spec_version` 是协议版本，`version` 是 Package 内容版本，应用版本/数据库迁移版本另记，不能混用。以下稳定原则来自正式合同及 C-review；未定项在批次 0 决定，不能由不同 writer 各自发明策略。

| 情景                                             | 处理要求/当前决定状态                                                                                               | 实现与验收归属                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 已发布 v2 的读取、查看、导出                     | 保留原文、内容身份、哈希和旧语义；不能换版本常量后使旧包失读                                                        | T1/T2/T4/T9                                                  |
| 新用户导入 v2，或既有路径新建 v2                 | 保留既有受支持行为作为兼容基线；新的产品贡献入口形成 v3。是否限制某旧入口必须在批次 0 明确，禁止偷偷删除旧能力      | T1/T2/T3                                                     |
| 已发布 v2 要升级为 v3                            | 不自动补造对象/验证/来源。需要补科研语义时形成待确认内容；原发布版本不改写，升级发布使用新内容版本                  | T1/T3；升级操作是否首轮提供，在批次 0 定，非必建独立转换工具 |
| v2 信息不足以合法形成 v3                         | 保留原包/草稿与诊断；指出必需缺口；不能用默认值伪造、改标签装成 v3                                                  | T1/T3/T4                                                     |
| 旧 v2 已被历史确认方案采用                       | 既有采用身份、内容和确认记录保持；新版本不能静默替换                                                                | T2/T5/T9                                                     |
| 现在新研究选择采用 v2                            | 用户已确认按真实提供内容受限复用；确需缺失信息才补齐新版本或正式核验，不强制一律升级，不假装v2具有v3语义 | T5，协议/资产层不得自行扩大禁用范围                          |
| 已发布 v3 内容修订                               | 新内容版本，旧版本不可变；同 id+version 的不同内容应冲突，不覆盖；版本标识格式与分配沿实际合同                      | T2/T3/T5                                                     |
| 不支持的未来协议、漏版本或非法类型               | 明确拒绝正式使用，保留原始输入与诊断；不能猜版本或静默按 v3 解析                                                    | T1/T2/T4                                                     |
| v3 必需字段/确定性引用非法                       | 整份不成为合法 Package，不删坏项后仍当同一版本使用                                                                  | T1/T2/T3                                                     |
| 合法包的来源或资源临时不可访问                   | 保留合法内容，标出受影响范围；不将暂不可访问误作结构非法，也不造当前核验结果                                        | T4/T6                                                        |
| 服务、数据库、客户端升级进度不一致               | 准备兼容发布顺序和支持能力核对；用户可能到达的链路未支持前不能宣称 v3 可用。旧客户端遇不支持版本明确反馈            | T2/T4/T9                                                     |
| 应用/数据库回退时已有 v3 资产或采用记录          | 不删除或降级已发布数据；评估旧服务能否读取，不能直接回退到只接受 v2 的栅栏；批次 0 定原则，T9 验证具体方案          | T2/T5/T9                                                     |
| 精确版本不存在、内容 hash 不符、同版本冲突或越权 | 按真实原因拒绝对应操作并保留已保存价值；不找“最近版本”替代、不开放权限绕过                                          | T2/T4/T5                                                     |

批次 0 的输出将区分：本轮必须实现、只保留兼容行为、明确不支持但需诊断的情况。未来升级测试通过不等于支持未知未来协议。

## 5. 用户核查与总控责任

总控承担机械验证、源码差异、JSON/来源核查、测试证据、依赖/WIP、写入冲突、独立验收安排和 TASKLIST 更新。用户不需要替工程排环境、逐个查看原始日志或猜该分发谁。

集中需要用户参与的节点：

1. **批次 0：** 核查完整方案的用户结果、旧包处理/升级边界，以及首案贡献成本和公平比较标准。总控提供具体决定清单与材料后核查，不先发空白问题。
2. **批次 3：** 作为贡献者核查真实包的对象、结果性质、来源和限制，实际体验形成/确认/阅读；科研确认是产品行为，不能由结构测试代替。
3. **批次 5/6：** 安排真实接手者，核查首案收益与第二案的关键可信结果；参与者在测量前登记，不要求现在就等待人员排期。
4. **批次 7：** 核查可开放范围、部署结果和普通用户实际入口，按项目流程处理重要合入/发布决定。

涉及 schema/auth 等 high 风险变更，代码人审遵循项目 review-workflow 的负责人/CODEOWNERS 要求；总控技术复核不能替代其规定的人审。用户的产品核查和代码人审是两类职责，总控会在对应交付中标明。
