# OpenAIR / PVD / OT｜任务 Done 与真实运行验收标准

**版本**：v1.0
**日期**：2026-09-07
**状态**：CANDIDATE
**适用范围**：PVD Standalone Agent、OpenAIR OT，以及后续同类 Workflow / Skill / Agent / 系统治理任务

---

## 1. 目的

建立一套唯一、可核查、可复用的任务完成标准，避免再次出现：

- 代码改完、测试通过，但用户问题仍然存在；
- E2E 跑通，但效果变差、速度变慢或体验变差；
- 为了跑通单个 Query，引入新的固定规则、Gate、alias 或特殊恢复逻辑；
- 局部异常被隐藏，但真实数据、科研质量或用户价值被牺牲；
- 文件拆了、函数短了，但职责和失败面没有真正缩小；
- 当前问题修复了，正式合同仍保留旧规则，后续又把同类脆弱性施工回来。

**统一裁决：任务只有同时满足工程、产品价值、真实运行和正式收口四类标准，才允许标记 Done。**

---

## 2. Done 的统一定义

### 2.1 状态流转

```text
未开始
→ 施工中
→ 工程通过
→ 产品价值通过
→ 真实运行通过
→ 正式收口
→ Done
```

任何阶段未通过，都不得提前标记 Done。

### 2.2 四道验收门

| 验收门 | 核心问题 | 必须回答 |
|---|---|---|
| G1｜工程通过 | 实现本身是否正确、简单、边界清楚？ | 改了什么？职责是否正确？有没有新增脆弱规则？targeted tests 是否通过？ |
| G2｜产品价值通过 | 用户到底得到什么改善？ | 用户原来的痛点是否真正消失？结果质量是否保持或提升？ |
| G3｜真实运行通过 | 真实场景是否证明改善？ | 效果、效率、体验、鲁棒性/恢复、可信度是否分别达标？ |
| G4｜正式收口 | 同类问题以后会不会重新长回来？ | 合同、Schema、Skill、状态和文档是否同步？是否留下临时补丁或双重规则？ |

---

# 3. G1｜工程通过

工程通过只证明“实现可以进入产品验收”，**不等于 Done**。

## 3.1 必须检查

### 责任边界

- 自然语言理解、科研判断、相关性、comparability、mechanism、trend、support/conflict 等语义判断由 LLM / 正式语义层负责。
- 代码只处理已经正式化的数据：
  - ID；
  - parameter_key；
  - unit identity / dimension；
  - operator；
  - numeric value；
  - source / provenance；
  - recommendation / planned / actual 身份；
  - 用户明确硬约束；
  - 状态机；
  - 存储；
  - resume；
  - 明确的资源预算和协议结构。
- 不新增 regex、keyword、字符串包含、有限 alias、固定数量、固定科研形态或复杂 if/else 作为科研/自然语言 authority。

### 失败范围

必须回答：

```text
一个字段坏了，最多坏到哪里？
一条记录坏了，最多坏到哪里？
一篇文献坏了，最多坏到哪里？
一个候选坏了，最多坏到哪里？
一个 Provider / 存储 / 状态错误，是否真的必须阻塞？
```

默认原则：

```text
坏字段       → 删除 / unknown / 未核验
坏记录       → 丢该记录
坏文献       → 丢该篇
坏 Evidence  → 丢该条
坏候选       → 淘汰 / 补生成
可选增强失败 → 跳过
真实系统故障 → 才允许升级
```

### 结构复杂度

结构治理不能只看“拆了几个文件”。

必须同时满足：

- 一个模块有明确单一主职责；
- 编排、科研判断、异常恢复、Provider、状态组装、渲染等职责不再揉在一个巨型函数中；
- 修改一个局部能力时，不需要理解或改动整条 Workflow；
- 局部异常可以在本层处理，不需要跨多层猜测；
- 不新增 reviewer、recovery layer、特殊状态或中间编排对象来维护已经过重的结构；
- 明显超长且多职责的文件/函数必须进入治理，不允许仅以“当前能跑”为理由长期保留。

### 测试

- 只运行与当前任务直接相关的 targeted tests；
- 覆盖成功、局部异常和边界场景；
- 对脆弱性治理任务至少加入一个“表达变化/局部异常”回归用例；
- 不以 full pytest 代替任务级验收；
- 代码级 PASS 不等于真实运行 PASS。

# 4. G2｜产品价值通过

每个任务开工前必须先写清楚：

### 用户原来的问题

要求用用户语言描述，例如：

> 用户已经等待 8～10 分钟，最终因为一个单位表达问题整轮失败，只能重新开始。

不要只写：

> `DeviceBoundaryError`。

### 用户得到的改善

必须具体，例如：

> 同一个物理量使用常见等价表达时不再导致整轮失败；无法确认的单个边界只标记为未核验，合法结果继续形成。

### 产品价值检查

每个任务至少回答：

1. 用户原来的问题是否真正消失？
2. 用户最终拿到的结果是否更多、更准或更稳定？
3. 有没有为了“跑通”而降低科研质量？
4. 用户是否减少等待、重复输入、重新运行或人工排错？
5. 用户是否需要学习系统内部格式、标准单位、Schema 或特殊命令才能正常使用？
6. 改动是否让失败更容易理解和恢复？
7. 是否只对黄金 Query 有效，还是同类正常输入都有效？

任何一项出现明显倒退，都不能进入 Done。

---

# 5. G3｜真实运行通过

真实运行必须拆成 **5 个独立维度** 验收。

不能用一句“E2E PASS”代替。

---

## 5.1 效果

回答：**系统最后给用户的东西是不是对的、够用的？**

### 核查内容

- 是否完成用户要求的目标；
- 关键结果是否完整；
- 科研判断质量是否保持或提升；
- 有效 Evidence / experiment / candidate 是否被保留；
- 不确定性是否真实表达；
- 是否出现为了继续流程而静默丢失关键事实；
- 用户要求 N 组时，是否尽可能形成 N 组合法结果；
- 无法形成完整结果时，是否给出真实、可用的部分结果和原因。

### 证据

至少提供一种：

- 最终用户 Artifact；
- 前后结果对比；
- 结构化结果快照；
- 关键字段人工核查；
- 必要时与已知真实实验/文献事实交叉验证。

### 通过标准

任务必须预先写清具体标准，不能只写“结果看起来正常”。

---

## 5.2 效率

回答：**用户为了得到结果花了多少时间和系统资源？**

### 核查内容

- 总耗时；
- 当前任务涉及阶段的耗时；
- LLM 调用次数；
- 重试次数；
- 是否重复执行已经完成的节点；
- 并行能力是否真实生效；
- 是否因为新 reviewer、Gate、恢复层增加额外等待；
- 为提高质量增加的成本是否合理；
- late failure 后恢复是否避免重新跑前置节点。

### 建议记录

```text
总耗时：
关键阶段耗时：
LLM calls：
重试：
重复执行节点：
并行度：
resume 节省时间：
```

### 通过标准

- 不允许为了结构“更漂亮”明显降低用户等待体验；
- 不允许通过大量额外 LLM 调用换取本可由更简单设计解决的问题；
- 若任务目标本身是性能治理，必须给出 before / after；
- 若效率略有下降但效果显著提升，必须明确说明并由产品价值裁决接受。

---

## 5.3 体验

回答：**用户能不能顺畅、清楚地使用，而不需要理解内部实现？**

### 核查内容

- 页面是否稳定，不乱跳、不串页、不清空已完成结果；
- 用户正在阅读的 Artifact 是否稳定；
- 状态词是否通俗；
- 是否暴露 Schema、Gate、traceback、内部异常类等机器信息；
- 失败时用户是否知道：
  - 发生了什么；
  - 已经保留了什么；
  - 是否需要自己操作；
  - 能否继续；
- 是否需要用户重复提交已经提供的信息；
- 是否需要记住特殊单位、固定措辞、内部参数名或特殊命令；
- 输出是否简洁、可读、能支持下一步决策。

### 证据

- 页面截图；
- SSE / task status；
- 用户 Artifact；
- 实际操作步骤；
- 失败/恢复路径截图或记录。

### 通过标准

用户只需要表达自己的研究问题和真实事实，不需要适应系统内部规则。

---

## 5.4 鲁棒性与恢复

回答：**换一种正常输入或出现一个局部异常，系统还能不能继续？**

### 输入变化检查

与任务相关时，至少覆盖其中一种：

- Query 改写；
- 中英文/缩写变化；
- 单位表达变化；
- 参数顺序变化；
- 多一个真实固定工艺条件；
- 少一条可选 Evidence；
- 某篇文献全文不可得；
- 某个候选不合法；
- 一次 LLM 输出不完整。

### 局部异常检查

必须证明：

```text
局部异常 ≠ 整 Node 失败
局部异常 ≠ 整 Run 失败
```

除非无法安全继续。

### Resume 检查

对 late-stage 任务必须确认：

- 最近可信 checkpoint 已持久化；
- failed / interrupted 等外部状态不会阻止合法恢复；
- 已完成节点不会重复执行；
- 恢复后的 ScientificState / Artifact 保持一致；
- 用户不需要重新等待已经完成的 5～10 分钟工作。

### 通过标准

不是要求“永不失败”，而是：

> 正常表达变化不应成为失败原因；局部异常只影响局部；真正系统故障发生后也能从最近可信状态恢复。

---

## 5.5 可信度

回答：**为了鲁棒和继续运行，有没有牺牲真实性？**

这是硬红线。

### 必须保护

- source / provenance；
- actual / planned / recommendation 身份；
- 用户明确 hard constraints；
- 真实实验事实；
- BO 固定输入输出及自身模型身份；
- 正式 unit identity / dimension；
- Artifact / checkpoint / state 的真实一致性。

### 禁止

LLM fallback 不得：

- 编造设备边界；
- 编造实验结果；
- 编造文献来源；
- 修改用户明确硬约束；
- 把 recommendation 当 actual；
- 为满足 Schema 或数量要求伪造科研证据；
- 用“unknown → guessed value”换取流程继续。

### 通过标准

鲁棒性来自：

> 局部丢弃、未核验、补生成、resume。

不能来自：

> 猜测、伪造、篡改或隐藏关键事实。

---

# 6. G4｜正式收口

真实运行通过后，还必须检查一次“以后会不会重新长回来”。

## 6.1 合同同步

检查：

- Skill 文档；
- JSON Schema；
- runtime contract；
- Workflow；
- Failure contract；
- Resume contract；
- tests；
- 用户可见说明。

不能出现：

> 代码已经删除旧 Gate，但 Skill 文档仍要求旧 Gate。

## 6.2 删除临时规则

必须清理：

- 单 Query 特判；
- 临时 alias；
- `Line-A regression` 一类长期兼容分支；
- 针对旧 Task 的主流程特殊恢复；
- providerless / submission_unknown 等只为旧失败现场存在的补丁；
- 已经失效的 fallback、Gate 和旧测试。

## 6.3 单一正式规则

同一件事只能有一条当前正式路径。

例如：

```text
单位正式化
```

不能同时存在：

```text
LLM semantic normalization
+ Python alias authority
+ Node9 临时字符串兼容
```

唯一任务总表统一使用以下字段：

| 字段 | 用途 |

| 类别 | 语义归位 / 局部隔离 / Resume / 结构拆雷 / 合同 |
| 用户问题 | 用户实际痛点 |

# 9. 三类典型任务的示例

## 9.1 单位语义正式化

### 用户问题

用户用正常的等价单位表达，最终阶段可能因为 `degC / ℃` 这类内部字符串差异整轮失败。

### Done

**工程**
- 自由单位先形成正式 unit identity / dimension；
- 代码只做正式单位后的数学换算；
- 不新增有限 alias authority。

**效果**
- 正确 hard boundary 仍被严格执行；
- 单位表达变化不改变科研结果。

**效率**
- 不新增额外 reviewer 链；
- 不因为单位形式变化重复跑前置节点。

**体验**
- 用户无需知道 canonical unit 写法；
- 无法确认时显示“该边界未核验”，不显示内部异常。

**鲁棒性/恢复**
- 多种等价单位表达通过；
- 单字段异常只影响该字段；
- late failure 可从最近 checkpoint 继续。

**可信度**
- 不猜未知边界；
- 不改变用户硬约束。

只有以上全部通过，任务才 Done。

---

## 9.2 最终候选局部淘汰

### 用户问题

一个候选违规，可能让已经运行数分钟的最终推荐整体失败。

### Done

**工程**
- 单 candidate 校验独立；
- 非法 candidate 被淘汰；
- 支持补生成缺失数量。

**效果**
- 合法候选全部保留；
- 用户要求 N 组时尽可能形成 N 组。

**效率**
- 不重新跑 Node1～Node7；
- 只补缺失 candidate。

**体验**
- 用户看到合法方案和真实不足原因；
- 不看到内部 Gate / exception。

**鲁棒性/恢复**
- 人为制造一个坏 candidate，Run 继续；
- 补生成失败也保留已有合法结果。

**可信度**
- 不为凑 N 组伪造候选或证据。

---

## 9.3 巨型模块拆雷

### 用户问题

一个文件/函数同时承担过多职责，任何局部修改都可能影响整条链，形成高回归和高失败风险。

### Done

**工程**
- 职责真正拆开；
- 不是纯粹把 3000 行移动到多个文件；
- 每个模块有明确输入、输出和异常范围；
- targeted tests 通过。

**效果**
- 拆分前后科研结果保持一致或更好。

**效率**
- 不新增额外 LLM 调用或不必要中间编排；
- 关键阶段耗时不明显恶化。

**体验**
- 用户路径和 Artifact 不因内部重构变复杂。

**鲁棒性/恢复**
- 单模块故障范围缩小；
- 修改一个能力不再牵动整条 Workflow。

**可信度**
- provenance、状态和身份语义保持不变。

因此：

> “文件从 3500 行拆成 5 个文件”永远不能单独作为 Done 证据。

# 10. 最终裁决规则

满足以下任意一条，任务不得标记 Done：

- 只有代码 PASS；
- 只有 targeted tests PASS；
- 只有一次黄金 Query E2E PASS；
- 为跑通新增了固定 alias / regex / keyword / Gate；
- E2E 成功但科研结果质量下降；
- E2E 成功但耗时明显恶化且没有产品价值理由；
- 内部错误被隐藏，但关键真实数据被静默丢失；
- 用户需要适应内部单位、固定措辞、Schema 或特殊命令；
- late failure 仍要求重新跑已经完成的节点；
- 结构拆分没有减少职责耦合和失败爆炸半径；
- 代码改了但正式合同仍保留旧规则；
- 通过 fallback 编造或修改真实事实。

最终 Done 必须能用一句用户语言说明：

> **用户以前遇到的具体问题已经消失，并且真实运行证明结果更可靠、效率可接受、体验顺畅、异常可恢复、事实可信。**

如果这句话无法被证据支持，就还没有 Done。
